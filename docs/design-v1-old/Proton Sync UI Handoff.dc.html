Proton Drive Sync — desktop UI implementation contract

This document is the bridge between the HTML design prototypes in this project and the Rust daemon that already exists. Its purpose is narrow and specific: for every number, label and control in the UI, state where the value comes from, so that nobody has to guess or invent an API while building. The prototypes are the visual truth; this document is the data truth.

The engine ships today as proton-syncd (a systemd user daemon) and proton-sync (a CLI). There is no GUI. Everything described here is additive: the UI is a client of the existing control socket plus the state files the daemon already writes.

1 · Fidelity and scope

The prototypes are high fidelity. Colours, type sizes, spacing and copy are final and should be reproduced as specified in section 7. Layout structure, interaction wiring and state behaviour are also final. What is not specified is the implementation toolkit — the mocks were built as web UI per the brief, so an Electron or Tauri shell reproduces them directly; a GTK4 or Qt implementation should treat them as a spec rather than markup to port.

The one non-negotiable
Two-way sync deletes user files. A remote deletion removes the local file permanently — not to trash — and folder deletions are recursive. The persistent safety banner, the dry-run gate before the first sync, and the typed DELETE confirmation before applying a destructive plan are product requirements, not decoration. Do not ship the UI without them.

2 · Architecture: the UI is a thin client

The GUI owns no sync logic and no index. It reads state and issues four commands. Three data sources cover every screen:

SourcePathUsed for
Control socket$XDG_RUNTIME_DIR/proton-sync.sockLive status, history, and the pause / resume / sync-now commands. Newline-delimited JSON, mode 0600, one client at a time.
State files<local_root>/.sync/The sync index (per-path state, sizes, timestamps, remote ids) behind the activity ledger and the file-manager emblems.
Config~/.config/proton-sync/proton-sync.tomlEverything in Settings. Written by the UI at 0600; saving restarts the daemon.
Journaljournalctl --user -u proton-syncdThe "Open journal" / "View journal" actions and error detail beyond the last-error string.

Poll status on a short interval (2 s while the window is focused, 10 s when it is not) and treat a socket error as its own UI state — never as zeroes. Section 6 covers this.

Each screen below lists its dynamic elements against the field or file that supplies them. Field names are the daemon's own, so they can be grepped in the repo.

3.2 Activity

The same ledger at full height with the filter chips promoted to the header. One row per planned or executed action: upload, download, move_local, move_remote, conflict, skip_unsupported, auto_link, error. Action colour carries direction (section 7); the row never relies on colour alone, the action name is always present.

3.3 Conflicts

The engine's conflict handling is non-destructive: when both sides changed, it keeps the local file and writes the remote copy beside it as name.proton-cloud.ext. Resolution therefore needs no new IPC verb — it is ordinary file work the UI performs on disk:

ChoiceFile operation
Keep mineDelete the sidecar. The local file uploads on the next pass.
Use Proton'sMove the sidecar over the original, replacing it.
Keep bothRename the local file to name.local.ext, then move the sidecar into place. Both then exist on both sides.
Decide laterNothing on disk. Still counts as outstanding everywhere in the UI.

Choices are staged and applied together, so a mis-click is recoverable before anything is written. Text files get a line-level diff; binaries show size and timestamp only, never a fabricated preview. Every conflict counter in the window — sidebar badge, tab header, Needs-you card, stat tile, ledger chip — must read from the same unresolved set. Disagreeing counts destroy trust faster than a missing feature.

3.4 Plan preview (dry run)

Runs the daemon with --dry-run and renders the JSON plan: a summary of every counter, then one row per action with path and remote id. Destructive rows are tinted and sorted to the top. Selecting a row explains, in plain words, why the planner chose it — index state plus what changed on each side.

The Apply button stays inert until the user types DELETE whenever destructive_actions > 0; with no destructive actions, Apply is enabled directly. After applying, the footer states what was executed, including the destructive count.

3.5 History

A reverse-chronological list of status_history entries with a per-entry summary. The daemon keeps the last 20 in memory, so the UI must state that limit rather than implying a full audit log; longer history comes from the journal.

3.6 Settings

A direct editor for the TOML, grouped: folders (local_root, remote_root), schedule (scan_interval_secs, events_driven), selective sync (include / exclude globs), the CLI (path, proton_timeout_secs, proton_list_attempts), and service startup.

Selective sync is presented twice over one source of truth: a folder tree whose checkboxes write exclude globs, and an advanced disclosure exposing the raw patterns with live match counts. Exclude beats include, and .sync/ is always ignored — state both in the UI. Changing a root re-bootstraps the index, so that path forces a dry run before the daemon restarts.

3.7 Tray indicator

An AppIndicator menu carrying the status line, pending_changes, conflict count, and the same actions as the window. Its glyph is symbolic and monochrome-safe with five states: up to date, syncing, paused, needs attention, daemon unreachable. When the socket is unreachable the menu collapses to Start service / View journal / Settings and shows no stale counters. "Quit" closes the window only — the daemon keeps running, and the menu says so.

3.8 Onboarding

Four steps: verify the proton-drive CLI is present and authenticated, choose the folder pair, review the dry-run plan, start the service. The first pass is a non-destructive merge and the copy should say so plainly, while still requiring the explicit acknowledgement that deletions later propagate both ways. Nothing syncs before that checkbox and the plan review.

3.9 File-manager emblems

Five 16 px symbolic emblems — synced, syncing, conflict, excluded, paused — for Nautilus (Python extension), Nemo, and Dolphin (KIO overlay). They read the sync index plus a per-path status query, and ship as optional per-distro packages rather than inside the Flatpak.

4 · Gaps the engine does not cover yet

Everything above is buildable on today's engine except the following. Each is a deliberate design bet on work the daemon does not do yet; decide each one before building the screen that depends on it.

UI expectsEngine todaySuggested resolution
Per-file transfer percentageOnly [i/N] file countsShip file-count progress first; add byte progress to the status payload later. Do not fake a percentage.
Remote folder browserNo listing verb on the socketThe UI can shell the CLI directly for listings, or the daemon gains a read-only list command.
Apply a reviewed planDry run and real run are separate invocationsEither accept that Apply triggers a fresh pass (the plan may differ — re-run and re-confirm if it does), or add a plan token the daemon can execute.
Live event pushRequest/response onlyPolling is adequate at these intervals; revisit only if the UI feels laggy.
Multiple folder pairsOne root pair, one daemon per userThe pair selector and header are already shaped for many; ship one and leave the affordance.
Auth state detectionSurfaces as CLI call failuresPattern-match the auth error to drive the "sign-in expired" state, or have the daemon classify it.

5 · Interaction rules

  • Every command is optimistic in the UI but confirmed by the daemon's reply, shown as a dismissible strip below the safety banner. If the reply does not arrive, revert the optimistic state.
  • Pause and Resume are one button whose label follows the state. Never show both.
  • Conflict choices are staged, not applied on click; the footer counts what will be written, and each decided file offers "Change choice" until Apply.
  • Destructive confirmation is typed, not a checkbox, and the gate copy names the specific file that will be lost.
  • Resolve links anywhere in the app open the Conflicts tab with that file already selected. No dead-end links.
  • Any list that can overflow scrolls. A clipped last row in a sync client reads as data loss.
  • Follow the system light/dark preference; the theme is a palette swap over one layout, not two designs.

7 · Visual specification

The palette derives from the repo's own icon: warm orange is local and upload, cyan is remote and download. That mapping is the core of the visual language — apply it to arcs, arrows, action names, diff panes and emblems alike, and never use it decoratively. Red is reserved exclusively for destructive actions.

IBM Plex Sans for interface text; IBM Plex Mono for every path, glob, field name, timestamp, id and count — the mono/sans split tells the user at a glance which strings are literal engine values. Gaps 16 px between cards, 12 px between tiles, 6–9 px inside control groups. Sidebar 214 px, conflict rail 236 px, action column 140 px, title bar 42 px, status footer 30 px. 8 · Packaging

Fedora is the development target; Ubuntu and Arch are first-class. Flatpak is the primary channel because it covers all three from one build, with native packages for users who prefer them: RPM (Fedora, via COPR), deb (Ubuntu), and a PKGBUILD on the AUR. All wrap the same daemon and CLI binaries plus the systemd user unit.

Two Flatpak-specific consequences the UI must handle: the sandbox needs explicit access to the chosen sync folder and to the host proton-drive binary, and the file-manager emblem extensions cannot ship inside the Flatpak — they are separate distro packages, so treat emblems as an enhancement and never the only signal of sync state. Because one daemon per user account is enforced by a global lock, the UI should surface the lock holder rather than failing silently when a second instance is attempted.
