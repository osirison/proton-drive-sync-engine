## Three ways to drive it

<CardGrid>
  <Card title="proton-syncd — the daemon" icon="seti:rust">
    A long-running background service that watches a local folder, reconciles it
    with Proton Drive, and applies uploads, downloads, moves, and deletes. Event-driven
    change detection keeps ongoing passes fast.
  </Card>
  <Card title="proton-sync — the CLI" icon="seti:powershell">
    A thin control client over a Unix socket: check `status`, `pause`/`resume`,
    trigger a `syncnow`, review `history`, and approve or deny withheld deletions.
  </Card>
  <Card title="Proton Drive Sync — the app" icon="laptop">
    A Tauri desktop app for Linux: live status, an activity ledger, side-by-side
    conflict resolution, a typed-confirmation dry-run review, settings, onboarding,
    and a system-tray indicator.
  </Card>
</CardGrid>


![The desktop app's main window with three changes syncing and two cards below it: one file changed on both sides with a Compare button, and two deletions waiting on you with a Review button.](../../assets/screenshots/main-needs-you.png)

<p><sub>The app never acts on a conflict or a deletion by itself — it stops and asks.</sub></p>

## Built to be trusted with your files

<CardGrid>
  <Card title="Preview before you commit" icon="magnifier">
    Every run can be previewed with `--dry-run`, which prints the exact plan as JSON
    and never touches a byte. The app renders the same plan and gates destructive
    applies behind a typed `DELETE` confirmation.
  </Card>
  <Card title="Deletions ask first" icon="warning">
    A directional **delete-approval** guard is on by default: deletions are withheld
    until you approve them, per item and per direction, and can be relaxed per folder.
  </Card>
  <Card title="Conflicts keep both sides" icon="document">
    When both sides change, nothing is lost — the engine writes a `.proton-cloud`
    sidecar so you can resolve it deliberately.
  </Card>
  <Card title="Commit only after success" icon="approve-check">
    The sync index records an action only *after* its side effect succeeds, in
    incremental checkpoint commits. A failure mid-plan keeps completed work durable
    and replans the rest; it never leaves half-recorded state.
  </Card>
</CardGrid>

:::caution[Early prototype — read the safety guide]
Sync is bidirectional and deletions propagate. A file deleted on Proton Drive is
removed from your local disk **permanently** (not to your OS trash), and folder
deletions remove the whole subtree. Test with disposable folders and backups first,
and read [Deletions & the safeguard](/safety/deletions/) before your first run.
:::
