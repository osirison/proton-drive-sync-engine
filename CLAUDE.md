# CLAUDE.md

## Overview

Rust prototype for bidirectional file sync between a local folder and Proton Drive. Ships two binaries backed by one library crate (`proton_drive_sync_engine`):

- `proton-syncd` (`src/bin/proton-syncd.rs`) — the daemon. Its one-shot `--dry-run` returns before `Daemon::new`: it takes **neither** lock (the global one would fail exactly when a daemon is up, the only time a preview is useful) and builds its **own** client; it only *warns* on stderr when a daemon holds the global lock (`daemon::probe_daemon_lock`: non-blocking shared `flock`, never creates the file; stdout is the report). A preview shows **one** pair — the first, or `--pair NAME` (byte-exact; an unknown name errors listing the configured pairs). `--pair` is checked after config resolution, not by clap (whether a run is a preview depends on `--dry-run`, `--no-dry-run` *and* the file's `dry_run`), and is an error unless the run is a preview. Without `--dry-run` every resolved pair goes to `Daemon::new`.
- `proton-sync` (`src/bin/proton-sync.rs`) — thin control CLI that talks to the daemon over a Unix socket.

Unix-only today: control-plane IPC uses Unix domain sockets (`#[cfg(unix)]` guards in `src/ipc.rs`). Edition 2024 toolchain required.

## Architecture

The engine reconciles **three sources of truth** into a plan, then executes it:

1. Local files under `local-root` (`index::scan_local_files_with_options`, SHA-1 hashed)
2. Remote files from `proton-drive filesystem list --json` (`proton::ProtonClient::list`)
3. The last-synced baseline in SQLite (`index::load_index`)

Data flow: **scan → `sync::plan_sync` → execute actions → commit index**. This is the spine; changes to sync behavior almost always start in `src/sync.rs`.

### Module responsibilities

One bullet per module. Only rules a change elsewhere could break, and traps, are listed; per-site reasoning lives in the doc comment on the item.

- `src/sync.rs` — **pure** planner, no I/O. `plan_sync` → `Vec<PlannedAction>`; bootstrap (empty index) and ongoing logic are separate, and ongoing decisions come from a `(local_delta, remote_delta)` matrix. Keep:
  - `plan_entity_action` is the **one** definition of what a path plans to. `compute_directory_deletion_verdicts` proves a recursive delete through it, never through `base.entity_kind` alone (that once deleted the only copy of a file, #282).
  - `ConflictNaming` (from `conflict_suffix`, default `proton-cloud`) must also reach every **detector**: `ScanOptions`, the daemon watcher and the GUI's disk walk. Otherwise the engine uploads the sidecar it just wrote. Changing the suffix orphans existing sidecars (they upload as ordinary files).
  - A local path that is not valid UTF-8 is unsyncable: it plans `SkipUnsupported`, built only through `PlannedAction::skip_unsupported`, which records why. It is never a transfer, so no subtree holding one is proved clean for deletion. Remote names are never screened.
  - `SyncAction::is_destructive` is the one destructive set: what the plan counts and what `apply --skip-destructive` drops. `delete_direction` is the approval gate's set and excludes `Purge`. Never add a second spelling of either.
- `src/daemon.rs` — the runtime. Read the doc comments on `step_blocking`, `run_job`, `PairRuntime`, `PairPass` and `ControlShared` before changing the loop. Keep:
  - **One loop, one step function.** `run()` loops on `step_blocking`, the same body the tests drive. Each step does a **bounded** drain of the control and watcher channels (`MAX_DRAIN_ROUNDS`, with the cancel flag read between events, so a flood cannot hold off a pop or a shutdown), then runs one popped job. Only the step function starts a pass, which is what keeps `syncing` unique. `Daemon::route` has one call site. Nothing reconciles before the loop: each pair's first pass is its first job, so the socket answers during boot and a shutdown cuts at a pair boundary. A pair is re-armed from the moment its pass **ends** (`cadence_for`).
  - **The control socket is served on its own task** from a published `ControlShared` snapshot, so status, pause and approve answer while a pass blocks the main task. `List` is the only verb that does work there: one CLI child behind `CliGate`, with a bounded wait that answers `busy`. `Syncnow` and `Plan` ack immediately, and clients poll `reconcile_seq`.
  - **State is split by scope** (ADR 0005 §1). `PairRuntime` holds one pair's state. `Daemon` holds what the process shares: one `Arc<C>` client (and so one `CliGate`), the cancel flag, the event session and the global lock. Passes run on `PairPass`, built **only** by `pass_for(i)` from the index the queue popped (see the N-pairs invariant).
  - **Locks:** every per-root lock first, then the user-global lock. A per-root lock that another process holds is fatal at boot (`LockHeld`); mid-life it keeps that pair unavailable.
  - **Real paths are checked before anything is created** (`real_path_overlap`). The config reader's rule is lexical and misses symlinks, and a nested pair has its `.sync` uploaded by the outer pair. The check runs at boot (fatal), on every retry, and before every `Sync` job of a running pair. **Both** pairs of an overlap are stopped. Rejected alternative: a scanner-side guard against other pairs' `.sync`, because a nested `.sync` can be user data (ADR 0005:1498).
  - **Pair selector** (ADR 0005 §4): `ControlShared::resolve_pair_index` is the one resolver, and it is byte-exact. An unresolved selector does nothing. With several pairs the daemon says once at startup that a request naming no pair acts on the default pair (maintainer decision M4).
  - **The plan verb is `Syncnow`-shaped.** It runs on the main loop (a full walk never runs on the IPC task) and shares `build_plan_report` with the one-shot `--dry-run`, so a rehearsal has one definition. See the plan-only invariant for `syncing` vs `reconcile_seq`.
  - Every log line of a job sits in a `pair{name=…}` span built by `pair_span` as `error_span!`. An info span is never created under `RUST_LOG=warn`, which dropped the pair name from the WARN lines.
- `src/ancestor.rs` — **pure** (#217): what each side of a conflict did to the last agreed version, for the conflict card. It is captured at **commit time** (`daemon::collect_agreed_summaries`): by the time a conflict exists, the agreed version is on neither side. Uncertain cases answer `None`. The line diff is deliberately duplicated in `gui/src/js/ui/diff.js`; `AGREEING_CORPUS` holds the two together, so change both.
- `src/schedule.rs` — **pure** `FullScanSchedule` (#193): the user-set full sweep (`weekly <day> HH:MM` / `monthly day <n>, HH:MM`). Three triggers can ask for a full walk: `events_full_scan_every` (in-run passes), `warm_start_full_walk_every` (warm starts) and this one (wall clock). All three set the same idempotent `force_full_walk` latch. A missed run is skipped. Daylight saving is decided only in `resolve_local`: an ambiguous time takes the **earlier** instant, compared as instants, not by field.
- `src/due_queue.rs` — **pure** `DueQueue` (ADR 0005 §5): which pair runs next. No I/O and no clock reads (`now` is passed in). Explicit requests go first in FIFO order, then the earliest deadline. It cannot spin, by construction.
- `src/reconstruct.rs` — **pure** `reconstruct_remote(base ⊕ delta)`: overlays a volume-event delta on the baseline, so the planner gets a complete remote map without a walk. Anything it cannot resolve returns `FallbackToSnapshot` (re-bootstrap rather than plan against an incomplete map). Removals cascade over the tracked subtree. Created and updated nodes are placed by listing their parent through the injected resolver, memoized per pass. A `Created` node missing from its parent's listing falls back, because the CLI listing lags the event stream (#30). Placement, and the skip for events outside the pair's folder, are decided here from the pair's root uid: see the cannot-place invariant and ADR 0006. It never reads another pair's index.
- `src/proton.rs` — the `ProtonClient` trait, and `ProtonDriveClient`, which shells out to `proton-drive`. Listings are tree-shaped JSON, and SHA-1 comes from `activeRevision.claimedDigests.sha1`, the only remote metadata the engine trusts. Keep:
  - **`CliGate` serializes every child process.** It is taken in `run_once`, the one place a child is spawned. The CLI is not concurrency-safe (a shared SQLite store, #23). The gate is held per child, not per pass, and the wait is bounded only for interactive callers (`CliBusy`). One client is one gate, so the daemon shares one `Arc<C>`; never build a second client.
  - **A listing is all-or-nothing.** An id or locator that is present but cannot be decoded fails the whole listing (`remote listing is incomplete`), because a dropped node reads as deleted and plans a `LocalDelete` (#59).
  - **CLI stderr is classified here and nowhere else** (`cli_failure` → typed `NodeNotFound`, `AuthFailure`, `CliBusy`). Callers downcast; they never match the text a second time.
  - Only read-only listings retry (`CommandPolicy`). `download_many` runs one chunk of downloads in a single invocation.
- `src/events.rs` — remote change detection through the volume event stream (ADR 0001); pure and transport-agnostic. `parse_volume_events` → `RemoteChange` (a trash is `Updated`+`trashed`, not `Deleted`). `EventsClient` refreshes once on 401. A fetch that got **no answer** (429, 5xx, timeout, dropped connection) is the typed `TransientFetchError`, and the daemon holds the pass for it (the change-feed invariant). Every other error counts as an answer, and the daemon walks. The transport and session are injected, so the crate ships no networking dependency. `events_driven` is on by default (`--no-events-driven` restores the snapshot-only path). With no keyring session the daemon degrades to snapshots on `scan_interval`.
- `src/index.rs` — the SQLite schema (`SCHEMA`), the local scan with SHA-1, `ScanOptions`, record CRUD, the per-scope event cursor, and `path_for_proton_id` (stored `proton_id` = composed `volumeId~nodeId`; bridge a raw `LinkID` with `events::node_uid`). Keep:
  - Paths are stored byte-exact (BLOB keys), because non-UTF-8 paths are real data.
  - `ScanOptions` must carry the daemon's `ConflictNaming`, not a default.
  - The never-synced set is one predicate, `is_never_synced_directory`, read by **both** the ignore test and directory traversal. The set is: a top-level `.sync`, `.proton-sync.toml` at any depth, conflict sidecars, and FreeDesktop trash directories (`.Trash`, `.Trash-<digits>`). A trash-mode local delete relocates the file into such a directory, so without the predicate the file uploads back.
  - `scan_local_tree` returns the kept entities **and** the dropped unsyncable entries from one walk. There is no partial form, so absence from it is evidence.
  - `reset_index_state` truncates every learned table in one transaction. It never truncates `pair_pause` (the user's request) and never removes the database file (a running daemon holds it open).
  - History is one schema: `sync_passes` (the retained rollup, notable passes only) and `sync_events` (expiring detail). Byte totals come only from the rollup. `last_transfer` is the engine's only remote-side timestamp; `file_index` has none. Retention exempts the newest full sweep (`id IS NOT (SELECT MAX…)`, not `<>`, because of NULL).
- `src/session.rs` — the current events seams. `CliKeyringSession` reuses the logged-in CLI's session from the OS keyring via `secret-tool`; a refresh re-reads the keyring. `CurlHttpTransport` shells out to `curl` (`--connect-timeout 10`, `--max-time 30`). `transient_curl_exit` is the one list of curl exit codes that mean "no answer". Independent auth is deferred (ADR 0001).
- `src/config.rs` — layered config. Precedence: **CLI flag > TOML file > XDG default**. For `dry_run`: `--no-dry-run` > `--dry-run` > file. Keep:
  - Every local path option expands a leading `~` (`expand_tilde`; `~user` is refused). The daemon runs without a shell, while the `proton-drive` CLI does expand `~`.
  - `validate_file_config_text` is the **one** home of post-parse rules, including every local path a file can set. gui-core's writer calls it, and packaged units launch the daemon with no flags, so a rule that only the daemon applies lets the GUI write a config the daemon cannot start on.
  - Two spellings of one setting in one file are a startup error naming both keys (`deletion_policy` vs `[delete_approval]`; `[[pair]]` vs top-level per-pair keys). `deletion_policy` (does a delete wait for approval?) and `local_delete_mode` (`trash`/`permanent`: what a local delete does) are separate questions.
  - A configured `log_level` or `full_scan_schedule` that does not parse is fatal (an unusable `RUST_LOG` falls through). `full_scan_schedule` is file-only, and unset means no sweep.
  - **Folder pairs** (ADR 0005): either `[[pair]]` tables with a required `name`, or top-level keys meaning one implicit pair named `default`. That implicit reading is **permanent**, not a migration step. `ConfigKey::scope` is an exhaustive match (no `_` arm) into `Daemon`/`Pair`, and `every_file_config_key_is_classified_exactly_once` checks both directions. **Residual:** `#[serde(skip_serializing_if)]` on a new `FileConfig` field hides that field from the guard. `ConfigKey::spellings` must list every spelling serde accepts; aliases are attributes, and a test holds the two lists equal.
  - `proton_cli`, `proton_timeout_secs` and `proton_list_attempts` are daemon-wide **by force**: they build the one shared client, and one client is one `CliGate`.
  - `resolve_pairs` is the one definition of the pair set (names, collisions); the daemon and `validate_file_config_text` both run it. No root may sit inside another root, and no pair's `db_path`/`lockfile_path` may sit inside another pair's root. The comparison is **lexical and never fails**: `~` is expanded best-effort, and `.`/`..` are collapsed in the key only. The daemon's real-path check covers what a lexical check cannot see.
  - Remote roots compare by `remote_root_comparison_key`, with the leading `/` stripped (`..` cannot occur, because `proton` refuses it). `same_remote_folder` is its `pub` form, and the GUI must use it.
  - **Beside several pairs:** every per-pair CLI flag is refused at startup, naming it, opt-outs included (M2; `per_pair_flags_set` is an exhaustive destructure). Every table sets both roots. `dry_run = true` inside a table is refused (M3). Daemon-wide values (`ProcessValues`) are computed once, so a resolved set agrees by construction. Config errors are all-or-nothing; only environment failures are handled per pair.
  - `resolve_runtime_configs` is the one resolver; `resolve_runtime_config` (exactly one pair) remains for tests. Clients read through `pair_views` (tolerant: it does not refuse half-written files) and `validate_pair_name(_among)` (the daemon's own sentences).
- `src/dirconfig.rs` — per-directory `.proton-sync.toml` (ADR 0002). A file applies to its directory and everything below it; the nearest file wins, and unset options inherit. Machine-local and never synced. A malformed, unreadable or ambiguous file (one with both delete-approval spellings) fails safe: the guard stays on. To extend, add an `Option` field to `DirectorySettings` and its resolved counterpart in `EffectiveSettings`.
- `src/trash.rs` — the one disposal seam for a local delete: `LocalDeleteMode::Trash` (the default; FreeDesktop trash through the `trash` crate) or `Permanent`. A missing path is an error in both modes. Tests never touch the real trash: lib tests use the thread-local `test_hook` (an un-hooked `Trash` disposal panics), and `tests/trash_disposal.rs` sets `XDG_DATA_HOME` in its own process (`set_var` is `unsafe` under edition 2024).
- `src/ipc.rs` — the JSON-line protocol over the Unix socket. Keep:
  - **Wire compatibility:** new fields are `#[serde(default)]`. Enums and tokens a client may not know end in `#[serde(other)]` or parse to `Other`, so an older client degrades instead of failing the whole reply. Clients branch on **typed outcomes** (`ListingOutcome`, `PlanOutcome`, `ApplyOutcome`, `AuthState`), never by matching `message` text.
  - Every `PathBuf` on the wire goes through `lossy_path` (the wire-path invariant).
  - `ControlRequest.pair` is the selector; `None` means the default pair. `ControlResponse.pair` is `Some(name)` exactly when the selector resolved. `pairs` is **never empty** on a real reply, even with one pair, because it is the clients' capability gate.
  - `Keep` is not `Deny`. `Keep` refuses a withheld deletion: it purges the baseline subtree so the surviving side is re-adopted, and latches a full walk (an incremental pass's remote map *is* the baseline). `Deny` only revokes an approval.
  - `ResetIndex` truncates before the baseline is loaded, then bootstraps. If the truncation fails, the latch is set again. The `--yes` confirmation is client-side; the wire has no field for it.
  - `List` (#99) is the only verb that does work on the IPC task. A subtree is walked **by the client, one request per directory**, and that is the design. A selector starting with `/` is absolute (`validate_absolute_remote_path`), and the reply answers in the same frame as the request.
  - The plan family is `Plan` / `PlanResult` / `Apply <TOKEN>`. `ReviewedPlan.actions` is a bounded window built with destructive rows first, which is safe because an apply names the token, never rows. `skip_destructive` overrides standing approvals for that one run.
  - A per-file transfer percentage is impossible: an upload has a total but no progress, a download has progress but no total, and `totalStorageSize` is not a file size.
  - `proton-sync` prints human-readable output; `--json` gives the raw reply. `list`, `plan` and `apply` exit non-zero when the answer is not a success.
- `src/paths.rs` — default paths. The index, the status and metrics sidecars and the per-root lockfile default to `<local_root>/.sync`, which the engine ignores (only a **top-level** `.sync`). The control socket lives in `$XDG_RUNTIME_DIR`: it is session-scoped, must stay short for `sun_path`, and must be findable without knowing the root. **Two-tier locking:** the per-root lockfile stops two daemons on one root, and a user-global lock under `$XDG_STATE_HOME` stops a second daemon for the same user, because every daemon shells out to the same CLI and the CLI is not concurrency-safe (#23). `CliGate` is the in-process half. `LockGuard` never unlinks a lockfile (`flock` binds the inode, #13), so a leftover file never means a daemon is running. XDG values are honoured only when absolute (#286). The temp-dir fallback fails closed unless the directory is mode 0700 and owned by the euid (#74). gui-core takes the socket path from here.
- `src/lib.rs` — `AppResult`, `boxed_error`, and the shared path primitives: `lexically_normalized` (one definition, used by `config::local_comparison_key` and `index::canonicalize_best_effort`), `wire_path`/`lossy_path` (the one way a `PathBuf` crosses a wire), and the path-safety ladder `validate_relative_path` / `validate_relative_path_non_empty` / `validate_absolute_remote_path` (the path-safety invariant).

### Invariants to preserve

- **Commit-after-side-effects, checkpointed.** An index write never precedes its side effect (ADR 0003). Each side-effecting action, and each batched download chunk, commits its own mutations in a checkpoint right after it succeeds. Index-only mutations (`AutoLink`/`Purge`) ride the next checkpoint or the final commit. The **event cursor** advances only in the final commit of a fully successful pass, never in a checkpoint, and is only ever *read before* the work it claims to cover. A bootstrap captures it before the walk. If that read fails while prior state may exist, the bootstrap persists **no** cursor. It never anchors after the walk, which would claim that changes made during a 30-minute walk were applied (#294; a first-ever bootstrap: #303).
- **Path-safety at boundaries.** Every relative path from outside (remote listing, local scan, conflict target) passes `validate_relative_path` / `safe_local_path` before it is joined onto a root; add a guard and a test at any new boundary. Anything that becomes a **side effect** uses the non-empty form, because `""` joined onto a root turns a per-entry action into a whole-root one (#72). Passing `safe_local_path` does not make a write to a predictable name safe, since a dangling symlink passes it. Such writes use `create_new` (`O_EXCL`) or a rename from a staging directory, and presence checks use `symlink_metadata`, never `exists()`.
- **Non-destructive on unknown digests.** When a remote file exists but exposes no usable SHA-1, `remote_file_delta` returns `FileDelta::Unknown` and the planner avoids destructive actions (see the `Unknown` match arms in `plan_ongoing_action`). Preserve this conservatism.
- **An event the pair cannot place is skipped only when the pair's tree is fully named and fully held** (#456, ADR 0006). The event stream is per volume, so most of a delta is about other folders. An event the pair cannot place is dropped as "outside this folder" only under **condition S**, decided at the end of the delta, never at the event's position in it. Condition S has four parts: the pair's root uid is known and it has no include rules; every directory in the final map carries a composed uid of this volume; no baseline record carries a real id that no event of this stream can carry; and every record sits directly in the root or in a held folder. Otherwise the pass walks, naming the record that blocked it. **A skip is never the answer to an ambiguous case.** These all walk: a tracked node naming a parent the pair does not hold; any event with no parent; the root's own events; a directory moved in by an update; a parent taken out earlier in the same delta. Without a root uid nothing is skipped as outside (the pre-#456 rules apply). A root uid answers only for the `remote_root` it was learned for. A delta whose every event was dropped is an idle pass. ADR 0006 holds the soundness argument (it assumes events arrive in order), the residuals and the model test.
- **Selective-sync filters apply everywhere.** Include/exclude globs (`ScanOptions`) filter local files, remote files, *and* base-index records before planning, so excluded records are never purged as "missing." Conflict sidecars and the index DB itself are always ignored.
- **First pass after boot always full-scans the *local* tree (warm start or bootstrap).** A fresh process has an empty `pending_changes` (`notify` replays nothing), so each pair's first pass must scan locally, or it would idle-skip an edit made while the daemon was down. It either warm-starts (an incremental pass with a forced local scan, replaying the remote from the stored cursor) or bootstraps; only the remote walk differs (ADR 0004). `is_first_reconcile` is per pair and clears only on success, so a failed first pass retries as a first pass. Any doubt about warm-start eligibility means a bootstrap (cursor age, the floor; ADR 0004). A fetch that got no answer is not doubt (the change-feed invariant). To force a walk: `proton-syncd --full-walk` or `proton-sync resync`.
- **Periodic safety resync is opt-in (off by default).** `events_full_scan_every` defaults to `0`, meaning never (`effective_full_scan_every` maps it to `u64::MAX`). After the first pass the daemon stays event-driven until a restart or a forced fallback. A positive N walks every N in-run incremental passes. This is distinct from `warm_start_full_walk_every`, which walks every N warm starts and is persisted: one heals a long-running process, the other a frequently restarted one.
- **A change feed that does not answer holds the pass; it does not walk the tree.** A fetch that got no answer (`TransientFetchError`) says nothing about the cursor or the tree, and walking for it cost about 25 minutes per walk on the largest pair. `wait_for_the_feed_or_walk` instead returns `FeedUnanswered` having touched nothing: no plan, no cursor move, no latch cleared, and the last `failed_items` put back. A held pass is neither completed nor failed. It has its own early return in `reconcile_blocking`, writes no `last_sync`, `last_error` or history, and **does not bump `reconcile_seq`**, which clients read as "the attempt finished". It only seals a booked apply as `Failed`. After `FEED_OUTAGE_BOUND` (10 min, monotonic, per pair) the pair walks and says so. A definitive error (rejected cursor, unparseable reply, 4xx) walks at once.
- **`scan_interval` is not a snapshot cadence in events mode; a degraded session is.** With live events, a `scan_interval` tick is just another (usually idle) incremental pass. It must not force a snapshot (#52); that would bring back the periodic walk. A **degraded session** (`events_driven` on, but no event source) snapshots every pass, so its cadence is `scan_interval`, not the 30 s poll (#50). Cadence is per pair (`cadence_for`), never a process-wide minimum. "Event-driven detection unavailable" is one message family: one reason per cause, said once, and said again only when the cause changes. Session causes latch on the process; no-volume and no-cursor causes latch on the pair. A single shared latch made two pairs overwrite each other.
- **A local change the watcher cannot queue must still force a scan.** The events-mode idle fast-path skips the local walk when the delta, `pending_changes` and `pending_deletions` are all empty, so nothing would ever re-derive a change the watcher dropped. Therefore:
  - a directory `Create`/`Modify` is queued, because an empty `mkdir` emits no file event;
  - a lost-events notice sets `force_local_rescan` on every pair (cleared only by a successful pass) and re-registers the watch, because notify adds a subdirectory's watch only when it handles that directory's own create event (#428).

  notify 8.2 reports an inotify overflow as an **`Ok` event carrying the `Rescan` flag**, not as an `Err` (`event.need_rescan()`, checked before the per-path handlers). The net once never fired because of this (#423). A watcher `Err` and a failed `mark_modified` are the other two causes. Losses are noted while a drain routes and settled once after it. Routing comes before every filter: a path goes to the pair whose root is its longest component-wise prefix, and a path no pair owns is dropped. The bounded drain narrows the window for the daemon's own write echoing back, but does not close it (#425).
- **A wire path is a rendering, never a selector; and an unsyncable entity is named, not counted.** `impl Serialize for Path` errors on non-UTF-8, and `serde_json` is all-or-nothing, so every wire `PathBuf` goes through `lossy_path` (#61, #300). Two paths can collapse to one string, so a command that turns a selector into a destructive effect matches in wire form and **refuses an ambiguous selector**. That binds any future command that authorises a plan row by path. Unsyncable entities go on a persisted, **merged** standing list (`record_unsyncable`), warned once per run. A remote reason drops off only on a full snapshot (an incremental pass does not plan it). A local reason (socket, symlink, FIFO, device) drops off on any pass that ran the local walk. `UnsyncableReason::origin` decides which. A path hidden by the user's own rules is excluded, not unsyncable.
- **Delete-approval guard is execution-time, and holds the cursor when withholding.** Gating (does a delete happen?) and disposal (`trash::LocalDeleteMode`: what a local delete does) are independent. The gate lives in `execute_plan_and_commit` (`decide_delete_gate`), not in the pure planner. It withholds a guarded `RemoteDelete`/`LocalDelete` (never `Purge`) that has no matching approval. A withheld action skips its side effect **and** its index mutation. Any withholding forces the cursor update to `None`; otherwise `reconstruct_remote` would drop the withheld `LocalDelete` once the cursor passed its event. Approvals are consumed in the delete's checkpoint (ADR 0002).
- **A failed item does not fail the pass, and partial failure is its own state.** `execute_plan_and_commit` continues past a failed action (#136): the action's mutations roll back, it goes into `failed_items`, and the rest of the plan runs, so one poisoned file cannot starve everything ordered after it. The pass returns `PassOutcome::Partial`, a **third** outcome that every branch on a pass outcome must enumerate; it must never fall through to "clean" (#246). A partial pass sets `last_error` but not `last_sync`, does not clear `is_first_reconcile` or `force_local_rescan`, **holds the cursor**, and re-queues the failed paths into `pending_changes` (a failed upload has no remote event). It still ends the pass: on shutdown, or after `CONSECUTIVE_FAILURE_LIMIT` failures with zero successes.
- **A plan-only pass observes and consumes NOTHING.** It runs the same scan and walk as a real pass, so anything it consumed would be spent without the side effects that justify spending it. This is structural: the pass does not go through `reconcile_blocking` (`plan_now` → `plan_only_blocking`), and it always full-walks the remote, so it never streams events. It persists and clears nothing (the full list is on `plan_now`). **A plan pass claims `syncing` — it must, or `activity` is gated off every status reply — but bumps no `reconcile_seq`.** Clients tell a plan pass apart by the pass block's `kind`. An apply is re-plan-and-compare, never replay. A divergence returns `Err` and publishes the fresh plan under a new token. A filtered apply skips destructive rows at the executor, never by filtering the plan, because the gate must see the full plan. A pause cancels a booked apply, but a booked plan still runs and seals. That asymmetry is deliberate, so do not make them consistent. Only `watch_syncnow` may bail out on a pause client-side.
- **A pair's pause survives a restart; the in-memory flag stays the authority (#102, decision D12).** The GUI restarts the daemon after every settings save, add and remove, so a pause is recorded in the pair's own index (`pair_pause`). `PairShared::paused` is what the running daemon reads, and `pause_record` doubles as the lock for writing both. A failed write still pauses, and the reply says the pause will not survive a restart (`pause_unsaved`). The record is flushed before the pair's next `Sync` job. A pair adopts its stored pause at boot and on promotion, before its first pass. A failed read starts the pair **not** paused (running is the status quo; a pause nobody asked for would be invisible). **Known gap (#442):** a paused `Unavailable` pair is not retried, so a pause set while it is unavailable reaches its index only on promotion, and a restart before then loses it.
- **A node that vanished mid-pass is skipped, never recorded, and also holds the cursor.** A download whose node is gone returns the typed `NodeNotFound`. The executor skips just that action, with no side effect and no index mutation, and the rest of the pass, including the rest of its batched chunk, proceeds (#31). It means "skip and replan", **not** "confirmed gone": a batch's note names no request, and the error can be transient, so nothing is purged on it. A skipped conflict-sidecar download skips the whole action, record included; a `Conflict` row with no sidecar would have no exit (#46). Any skip holds the cursor. Nothing else (a failed listing, upload or delete) is treated as vanished.
- **History is written behind its side effect, and an idle pass writes nothing.** `PassLog` rows buffer exactly like `index_mutations`: a failed action truncates them, and a checkpoint drains them in the same transaction. So history never describes a side effect that did not land. The `sync_passes` row opens lazily as `interrupted` with duration 0, and every graceful ending seals it, so `interrupted` means a crash and no repair sweep is needed. Only notable passes are recorded (changed something, did not end clean, or was a full sweep), because the 30 s poll runs about 2900 passes a day.
- **A folder that is not there, a lock another process holds and a watch that did not take do not stop the daemon, and a missing folder is not a failed pass** (#102 phase 4b, maintainer decisions M1/M1b; full reasoning and review rounds: ADR 0005, phase 4b notes, items 12–15).
  - **Boot** prepares each pair (folder, state directories, per-root lock, index). Any failure makes it `PairSlot::Unavailable` with a published reason instead of exiting; exiting made systemd restart the daemon every 10 s. The order is: per-root locks, then the global lock (fatal), then the indexes.
  - **A retry** is a `Sync` job on an unavailable, unpaused slot, using `RootMode::MustExist`. It **never creates the folder**: an unplugged drive's mount point must not become an empty tree reconciled against the remote. Only boot creates it.
  - **No code path that a pass or a retry runs can create the root or any ancestor of it.** Executor directories go through `ensure_directory_below`, which works level by level and stops at the root. Download staging directories are made non-recursively. `write_atomically` makes no directory. State directories are made below the folder that was just found. The `create_dir_all` calls that remain are boot-only.
  - **A folder that vanishes or is replaced under a ready pair** is the typed `RootUnavailable`, checked against the directory's identity (`known_root`), not just `is_dir()`. It is checked at the top of the pass (after the apply request is taken, before the latches are consumed), after the scan, before every action, download chunk and upload/move transfer, and before the final commit (`ensure_root_available`). It ends the pass at once rather than counting as an item failure. It holds the cursor and writes no history row or sidecar, but it still sets `last_error` and bumps `reconcile_seq`. A consumed `resync` is latched again. A plan is refused in the same words.
  - **A look that fails with anything other than "not found"** (`EIO`, `ESTALE`, `EACCES`) decides nothing (`Look::Unreadable`): no demotion, no hold, no acceptance. Mid-pass it ends the pass, after committing the index-only work accumulated so far (`keep_accumulated_work`).
  - **Replacement** (`examine_ready_pair` before each `Sync` job; `judge_carried_replacement` before a promotion prepares anything). The pair is **held** (`StandingCause::ReplacedByEmptyFolder[Uncounted]`), with nothing created, opened, locked or downloaded, when all of these are true: the folder is a different directory, or its index or lock is no longer the file at its path; it holds nothing the pair's rules would keep; and the baseline records items or could not be counted (an unreadable count is not zero). Otherwise the pair would delete everything remote, or download everything into an empty mount point: #426, mid-life. A folder emptied **in place** with its state intact is the user's own deletion. A replacement with content is accepted, and its first pass **withholds every deletion whatever the policy** (`force_delete_approval`, persisted until a pass withholds none). A filesystem that names the folder inconsistently gets presence-only checks.
  - **Ways out of a hold:** content appears in the folder, or `proton-sync reset-index --yes` (which bootstraps and plans no deletion). A restart is deliberately **not** offered. **Known gap:** holds are kept in memory only, so a restart while held is #426 again.
  - What a pair published is carried across a demotion. `status_history` is never empty, because gui-core reads empty as `FirstRun` and would show onboarding (M1b).
  - **A watch that did not take** keeps the pair ready. `maintain_root_watch` registers or retries before each pass, and registers again when the root's identity has changed. Any re-registration or failure sets `force_local_rescan`.
- **An index records which Proton folder its baseline describes, and a pair configured with another one does not run** (#453). A baseline compared with a different Proton folder reads every path the new folder lacks as deleted on Proton, and plans `LocalDelete`s. The `remote_root_node` row records the folder under `config::remote_root_comparison_key`; key equality is the only test of "same folder". The folder is written once, in the same transaction as the first commit that leaves a baseline row, and never overwritten (an empty baseline describes no folder). It is checked at one door, `PairRuntime::open_checked` (at boot and on every retry). A different folder makes the pair `Unavailable` (`StandingCause::RemoteRootChanged`) before anything is listed, created or downloaded. A record that cannot be read is not "no record". There are two exits. One is to put `remote_root` back and restart, which is safe here because the record is persistent. The other is `proton-sync reset-index --yes --pair NAME`, which starts over from both sides and deletes nothing. `resync`, a scheduled sweep and another pair's reset do **not** release the hold. The desktop app's Settings starts a pair over offline before changing its Proton folder (`gui/src-tauri/src/commands/start_over.rs`), and decides "another folder" with `same_remote_folder`, the hold's own rule. Residuals (a legacy index takes the configured folder; an older binary can leave the record stale; the key is a path, so a folder renamed in the web app needs a reset, and another account at the same path is outside the guard): ADR 0005:1940.
- **N pairs, one queue: a pass touches only its own pair, every consumed request is sealed, and shutdown cuts at a pair boundary** (#102 phase 4a). A pass reaches its pair's published state only through `PairPass::pair_shared`, built by `pass_for(i)` from the index the queue popped. With an index-0 shortcut, pair B's pass could take A's apply or consume A's reset latch, which is why every shortcut is `#[cfg(test)]`. Every arm of `run_job` that consumes a request seals it, because pollers have no deadline. Shutdown is the cancel flag plus a `Notify`, checked before every pop: a shutdown mid-pass fails only that pass (its checkpoints stay, its cursor does not move). Requests still queued at shutdown are not sealed.

### Testing pattern

`Daemon<C: ProtonClient>` is generic, and tests inject fake clients and event sources (see the `daemon.rs` tests). `daemon.pair()`, `pair_mut()`, `pass()`, `reconcile_blocking()` and `ControlShared::pair()` are `#[cfg(test)]` index-0 shortcuts; `runtime(i)` and `pass_for(i)` address any pair. Multi-pair tests use `Daemon::from_pairs` + `pair_configs(dir, names)` + `MultiRootClient`; single-volume tests use `steady_shared_volume_daemon`. **Drive anything about ordering through `step_blocking` itself** (`Stepper`: real channels, a `RecordingWatcher`, a `FakeClock`), never through a test-only copy of the loop body. Loop-level behaviour runs `Daemon::run` on a multi-thread runtime.

- **A test that builds a daemon from a resolved config must repoint `global_lock_path` first.** The resolved config carries the real per-user lock, which a running daemon on the same machine holds (`docs/agent-notes/resolved-configs-carry-the-real-global-lock.md`).
- **A test starts a binary of this crate only through `tests/common`** (`syncd`/`sync_cli`, `sandboxed`, `run_bounded`, `spawn_logging`, `run_other_tool`, `refuse_the_real_cli`). These helpers sandbox `HOME`, XDG, D-Bus and `PATH` stubs, and refuse a daemon with no fake `proton-drive` or with `events_driven` on. A refusal test that regresses becomes a real daemon; one bound the live socket. `tests/test_isolation.rs` enforces this rule by scanning `tests/`. Real session and events code runs only through `common::ScriptedEvents`.
- `tests/scripts.rs` runs the shell scripts only on temporary files and dry runs, with `systemctl` and `cargo` stubbed. Never run the scripts for real from a test.
- Planner tests are pure and use in-memory maps (`sync.rs`). Put regression tests next to the logic you change, and boundary tests where external paths first enter.

## Conventions

- Errors: `AppResult<T>` = `Result<T, Box<dyn Error + Send + Sync>>`; build ad-hoc errors with `boxed_error(...)`.
- Logging: `tracing` to **stderr** (stdout is reserved for machine-readable dry-run JSON); `RUST_LOG`, default `info`.
- Uploads, downloads and deletes are never auto-retried (to avoid duplicate side effects); only read-only listings retry, per `proton_list_attempts`. Continuing past a failed action (#136) is not a retry: each action is attempted at most once per pass.
