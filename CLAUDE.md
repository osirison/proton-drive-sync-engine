# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Rust prototype for bidirectional file sync between a local folder and Proton Drive. Ships two binaries backed by one library crate (`proton_drive_sync_engine`):

- `proton-syncd` (`src/bin/proton-syncd.rs`) — long-running daemon; also hosts the one-shot `--dry-run` path, which returns before `Daemon::new` and so takes **neither** lock and builds its **own** `ProtonDriveClient`. That is deliberate — taking the user-global lock would fail the preview exactly when a daemon is up, the only case it is useful in — so it *warns* instead (#317): `daemon::probe_daemon_lock` takes a **shared** `flock` on `config.global_lock_path` non-blockingly and drops it in the next statement, which is as close to "check without acquiring" as `flock` (which has no query op) allows. Never waits, never holds, never creates the file, and answers a three-state `GlobalLockProbe` whose `Unknown` is evidence of neither. stderr only: stdout carries the report. **With several `[[pair]]` tables a preview shows ONE pair** (#102 phase 4c): the default (first) pair, or the one `--pair NAME` names — a preview rehearses one tree and the report has no pair dimension. `--pair` is validated **after** resolution (`config::resolve_runtime_configs`, not a clap `requires`: whether the run is a preview depends on `--dry-run`, `--no-dry-run` *and* the file's `dry_run`, and clap cannot read the file), is an error unless the run is a preview, is matched byte-exactly like the wire, and an unknown name is an error that names the configured pairs. Without `--dry-run` the binary hands every resolved pair to `Daemon::new`.
- `proton-sync` (`src/bin/proton-sync.rs`) — thin control CLI that talks to the daemon over a Unix socket.

Unix-only today: control-plane IPC uses Unix domain sockets (`#[cfg(unix)]` guards in `src/ipc.rs`). Edition 2024 toolchain required.

## Architecture

The engine reconciles **three sources of truth** into a plan, then executes it:

1. Local files under `local-root` (`index::scan_local_files_with_options`, SHA-1 hashed)
2. Remote files from `proton-drive filesystem list --json` (`proton::ProtonClient::list`)
3. The last-synced baseline in SQLite (`index::load_index`)

Data flow: **scan → `sync::plan_sync` → execute actions → commit index**. This is the spine; changes to sync behavior almost always start in `src/sync.rs`.

### Module responsibilities

- `src/sync.rs` — **pure** planner. `plan_sync` produces `Vec<PlannedAction>` with no I/O. Bootstrap (empty index) vs ongoing logic are separate; ongoing decisions come from a `(local_delta, remote_delta)` matrix in `plan_ongoing_action`. Also owns conflict-sidecar naming (`ConflictNaming`, default suffix `proton-cloud`, configurable via `conflict_suffix` — **changing it orphans sidecars already on disk**: they stop matching `is_conflict_copy`, so the scanner no longer ignores them and they upload as ordinary files; guard `changing_the_suffix_orphans_sidecars_written_under_the_old_one`. Threaded explicitly from `plan_sync`/`plan_sync_entities` down, and reaching every *detector* too — `ScanOptions`, the daemon watcher, the GUI's disk walk — because one spelling on the writing side and another on the reading side means the engine uploads the sidecar it just wrote) **and each sidecar's source**: `PlannedAction.sidecar_from_local_copy` distinguishes the ordinary conflict (download the remote revision) from `(Changed, Missing)` — a local edit whose remote copy was deleted elsewhere — where the sidecar is a *copy of the local file*, because there is nothing to download and a conflict with no sidecar has no exit and is invisible to the GUI's disk-walking conflicts list (#46). A kind mismatch is likewise two questions, not one: `is_live_kind_clash` (both sides live and disagreeing) is the only real `TypeConflict`, while `only_base_kind_is_stale` means the index row is out of date and the surviving entity is planned as a bootstrap, whose upsert replaces the row's `entity_kind` (#47). `plan_entity_action` is the **single** definition of what a path resolves to, and `compute_directory_deletion_verdicts` proves its subtrees through it: a recursive directory delete may only be proved against the actions that will really be planned. Dispatching that proof on `base.entity_kind` alone narrowed a live entity of the *other* kind away as absent on both sides, scored it a clean `Purge`, and deleted the only copy of it (#282). The proof is one bottom-up fold — each entry planned once, folded into its nearest *tracked* ancestor, since selective-sync gaps mean the immediate parent may have no base row — and is skipped wholesale when no base directory is live on exactly one side, those arms being the only readers of a verdict (#48). A path that is not valid UTF-8 is **unsyncable** (`is_representable_remotely`, #270): the CLI reports the remote tree as JSON, so an upload's copy comes back under a lossy key and forks into a perpetual Upload+Download pair. The gate sits in `plan_entity_action`, the one definition of what a path plans to, so the deletion proof inherits it: such a path plans `SkipUnsupported` and nothing else, which is not a delete, so no ancestor subtree holding one is ever proved clean and the recursive `LocalDelete` that would destroy its only copy is never authorised. A `MoveRemote` onto such a path is dropped in `plan_file_path_transitions`. A directory `MoveLocal` suppresses its **untracked** live descendants there too (#12): the rename happens before the per-path actions, so a bootstrap `Upload` planned for a new file at the old path would first recreate the moved-away parent remotely and then read a file that is no longer there. Nothing can be re-planned at the new path either — the pre-move scan does not hold that key — so the subtree is left to the next pass, which the executor guarantees runs by re-queueing the move destination. The rule is one-sided: remote names are never screened, since a genuine U+FFFD is indistinguishable from a lossy one and an already-forked pair settles by downloading the lossy copy. Every `SkipUnsupported` is built through the one constructor `PlannedAction::skip_unsupported`, so it always says **why**: `UnsyncableReason` is `unrepresentable_path` (the local #270 cause, visible to any pass that scans locally) or `remote_not_downloadable` (a Proton-native Docs/Sheets node, or a #59-degraded one) — plus the five #232 local kinds, which arrive from the scanner rather than the planner and so never appear on a `PlannedAction` at all. Every reason answers `origin` (`Local`/`Remote`/`Unknown`), the one definition of which passes may drop a standing item by absence. Note what does *not* plan a skip: a remote file with no `claimedDigests.sha1` yields `FileDelta::Unknown`, whose arms plan an `AutoLink`/`Conflict`/nothing — a Proton-native document has no digest *because* it is not a byte blob, which is the fact #295's evidence read backwards. `UnsyncableItem` (path + kind + reason + first-seen) is the shared shape #232's local kinds — sockets, symlinks, FIFOs, devices — plug into; the token is hand-serialized so an unknown one parses to `Other` instead of failing an older client's whole reply, which is exactly what let those five be added without a lockstep client upgrade. `entity_kind` is `File` for every local kind: the engine knows two kinds and none of these is a directory it would descend into (a symlink to a folder is not followed either), so the *reason* is what says what it really is. `SyncAction::is_destructive` is the **one** definition of the plan's destructive set (`RemoteDelete`/`LocalDelete`/`Purge`) — `PlanSummary::destructive_actions` counts with it and `apply --skip-destructive` (#192) drops with it, so the number a user is shown and the rows a filtered apply omits are the same set by construction. A different question from `delete_direction`, which is the *approval gate's* set and excludes `Purge` (index-only, destroys nothing). `plan_token` (#100) is a plan's identity: a version-tagged SHA-1 over the rows sorted and length-prefixed, from **raw path bytes** (two paths differing only in invalid UTF-8 are two plans and the wire form collapses them), covering every field that says what will happen — `size_bytes` included, because an upload whose file changed under the review is exactly the divergence the token exists to catch. `DryRunReport.cannot_sync` (#315) carries the walk's own drops — sockets, symlinks, FIFOs, devices — under a name that is deliberately **not** `unsyncable`: that word means the daemon's persistent merged store, and a one-shot report has no store to merge into and no age to carry. Disjoint from the plan's own `SkipUnsupported` rows, so the two can be summed.
- `src/daemon.rs` — the runtime. `run()` binds the control socket, registers every ready root on the watcher (a root that cannot be watched is not fatal: see the "folder that is not there" invariant), seeds the **due queue** (`src/due_queue.rs`; every pair due now, ties in config order) and then loops on **one** step function, `step_blocking` — the same body the tests drive with real channels and a fake clock (#102 phase 4a): drain what is queued **now** on the control and watcher channels, **bounded** so events that keep arriving cannot hold off the pop or a shutdown (a drain that ran until the channel was empty took 4.2 s to reach a set cancel flag at 50k events/s, as measured in review): the control channel's backlog at entry once, the watcher channel in at most `MAX_DRAIN_ROUNDS` (3) rounds each sized by the backlog counted when it begins — one round was not enough, because an echo of the pair's own download that arrived while the backlog ahead of it was routed missed that count, so the pop ran first, the pair's pass cleared `authored_writes`, and the next drain flipped the fresh `Synced` record to `Modified` and uploaded the stale file over a newer remote edit (#49) — with lost-event notices gathered across every round and settled once, and the cancel flag read between events — turning commands into explicit jobs and routing watcher events to the pairs that own them, check the cancel flag, pop one job and run it, all inside one `block_in_place` per wake. Between steps it waits on the shutdown `Notify`, the two channels, or the queue's next deadline (an absolute `sleep_until`, so rebuilding it every turn cannot postpone it). A watcher event received in that wait is **carried** into the next step (`LoopInputs::carried`) and routed there, first, inside the same bounded drain (it is the oldest, so it is the cause the drain reports for lost events; routing order changes nothing else, since `pending_changes` is a set and `mark_modified` is idempotent): the wait routes nothing itself, so `Daemon::route` has exactly one call site and no routing path that a step-driven test does not reach. **Nothing reconciles before the loop**: each pair's first pass is the first job it pops, so the socket answers while later pairs wait and a shutdown cuts boot at a pair boundary. A pair's cadence is `cadence_for` — the fast event poll while its events are live (`events_driven` *and* a session), its own `scan_interval` otherwise (see the cadence invariant below) — re-armed from the moment its pass **ends**, which is what keeps a long pass on one pair from starving another. A signal sets the cancel flag and notifies; the step checks the flag before every pop, so no further pair starts once shutdown is asked for. **The control socket is served on its own task** (`serve_control_socket`, one further task per connection) from a continuously-published `ControlShared` snapshot (+`paused`/`syncing`/`auth` atomics and a `reconcile_seq` pass counter), so status/pause/approve answer instantly even while a reconcile blocks the main task; everything a connection is served from is one `ControlPlane` (snapshot, the second SQLite connection for approval writes — both set a busy timeout — the loop channel, and the `list` verb's `BrowseContext`). `List` is the one verb that runs work there: it `spawn_blocking`s a listing on the daemon's **own** client behind `proton::CliGate`, bounded by `BROWSE_GATE_WAIT` (well inside `IPC_IO_TIMEOUT`) so it answers `busy` instead of parking a control connection behind a transfer. Sign-in state (#103) is recorded by `note_auth_evidence`: a completed pass is evidence of `signed-in` (a bootstrap listed, an incremental fetched the delta, a partial landed at least one action), a pass failing on a typed `AuthFailure` is `signed-out`, and any other failure moves nothing. A sign-out is reported through the **same** one-reason-per-cause message family (one line per cause, said once, re-said on change) rather than a second channel — on the *process* latch (`Daemon::session_declined`, whose typed `SessionDeclineCause` is what lets recovery clear only its own cause), since a session is per-user. `Syncnow` is an immediate ack — the sync runs on the main loop, and clients (e.g. `proton-sync syncnow`) poll status until `reconcile_seq` advances past the ack's value with `syncing == false`. `Shutdown` (IPC) exits through the same path as SIGTERM, including cancelling an in-flight proton-drive command. `reconcile_blocking_inner` dispatches between `bootstrap_reconcile` (full-tree snapshot) and `try_incremental_reconcile` (event-driven, O(changes)); the first pass after boot goes through `first_reconcile`, which **warm-starts** (incremental with a forced local scan) when eligible or bootstraps otherwise (see ADR 0004 and the "First pass after boot" invariant). All funnel side effects + incremental checkpoint commits through `execute_plan_and_commit` (consecutive planned downloads execute as chunked multi-file `download_many` invocations, grouped by destination directory). The event cursor advances **only** in the final commit of a fully-successful pass, and only when `events_driven` is on. `events_driven` is now **on by default** (opt out with `--no-events-driven` / `events_driven = false`, which restores the byte-identical snapshot-only path); when the reused CLI session/keyring is unavailable the daemon degrades to snapshots at runtime anyway — on the `scan_interval` cadence, not the event poll, and it says so once (`note_degraded_session_if_needed` reports through the same one-reason-per-cause family as `resolve_event_scope`'s declines, at the process scope). Holds advisory lockfiles (`LockGuard`) to prevent duplicate instances: each pair's per-root lock is taken **before** the one user-global lock, and a per-root lock held by another process is the one preparation failure that is **fatal at boot**, naming the pair (`LockHeld` is a typed error, so a mid-life retry can tell contention from any other failure and merely keeps that pair unavailable). **Before any of that — before a folder is made, a state directory created or a lock taken — every pair is checked against every other on REAL paths** (`real_path_overlap`, #102 phase 4c): the config reader's nesting rule is lexical and cannot see a symlink or a cwd-relative root, and the consequence is the same one it cites (a pair nested in another has its `.sync` index, lockfile and sidecars uploaded as the outer pair's files, because `is_sync_state_path` ignores only a *top-level* `.sync`). It resolves each root and each state file's directory as far as it exists (`index::canonicalize_best_effort` walks up to the deepest existing ancestor, so a folder that does not exist *yet* under a symlink is still placed), and refuses a root equal to, inside or containing another's, a state file inside another pair's root, and one state file with two owners (which `flock` on the shared inode would only have reported as "daemon already running"). **One function, three callers**: boot, where an overlap is fatal naming both pairs and both the written and the real path; `retry_unavailable`, where the pair stays unavailable with that sentence as its reason — so a folder that was missing at boot is checked when it appears, not never; and `examine_ready_pair` (through `stop_overlapping_pairs`), which puts it to a pair that is **already running** against every other pair, ready or not, before each of its `Sync` jobs. The first two look once, so a layout that changed afterwards (a pair's folder moved into another's with a link left where it was) kept both `Ready` and the outer pair uploaded the inner one's `.sync` — lockfile and status files — as ordinary files (PR #434 review, F2). **Both pairs of the overlap are stopped**, each demoted with its own side's wording (the one a retry produces, so a retry that keeps it unavailable restates nothing), and not only the inner one: the inner `.sync` is already in the outer pair's tree, and the outer pair, correctly configured and still `Ready`, would upload it on its next pass. The check is symmetric in what it finds (a shared folder and a shared state file have no inner side), so no rule about who is at fault is needed; nothing is removed or tidied, and both resume at their next attempt once the layout is put right. All three compare against every other pair, ready or not, so the answer does not depend on which of them could be prepared. A running pair **stops only ready pairs, but asks about unavailable ones too** (second review, H1): an unavailable pair runs nothing, but the running pair *reads* its own tree, and an unavailable pair's folder — `.sync` from when it last ran included — is what it would upload once that folder is inside it, for a pair that is down for an unrelated reason (a held lock, an index that failed to open, a folder restored from a backup) and whose own retry never asks. An unavailable pair's folder counts **only if it exists** (a missing or unmounted neighbour has nothing in the tree, and must not turn one unplugged drive into two stopped pairs), and it is skipped whole when it does not — so a state file of its that lies in the running pair's tree beside a missing folder is not found until the folder is. A scanner-side guard (never upload another pair's `.sync`) was weighed and not built: `is_sync_state_path` is name-based and top-level only by decision (a nested `.sync` is user data, e.g. another sync tool's), and keying it on other pairs' real state directories would put their paths into `ScanOptions`, the daemon watcher and gui-core's disk walk and recompute them whenever the layout changes. When more than one pair is configured the daemon also says once, at startup, that the desktop app, the tray's Pause and the notifications address the default pair only (maintainer decision M4; `note_that_the_desktop_app_addresses_one_pair`). **State is split by scope (#102 phase 2, ADR 0005 §1):** a `PairRuntime` owns everything one folder pair's pass decides from and writes back (its `PairConfig` and index connection, `ScanOptions`, the watcher queues, the first-pass/warm-start floors, the `last_*` summaries, withheld deletions, failed items, the standing unsyncable list, the pass log/history/intent, its per-root lock), while the daemon owns what the *process* shares — the one `Arc<C>` client (hence one `CliGate`, #23), the cancel flag, the `ControlShared` handle, the event-stream **session** and its factory, the three cadence seams, and the global lock. `Daemon::pairs` is a `Vec<PairSlot>` — `Ready(PairRuntime)` or `Unavailable` (maintainer decision M1: a pair whose root cannot be prepared keeps the daemon running, N = 1 included; boot, a retry and `demote_pair` build them — see the "folder that is not there" invariant) — one slot per `[[pair]]` table, in file order, the first being the default pair (#102 phase 4c lifted the old one-pair refusal). The whole reconcile family runs on `PairPass<'a, C>` — a borrowed view of one pair, **its own** `PairShared` (`pair_shared`), plus those shared pieces — so a pass structurally cannot reach another pair. `Daemon::pass_for(i)` is the **one** place an index becomes a pass, and the due queue is what chooses `i`; the index-0 shortcuts (`ControlShared::pair()`, `Daemon::pair()`/`pair_mut()`/`pass()`/`reconcile_blocking()`) are `#[cfg(test)]`, so the compiler finds any production site that forgets which pair it is about. `Daemon::new(Vec<DaemonConfig>)` is the public door to the N-pair constructor `Daemon::from_pairs` (generic over the client, so crate-private; **the one place that checks the pairs agree** — it refuses a set whose daemon-wide halves differ, `config::resolve_runtime_configs` computing them once so a resolved set agrees by construction — and the event session is wanted if *any* pair streams — `any_pair_streams`, evaluated once inside `from_pairs_with_opener` and handed both to the builder of the session the daemon starts with and to the factory that rebuilds it); `DaemonConfig::into_parts` is the one projection of the resolved config onto `ProcessConfig` + `PairConfig`, consuming, so no second copy of `local_root` exists. **The plan verb (#100/#192/#209) is `Syncnow`-shaped, not `List`-shaped**: `plan_now`/`plan_only_blocking` run a plan-only pass on the main loop (a full local walk plus an O(folders) remote walk must never run on the IPC task), which is what makes the existing `SyncActivity` describe the rehearsal and closes #209's progress line with no second channel. It shares one body with the child `--dry-run` — `build_plan_report`, scan → list → plan — so there is one definition of what a rehearsal is and the token cannot depend on who asked. `PassIntent` carries an apply through `reconcile_blocking_inner` to the **one** comparison in `execute_plan_and_commit`, taken before that method mutates anything about the pass; every exit seals the request (`seal_apply_outcome`), because a booked request nothing answers is a client polling for ever. An apply overtaken by a **pause** is cancelled rather than latched (`discard_queued_apply_for_pause`): `resync`/`reset_index` survive a pause because they describe the next pass, but an apply performs deletions under a minutes-old review. A plan pass claims `syncing` — it must, or `activity` is gated off every status reply — while bumping no `reconcile_seq`, so `PairShared.plan_pass` tells the two apart and `a_counted_pass_is_running` is what the `syncnow`/`resync` acks ask: a client told "already in progress" waits for `reconcile_seq + 2`, which a queued sync behind a *rehearsal* can never reach alone. **The control-protocol pair selector (#102 phase 3, ADR 0005 §4).** `ControlShared.pairs: Vec<PairShared>` (one per configured pair, ready or not; `PairShared` gained `name`), resolved by the wire's `ControlRequest.pair` through `ControlShared::resolve_pair_index` — the **one** resolver, byte-exact, used by `handle_control_connection` alone; the daemon core addresses `pairs[i]` by the index the queue popped. Most of the ~30 methods that used to read the singular `self.pair` now live directly on `impl PairShared` (unparametrized — the caller already resolved which pair); only the handful that also read `ControlShared::auth` (`response`, `metrics`, `response_with_sampled_activity`) take `pair: &PairShared` explicitly. `ControlPlane`'s three per-pair values (the approvals connection, the metrics path, the `list` verb's `remote_root`) are `ControlPlanePair`, one per entry of `ControlShared::pairs` in the same order; `BrowseContext` keeps only the process-wide client + gate wait. An **unresolved** selector — `handle_control_connection` refuses before running the verb's body at all — answers `pair: None`, `pairs` still populated, and does nothing: no latch, no schedule, no approval, no reset. `Shutdown` alone ignores the selector (daemon-wide) and always resolves to the default pair. `LoopCommand::SyncNow`/`PlanNow` carry the resolved pair index, which the loop queues as an explicit job for exactly that pair (`DueQueue::request`: ahead of every timer-due pair, in arrival order, a repeat coalescing only while the first is still queued — so a request made during that pair's pass queues one more, which keeps `watch_syncnow`'s `seq + 1`/`seq + 2` exact per pair). An explicit `Sync` popped while that pair's scheduled sweep is overdue pops **as the sweep** (`Cause::Sweep`): `resync` and a due sweep are one full pass (#193), and the daemon re-arms a sweep only for that cause, so it is never folded into an explicit `Plan`, which is inert and consumes nothing. An unresolved selector's reply still flattens `pairs[0]`, only because `response` needs *a* pair; it is stamped `pair: None`. `ControlShared::active_pair` (the unique `PairShared` with `syncing == true` — well-defined because passes are serialized) is what `SharedProgressSink` routes a live callback to; a callback that arrives with no pair syncing is dropped rather than guessed at (unreachable today: `list_one_directory` reports through neither `ProgressSink` method, verified in `proton.rs`). Only the step function starts a pass, which is what keeps `syncing` unique. **Every request a job consumes is sealed, on every arm** (`run_job`'s table): a ready pair runs its pass, or — paused — has its queued apply sealed `Failed`; an unavailable pair's `Sync` first retries its preparation (`retry_unavailable`; unpaused only) and, if that did not take, publishes its reason with a `status_history` that is never empty (M1b: without it gui-core reads "never synced" as `FirstRun` and shows the onboarding wizard to a user whose drive is unplugged), seals a queued apply and bumps `reconcile_seq`; a `Plan` on it is sealed `Failed`. Clients poll with no deadline, so an arm that drops a request hangs one. Every log line a job, a routed event group or a pair's boot preparation emits sits inside a `pair{name=…}` span, so the one-reason-per-cause messages stay attributable with N pairs. The span is built in one place, `pair_span`, as an `error_span!`: a span below the subscriber's level is never created, so an info-level one dropped the pair from every WARN and ERROR line under `RUST_LOG=warn`.
- `src/ancestor.rs` — **pure** (#217/#347): what each side of a conflict did to the **last agreed version**, as one digest per line plus the three counts `added`/`changed`/`removed` — the whole vocabulary the conflict card's first line needs. That line was a pair of **constants appended to every card unconditionally**: a 4 GB video read `You added a line, 5 minutes ago`, with a timestamp that was not its file's, on the one screen where someone is choosing which version to destroy. It cannot be answered from the two live versions — against Proton's current copy alone the very same edit reads as a *removal* — so it needs a third one. **The capture point is not where #217's decision placed it, and this is load-bearing**: `SyncAction::Conflict` downloads the remote revision into the sidecar and *never touches the local file*, then upserts `FileRecord::from_local`, replacing the baseline digest with the current one — so at conflict time the agreed version is on neither side and in no index row. The only moment it exists is the sync that agreed it, which makes capture a **commit-time** fact (`daemon::collect_agreed_summaries`, called from `commit_checkpoint` *and* from the final commit, because adoption is index-only and never reaches a checkpoint) rather than a conflict-lifetime one. `index::agreed_line_summaries` holds **one row per path**, the digest being data rather than key — the first version keyed `(path, agreed_digest)` and claimed that gave "dropped when the conflict resolves" for free, which was false: `INSERT OR REPLACE` only replaces the same key, so every version a file was ever agreed at kept a row, and eviction being global by age let one busy path crowd out every quiet one (exactly the files a conflict card is asked about, since a conflict needs a second machine). Keying on the path makes the supersession real and bounds the table by the tree rather than by its history. It is read back by `newest_agreed_summary`, never by the index row's own digest, which by then is the diverged local file's. Bounded (`MAX_AGREED_SUMMARIES`, whose doc carries measured row sizes rather than a guess), pruned beside the history prune, truncated by `reset_index_state`. **The bytes are re-hashed before they are filed**: an adoption is index-only, so its read happens at the final commit against a scan taken at the start of the pass, and a file edited in between would otherwise be summarised as the edited content under the agreed digest — after which the card would compare that file against a summary of itself and say its lines were unchanged. **Every uncertain path says less**: not UTF-8, over `MAX_SUMMARY_BYTES`, past `MAX_SUMMARY_LINES`, a diff past its cutoff, or one side unreadable — all answer `None`, the card draws one line fewer, and nothing here can fail a pass. Both sides or neither, because one side's verb beside the other's silence reads as "and Proton did nothing". Line splitting follows `ui/diff.js`'s rules exactly (CRLF normalised, the empty element a final newline produces dropped) and **pairing is per contiguous run, exactly as `pairBlocks` does** — pairing globally called a line removed at the top and a different line added at the bottom "one changed line" while the panel beneath found zero changed pairs, so the card contradicted its own disclosure. The LCS is deliberately stated twice rather than shared, since sharing it would mean shipping the agreed version's line *strings* across the wire — the storage the decision rejected — or a second splitter in JS; the two are held to a **shared corpus** asserted on both sides (`AGREEING_CORPUS`), because "they agree" is a property to check rather than a comment to write. The relative time is drawn on **your** side only: nothing preserves a remote mtime, so the sidecar's is when the daemon wrote it, and welding that to a verb would claim someone edited Proton's copy at a moment nothing knows.
- `src/schedule.rs` — **pure** `FullScanSchedule` (#193, G4): the one *user-facing* full-sweep trigger, `weekly <day> HH:MM` / `monthly day <n>, HH:MM` in **one** spelling that round-trips and is what the Settings key line draws. `next_due(after)` answers strictly after the moment asked about (so a sweep cannot re-arm on the instant it ran, and a daemon starting exactly on the boundary does not fire twice), and the monthly rule is `min(day, last day of that month)` — the design's *"Months without a 15th"* is a template with its fixture's day in it, and clamping is the only reading that keeps `monthly` meaning twelve sweeps a year. **Three things can ask for a full sweep and they are not variants of each other**: `events_full_scan_every` counts in-run passes, `warm_start_full_walk_every` counts warm starts across restarts, and this counts wall clock. The first two are self-heal nets with no UI; this is the one a person sets. They do not arbitrate — all three mean "the next pass is a full one", so they compose by setting the same idempotent `force_full_walk` latch `resync` sets, which is what makes the decision's *"does not queue a second, does not suppress one either"* cost no code. The queue keeps that promise for an *explicit* request too: a `resync` popped beside an overdue sweep is handed out as that sweep (`DueQueue::pop` → `Cause::Sweep`), because leaving the sweep overdue would walk the tree a second time. **A missed run is skipped, never caught up**: `next_due` is asked for a time strictly in the future, because a daemon that is up is up at the moment by definition and a restart-heavy one is already swept every `warm_start_full_walk_every` warm starts. Everything is `NaiveDateTime` on purpose — the conversion to an instant is the daemon's single `resolve_local`, so daylight saving is decided in one place: an **ambiguous** local time (clock went back) takes the **earlier** instant and a **nonexistent** one (clock went forward) steps forward a minute at a time to where the gap ends, bounded at 180 — both favouring running the sweep over skipping it, which is the whole point of a safety net. The earlier one is chosen by **comparing the instants**, never by taking a field: `LocalResult::Ambiguous` is documented `(earliest, latest)` and chrono 0.4.45's `Local` returns them the other way round (measured on Europe/Berlin's 2026-10-25 fold), so the first version of this said *earlier* and did *later*, and `.earliest()` would have been wrong too. The resolver is injected rather than being `Local`, so the policy is tested without `set_var` (`unsafe` under edition 2024, and it races any concurrent `getenv` — the same reason `trash.rs` keeps its redirection out of the lib binary).
- `src/due_queue.rs` — **pure** `DueQueue` (#102 phase 4a, ADR 0005 §5): which pair runs next. No tokio, no I/O, no clock reads (every method is handed `now`). `pop` order: the explicit FIFO first (`syncnow`/`resync`/`reset-index`/`keep`/`apply` as `Sync`, `plan` as `Plan`), not gated on time; otherwise the due pair with the earliest deadline (its timer or its #193 sweep, whichever comes first), exact ties broken by a cursor rotating over config order. **No spin by construction**: a timer/sweep pop re-arms provisionally before it returns, `pop` and `next_wake` share one `deadline` rule (so `pop(now) == None` implies `next_wake() > now`), and a zero cadence is refused by assertion. The daemon re-arms every `Sync` job from the moment its pass **ended** (starvation-free between timer-due pairs; a skipped paused or unavailable pair fires no backlog) and never a `Plan` job (inert); cadences are set by the daemon (`cadence_for`), never computed here.
- `src/reconstruct.rs` — **pure** `reconstruct_remote(base ⊕ delta)`: overlays a volume-event delta onto the last-known remote view (the baseline `file_index`) to hand the planner a *complete* remote map without a full walk. Removals (delete / `Updated`+`trashed`) resolve from the baseline; created/updated nodes resolve via an injected `RemoteChangeResolver` (a targeted parent list); anything unresolvable returns `Reconstruction::FallbackToSnapshot` so the daemon re-bootstraps rather than plan against an incomplete map. A **`Created` node that is absent from its parent listing also falls back** — the CLI listing lags the event stream, and dropping it would advance the cursor past a create nothing re-derives (#30); an absent *`Updated`* node is a real move/trash and only drops its stale location. Selective-sync filters apply to the delta.
- `src/proton.rs` — `ProtonClient` trait + `ProtonDriveClient` impl that shells out to the `proton-drive` executable. Parses the tree-shaped remote JSON (nodes may nest under `children`/`entries`/`files`). Extracts SHA-1 from `activeRevision.claimedDigests.sha1` when present. `CommandPolicy` governs per-command timeout and list retry attempts. `download_many` fetches a batch of files in **one** CLI invocation (multiple `path...` args, one shared staging dir, per-file results; the per-invocation timeout scales with batch size, and a failed batch salvages fully-staged files by verifying their claimed SHA-1) — the executor chunks consecutive planned downloads to `download_batch_size` (default 25; `1` restores one-subprocess-per-file). `list_directory` is the non-recursive, single-directory list used for targeted event resolution (the O(1) sibling of the O(folders) BFS); the daemon's `TargetedResolver` memoizes one listing per parent **for the duration of a pass**, so N events in one folder cost one invocation instead of N (#70) — the memo is built and dropped with the pass because resolution reads *current* remote state. **A listing is all-or-nothing.** The CLI wraps `id`/`uid`/`name`/`path` in a `{ok, value}` result, parsed into `WrappedString`'s three states: `Absent` (field missing/null — legitimate, dropped silently as before), `Decoded`, and `Undecodable` (a value that is *present* but carries no usable string). A node whose identity or both locators are `Undecodable` fails the whole listing with a `remote listing is incomplete` error rather than being dropped — a dropped node is indistinguishable from a deleted one and would plan a `LocalDelete` for content that still exists remotely (#59). A degraded node that one locator still places is kept but **inert** (no digest, `downloadable: false` → the planner's `Unsupported` arm). The file-insert branch also rejects the empty relative path, like the directory branch (#72). Per-node error classification lives here too: a download whose CLI stderr says the node is gone returns the typed `NodeNotFound` (`is_node_not_found_error` for callers) instead of a plain message, so the executor can skip that one action — stderr is matched here only, never re-matched by callers. The same rule now carries **auth** (#103): `cli_failure` is the one constructor behind every "the CLI exited non-zero" error, and it types a session-shaped stderr `AuthFailure` (`is_auth_failure_error`), so the daemon's sign-in verdict comes from a downcast rather than from a second needle list in `daemon.rs` or the GUI — two definitions of "signed out" disagree. A `PassFailures` breaker trip inherits it (`abandoned`), because "this is systemic, not per-item" is precisely the expired-session case its own doc names. Concurrency lives here too: **`CliGate` serializes every `proton-drive` child** a client spawns, taken in `run_once` (the single spawn choke point, so a new call site is covered without being told). It is the in-process half of the `paths.rs` user-global lock (#23), needed because the control socket's `list` verb (#99) runs CLI work on the IPC task while the main loop may be mid-pass on the same client — one client is one gate, which is why `Daemon` holds `Arc<C>` and shares that instance rather than building a second. The decision is written at `CliGate`: the gate is held for **one child**, not one pass (so an interactive request lands in the gaps of a 30-minute walk), and the wait is bounded for interactive callers only (`GateWait::AtMost` → typed `CliBusy`, `is_cli_busy_error`) while the daemon's own work waits forever. `browse_directory` is `list_directory` under that bounded wait with one attempt; both share one body (`list_one_directory`), and `list_directory`'s signature and never-fail-the-bootstrap contract are unchanged.
- `src/events.rs` — **remote change detection** via Proton's volume event stream (the O(changes) alternative to the O(folders) `proton.rs` full walk). Pure, transport-agnostic: `parse_volume_events` normalizes the cleartext event delta (`RemoteChange`: created/updated/deleted + `trashed` flag — note a *trash* is `Updated`+`trashed`, not `Deleted`), and `EventsClient<T: HttpTransport, S: SessionProvider>` fetches it, refreshing once on `401`. Detection needs only a session (no decryption); the concrete HTTP transport and session provider (an independent forked session) are injected, so the crate ships no networking dependency. See `docs/adr/0001-*`.
- `src/index.rs` — SQLite schema (`file_index` table + `remote_event_cursor` + `delete_approvals` + `warm_start_state` + `unsyncable_items` + `withheld_deletions` + the history pair `sync_passes`/`sync_events`), local directory scanning, SHA-1 hashing, `ScanOptions` (include/exclude globs + ignore rules + the `ConflictNaming` deciding which files are sidecars — pass the daemon's, not a default, or the scanner and the planner disagree; `should_ignore_path` takes it too), and record CRUD. For event-driven reconcile it also persists the per-scope events cursor (`EventCursor` load/store/clear) and resolves a remote node id back to a local path (`path_for_proton_id`, keyed by the stored `proton_id` = composed `volumeId~nodeId`; bridge an event's raw `LinkID` with `events::node_uid`). `warm_start_state` (single row) persists the across-restart warm-start counter (`load/store_warm_start_count`) that drives `warm_start_full_walk_every`. The `delete_approvals` table stores standing per-item delete approvals keyed by `(path, direction)` and pinned to a `fingerprint`. `withheld_deletions` is its sibling for the *other* half of the lifecycle: the epoch each withheld deletion was **first** held at, keyed and pinned identically, replaced wholesale each gate pass with the previous ages carried forward (a changed fingerprint re-stamps) — `PendingDeletion::detected_epoch_secs` is the age of the *pass*, since the gate stamps `now` on everything it withholds and a pass cannot idle-skip while anything is pending (#225). `purge_subtree_records` is the refusal primitive (#224): it forgets a path and everything under it, component-wise, so the surviving side re-adopts. `unsyncable_items` persists the display-only "cannot be synced" list (byte-exact BLOB key, because the `unrepresentable_path` reason *is* the non-UTF-8 paths a TEXT key mangles — see `normalize_legacy_text_keys`). `scan_local_tree` is the full local stat-walk in its richer form: it returns the entities the walk kept **and** the `UnsyncableEntry`s it dropped (#232), from one walk, so a caller merging the second cannot pair it with a stale first — every other `scan_local_*` entry point is this one with the second half discarded. There is no partial form, which is what lets a caller read a path's absence from that list as evidence. `local_tree_holds_syncable_entry` is its early-exit sibling on the same predicates: it answers only "would the scan keep anything" and stops at the first hit (the daemon's replaced-by-an-empty-folder guard, #102 phase 4b), so an empty folder costs one directory listing. `should_ignore_path` also skips `.proton-sync.toml` at any depth, and — with the rest of the never-synced set — a **FreeDesktop trash directory** inside the root (`.Trash` at a mount top-dir, or `.Trash-$uid` where the suffix is all ASCII digits): a local delete in trash mode relocates the file rather than unlinking it, so without this the next scan finds it again under a new path and uploads it back. The rule is one predicate, `is_never_synced_directory`, read by **both** `should_ignore_relative_path` and `allows_directory_traversal` — the file test alone excludes the entries and still descends into the folder. `reset_index_state` truncates every table the daemon decides from (baseline, cursors, warm-start counter, approvals) in one transaction — it never removes the database *file*, which a running daemon holds open. It also owns **pass and path history** (#213/#229/#238/#230/#190/#191) as *one* schema with six queries over it, not six storage decisions: `sync_passes` is the retained **rollup** (one row per *notable* pass — `started_at`, measured `duration_ms`, `kind` ∈ {`full-sweep`,`warm-start`,`incremental`}, `outcome` ∈ {`clean`,`partial`,`failed`,`interrupted`}, `changed`/`failed` counts, per-direction byte sums) and `sync_events` is the expiring **detail** (one row per side effect that landed: `pass_id`, `path`, nullable `source_path`, `action`, nullable `bytes`). There is no `direction` column — direction is `SyncAction::transfer_direction`, a property of the action. `last_transfer` is the point query over that detail (#233): the newest event row for a path whose action has a `SyncAction::transfer_direction`, scanned newest-first and stopped at the first hit. It is the **only** remote-side timestamp the engine has — `file_index` holds none, because `proton.rs` parses `activeRevision` for `claimedDigests.sha1` and nothing else, so a new column would be a second copy of a table that already answers it. `None` means the engine has no record of moving that path's bytes: nothing ever transferred, it aged out of retention, it was adopted (`AutoLink` moves no bytes), or it has moved since. A **byte total always comes from the rollup** (`byte_totals_since`), never by summing event rows, so it outlives the detail and there is exactly one way to get the number — and it is a different question from `PlanSummary::upload_bytes`, which is what a plan *intends* to move rather than what landed; `sync_events.bytes` is per-row display data, and a *path-filtered* `file_events` therefore returns `totals: None` rather than a window-wide figure that reads as one file's. Retention (`HistoryRetention`, applied by `prune_history` only on a pass that wrote rows) bounds each table by age **and** rows — passes 2000/1yr, events 20k/90d — and **exempts the newest full sweep from both pass bounds**, because every non-clean pass is notable and a chronically failing daemon would otherwise evict it within hours (written `id IS NOT (SELECT MAX(id) …)`, not `<>`: a NULL subquery would void the whole predicate).
- `src/session.rs` — concrete impls of the `events` seams for the **current CLI-session-reuse** approach: `CliKeyringSession` (a `SessionProvider` that reuses the logged-in `proton-drive` CLI's session from the OS keyring via `secret-tool`; `refresh` re-reads the keyring rather than owning a token refresh) and `CurlHttpTransport` (a dependency-free `HttpTransport` shelling `curl`). Independent (browser-forked) auth is deferred by decision — see `docs/adr/0001-*`.
- `src/config.rs` — layered config resolution. Precedence: **explicit CLI flag > TOML file value > XDG default**. `resolve_runtime_config` merges `DaemonConfigInput` (from clap) with `FileConfig` (from `--config`), validates roots/globs, and resolves `dry_run` (`--no-dry-run` beats `--dry-run` beats file `dry_run`). Every local-filesystem path option expands a leading `~` to `$HOME` (`expand_tilde`; `~user` is rejected) — the daemon runs shell-less, and a literal `~` root diverges from the `proton-drive` CLI, which does expand it. Also resolves the daemon-wide **delete-approval** defaults (`[delete_approval] remote/local`, both default `true`; `--no-delete-approval` forces both off) that seed `src/dirconfig.rs` — plus `deletion_policy`, the *same* guard as one named setting (`ask_every_time` / `only_permanent` / `never` / `only_recoverable`, #194) — and `local_delete_mode` (`trash` default / `permanent`, kebab spelling aliased), which is a **different question from either**: `deletion_policy` decides whether a deletion waits for approval, `local_delete_mode` decides what a local one *does* when it goes ahead. `KeyScope::Pair`, because it describes a tree. **The two spellings are mutually exclusive**: a file setting both is a startup error naming both keys, because one setting written two ways has no defensible precedence — and that rule is what lets a round-trip writer know which key it may rewrite (an existing `[delete_approval]` file keeps working and is never rewritten into the new spelling). Owns three further keys the Settings screen's Advanced tab needs (#237): `log_level` (`--log-level` > `RUST_LOG` > file > `info` — a **configured** value is validated and fatal while an unusable `RUST_LOG` falls through, because `EnvFilter` reads a bare `inf0` as the target directive `inf0=trace` and silences the daemon while looking accepted), `conflict_suffix`, and `socket_path` (which was always a key — #237's premise that it was not is stale). `full_scan_schedule` (#193) is per-pair, **file-only with no CLI flag** (a schedule is not a thing to pass on a one-shot command line, and `--full-walk` already answers the only question a flag would ask), and **unset means no scheduled sweep** — which is what every config written before the key says and must keep saying. A value that does not parse is **fatal at startup**, the `log_level` rule for a sharper reason: a schedule the daemon cannot read is a full sweep that silently never runs, and an unrun safety net is the one thing nobody notices is missing. `validate_file_config_text` is the **one** place the post-parse rules live (relative `socket_path` after `~` expansion, `log_level`, `conflict_suffix`, `full_scan_schedule`, both-spellings, positive integers, globs, and **every local-filesystem path a file can set** — `local_root`/`db_path`/`lockfile_path` per pair plus `socket_path` and `proton_cli`, since `ConfigDoc::save` validates through here alone while every packaged unit launches the daemon flagless, so a path only the daemon expands is a config the GUI can write and the daemon cannot start on); `gui-core`'s config writer calls it rather than re-deriving them, and the **warm-start** config (`WarmStartConfig`: `warm_start`/`--no-warm-start` default on, `warm_start_full_walk_every` default 30, `warm_start_max_cursor_age_secs` default 7 days — both `0` = disabled sentinels — plus the one-shot `--full-walk`). See ADR 0004. **Folder pairs (#102 phase 1, ADR 0005).** A config file's per-pair half may be written two ways: `[[pair]]` tables, each with a required `name`, or — for a file with **no** `[[pair]]` — the top-level keys, which are then *one implicit pair called `default`* (`DEFAULT_PAIR_NAME`). That implicit reading is **permanent, not a migration step**: every config written before multi-pair resolves byte-identically, unrewritten, and no user action is asked for. Both spellings at once is a startup error naming the offending keys — the same rule as `deletion_policy` + `[delete_approval]`, for the same reason. Which keys are which is not a table in a doc but a value the code reads: `ConfigKey::scope` is an **exhaustive match with no `_` arm** returning `KeyScope::{Daemon,Pair}`, so a new variant cannot be added without answering the question, and `every_file_config_key_is_classified_exactly_once` compares `ConfigKey::ALL` against the keys a `FileConfig` serializes to — both directions, because either gap is silent. The two halves of that guarantee are **not** the same failure and saying "a new field is a build failure" overstates it (#339): the exhaustive struct literal in the fixture makes the *compiler* demand that a new field be mentioned, and the test is what refuses one that has no variant. That second half was blind until #339 — the key set was read through `toml::Value`, TOML has no null, and a field left `None` was therefore omitted from **both** sides of the comparison, so `None` (the natural value for a fresh `Option`) satisfied the compiler and vanished from the test. It reads the key set through JSON now, and `the_key_set_a_classification_guard_reads_keeps_a_field_left_unset` pins the property directly: an all-`None` struct must have the same keys as a fully populated one. **Narrowed, not closed** — `#[serde(default, skip_serializing_if = "Option::is_none")]` on a new field reopens it byte-for-byte (measured: 84/0 green with the same poison). Nobody has a reason to write that on a `cfg(test)`-only `Serialize`, which was equally true of `None` before #339 — so what the guard proves is that a field is invisible *only* when someone silences it deliberately, not when they leave it at its natural value. Rule 1 *reads* that classification (`FileConfig::key_present`, also exhaustive), which is what keeps it load-bearing rather than decorative. `socket_path` and `log_level` are daemon-wide by nature; `proton_cli`/`proton_timeout_secs`/`proton_list_attempts` are daemon-wide **by force** — they construct the one shared `ProtonDriveClient`, and one client is one `CliGate` (#23), so N clients would be N gates (guard `the_shared_proton_client_keys_cannot_be_per_pair`); everything else describes a tree and is per-pair. `resolve_pairs` is the one definition of the pair shape, called by the daemon *and* by `validate_file_config_text`, and it carries the rules about the pair **set** — the ones no flag can change the answer to, since a flag cannot say *which* pair it amends: both-spellings, an explicit `pair = []` refused rather than read as the default pair, `name`, and collisions **between two pairs**. Both spellings go through all of it; the implicit-pair arm used to return before the name and root rules, which is exactly how #339's divergence existed. `name` is required, `[A-Za-z0-9._-]{1,64}` and unique **case-insensitively** (#298's rule one layer up; `pair_name_key` is the one fold, and `Daemon::from_pairs` compares through it too, so the runtime never accepts a pair set the file reader refuses) — plus the two refusals the charset cannot express, without which its own justification ("never looks like a path", "always a safe command argument") was a claim the code did not honour: `.` and `..` are path components spelled inside the charset, and a leading `-` is option syntax (`proton-sync --pair -h`). `default` is reserved for the **first** table, which is the pair an omitted selector addresses — the `all` decision (ADR 0005 §4, the #140 lesson) applied to the other sentinel — rather than refused outright, since the first pair may legitimately be called that and §7's promote-to-`[[pair]]` rewrite would write it. Root collisions have a concrete cause, not a principle: `index::is_sync_state_path` matches only the *first* path component, so a pair inside another pair's root would have its `.sync` index, lockfile and sidecars uploaded as the outer pair's ordinary files — and that same consequence was reachable **around** the rule, which was written root-vs-root, so a pair's `db_path`/`lockfile_path` may not be another pair's nor sit inside another pair's `local_root` (#339). Comparison is **lexical** (a file must be checkable without touching the filesystem) and, crucially, **cannot fail**: `~` is expanded best-effort (`expand_tilde_for_comparison`, the `gui-core::expand_config_path` shape) so `~/Sync` and `/home/me/Sync` are not read as two roots, while a value it cannot expand is compared verbatim rather than refused — a structural rule may never refuse a value a flag replaces. **Lexical is not the same as unresolved** (#365): `local_comparison_key` collapses `.` *and* `..` against the component each undoes, because every rule built on it asks whether two paths are the same file or one contains the other, and `state/../state/index.db` is `state/index.db` on any POSIX filesystem — comparing the written spellings gave one inode two keys and let a config walk through `require_distinct_state_paths` into exactly the state it refuses (the index holding a whole-file advisory lock), while the cross-pair variant fell through to the generic pair-count refusal that masked it until phase 4c lifted the cap. Collapsing is a property of the **key only**, never of the path the daemon opens. The `..` half is `lib.rs`'s `lexically_normalized` — **one** definition shared with `index`'s `canonicalize_best_effort`, which needed the identical primitive for the identical reason (a path that does not exist yet cannot be canonicalized) and had already drifted from this one on the `Prefix` arm while both were private. The arms that *keep* a `..` carry as much of the rule as the one that cancels it: a leading `..` cancels nothing so it survives (dropping it would make `../a` equal `a`), and `/..` is `/` since a root has no parent. A path that addresses the **current directory** (`.`, `./`, `a/..`) keys as `.` — not as the empty path the primitive returns, which is a prefix of every path there is, and not as its own literal, which gave `./a/..` and `a/..` two keys for one directory and re-opened the very masking the change closes. **The residual cuts both ways and the code says so** rather than claiming a safe direction it does not have: lexical is not symlink-aware, so it both misses two paths reaching one inode through a symlink *and* wrongly matches `current/../index.db` against `index.db` when `current` is a symlink, since the kernel resolves that `..` against the link's target. The trade is deliberate — the missed refusal it closes is silent and ends in a daemon locking its own database, while the false match is loud, arrives before anything runs, and is undone by spelling the path without the `..` — and `a_dotdot_through_a_symlink_is_refused_lexically_and_the_message_says_what_it_compared` pins it so it is a recorded choice rather than a rediscovery. Closing it needs `canonicalize`, which touches the filesystem and errors on a path that does not exist yet. `remote_root_comparison_key` deliberately does **not** collapse `..`, and the reason is not the arithmetic (lexically `/Drive/a/../b` *is* `/Drive/b`, which its own doc used to get wrong) but that `proton::clean_remote_root_path` answers `None` for any remote path carrying a `..`, so no such root reaches the daemon at all. Remote roots compare with the leading `/` stripped since `/Drive/X` and `Drive/X` name one location, and a refusal about two paths *overlapping* quotes what the file **wrote** rather than the comparison key it was reduced to. The two refusals about paths being the **same file** still quote the resolved path, correctly — they read "both resolve to X", and X is the thing they are about. Value-level per-pair rules run per pair in `validate_pair_file_values` — deliberately *not* in `resolve_pairs`, since a flag can still mask each of them (`--local-root /x` over a file's `local_root = ""` starts today), and the merged value is caught where it always was, in `validate_runtime_config`. Three rules live in that flag-maskable half rather than the structural one: an empty root, a `~` the daemon cannot expand, and **one file named as both a pair's index and its lockfile** (`require_distinct_state_paths`, on the file's own values for a reader with no flags and on the merged values for the daemon — the `[[pair]]` spelling had it in the structural layer, where `--db-path`/`--lockfile-path` could not rescue it and where the top-level spelling never got it at all). **Any number of pairs is accepted** (#102 phase 4c deleted `refuse_unsupported_pair_count`, which both readers had called so that `ConfigDoc::save` never wrote a config the daemon would refuse to start on — the two still agree, because both now run the same `resolve_pairs`). **`resolve_runtime_configs(input) -> RuntimeConfigs { pairs: Vec<DaemonConfig>, mode: RunMode }` is the one resolver** (`RunMode::{Daemon, Preview { pair }}`); `resolve_runtime_config` is that plus a check that exactly one pair came out, kept for the 70-odd test sites and the example-config check. The order is the design: the pair shape (every rule about the pair *set*), then the flag rule, then the mode, then `merge_pair` per table (the daemon-wide half — socket, global lock, `proton_cli`, timeout, attempts, log filter — is `ProcessValues`, computed **once** and copied, so a resolved set agrees by construction), then each pair's `validate_runtime_config`, then the preview selector. **Config errors are all-or-nothing** (one table that cannot resolve stops the daemon before anything is locked; beside several pairs the message names the pair, beside one it is byte-identical to before); only an *environment* failure is per pair, and that is the runtime's (phase 4b). **Flags keep meaning "the single pair" — and beside several pairs every per-pair flag is refused at startup, naming it** (maintainer decision M2; `DaemonConfigInput::per_pair_flags_set` is an *exhaustive destructure with no `..`* sorting every field into daemon-wide / mode / per-pair, so a new flag cannot compile unclassified). That includes the opt-outs (`--no-delete-approval`, `--no-events-driven`, `--no-warm-start`): a flag cannot say *which* pair it amends, and one that quietly kept a safeguard on for one pair and off for another is the worst reading. Daemon-wide flags (`--config`, `--socket-path`, `--proton-cli`, `--proton-timeout-secs`, `--proton-list-attempts`, `--log-level`) and the mode flags (`--dry-run`, `--no-dry-run`, `--full-walk` — every pair's first pass —, `--pair`) still apply. **Two new file rules beside several pairs**, both in the shared readers: every table sets `local_root` and `remote_root` (`require_roots_in_every_table`, structural and in `resolve_pairs`, because no flag can supply one and `validate_pair_roots` compares only the roots it is given, so a pair without one would have silently skipped every cross-pair rule), and `dry_run = true` inside a table is refused (`refuse_dry_run_in_a_pair_table`, maintainer decision M3: a preview rehearses one pair and exits, so a per-pair key cannot pick the process's mode) — by `validate_file_config_text` outright, and at startup unless `--dry-run` or `--no-dry-run` says what the run is. `dry_run = false` is the default spelled out and is accepted. **`--pair NAME` is validated after resolution** (`RunMode::Preview` only; byte-exact; an unknown name names the configured pairs). `resolve_control_socket_path` is the **client** half of the same precedence (`--socket-path` > file `socket_path` > XDG default, sharing `require_absolute_socket_path`), so `proton-sync --config` finds a file-configured socket instead of every invocation repeating `--socket-path` (#63). `DaemonConfig` gained `name` (#102 phase 3): the resolved pair's own name, `config::DEFAULT_PAIR_NAME` for the implicit single-pair file or the `[[pair]]` table's `name`, carried onto `daemon::PairConfig` by `into_parts` — the value a control-protocol wire selector is matched against, byte-exactly, nowhere re-derived.
- `src/dirconfig.rs` — **hierarchical, per-directory config** (the `.gitignore`-style layer). A `.proton-sync.toml` in any directory applies to it and everything beneath it; `DirectoryConfigResolver::resolve` walks the entity's ancestor directories root-first over the daemon-wide default (nearest wins; unset options inherit). Machine-local: ignored by scan/plan/watch (`index::should_ignore_path`) and never synced. A file may use either delete-approval spelling (`[delete_approval]` or `deletion_policy`) but **not both** — as in the daemon config, except that a directory file cannot stop the daemon, so an ambiguous one takes the malformed path. Malformed/unreadable/ambiguous files fail safe (guard stays on). All-`Option` `DirectorySettings` → resolved `EffectiveSettings`; extend by adding an `Option` field + resolved counterpart. See `docs/adr/0002-*`.
- `src/trash.rs` — the **one** disposal seam for a local deletion. `LocalDeleteMode` (`Trash` default / `Permanent`) and `dispose(mode, path, kind)`, which is the only place either outcome is spelled: `Permanent` is the pre-change `remove_file`/`remove_dir_all`, `Trash` hands the path to the `trash` crate, which implements the FreeDesktop spec (relocate under `$XDG_DATA_HOME/Trash`, write the `.trashinfo` record a file manager's Restore reads). The `chrono` feature is taken back after `default-features = false` **because without it no `DeletionDate` is written** and the entry lands with nothing to age or sort by. A missing path is an error in both modes, not a no-op — the caller's `exists()` check owns that decision, and `tests/trash_disposal.rs` pins which side it is on. **Tests never touch the developer's real trash**, by two mechanisms because one binary cannot serve both: lib tests go through the thread-local `test_hook` (and an un-hooked `Trash` disposal *panics* rather than escaping), while `tests/trash_disposal.rs` proves the real crate in its own process, where a single `OnceLock`-ordered `set_var` of `XDG_DATA_HOME` is sound. Redirecting it in the lib binary is not: `std::env::set_var` is `unsafe` under edition 2024 and races *any* concurrent `getenv`.
- `src/ipc.rs` — JSON-line request/response protocol over the Unix socket; binds with mode `0600` **inside a freshly created 0700 staging directory and renames the socket into place**, because `bind` creates it `0777 & ~umask` and a chmod afterwards leaves a window in which any local user can issue a command (#62; a process-wide `umask` flip would race the runtime's other threads). The staged path is longer than the published one, so `bind_listener` measures it against the platform's own `sockaddr_un` and refuses a socket that fits only unstaged, naming staging as the cause; cleanup is `remove_dir`, never `remove_dir_all`, so it can only ever remove the empty directory it created. Every wire `PathBuf` serializes through `lossy_path` (`wire_path` = `to_string_lossy`, verbatim back): `impl Serialize for Path` *errors* on a non-UTF-8 path, so one withheld deletion for such a file used to fail **every** reply — status/pause/approve alike — and lock the control plane out (#61). `approve`/`deny` selectors are therefore matched in the wire form too (as `Path`s, so a trailing slash still matches), and a selector matching more than one pending deletion approves nothing. Every reply that renders a *selector* back is bounded by `SELECTOR_DISPLAY_LIMIT` through the one `daemon::truncate_for_display` body that also backs `truncate_error` (#313) — a request may carry 64 KiB and nothing narrower bounds `argument`. **Display only**: the matching above still compares the full wire form, since truncating before it would make two different paths compare equal. `ControlResponse` carries `syncing` + `reconcile_seq` + `activity` + `failed_items`/`failed_item_count` (all `#[serde(default)]` for wire compat); `ControlCommand::Shutdown` asks the daemon to exit gracefully (used by the GUI's restart-daemon flow and `proton-sync stop`); `ControlCommand::Resync` (`proton-sync resync`) latches a full-tree walk for the next pass (self-heal drift; overrides the warm start); `ControlCommand::ResetIndex` (wire `"reset_index"`, `proton-sync reset-index --yes`) latches a discard of everything the daemon has learned — the main loop truncates *before* it loads the baseline, then rebuilds by bootstrap adoption, and the latch is **re-set if the truncation fails** so a confirmed request is never lost. The `--yes` gate is client-side because the wire carries no confirmation field. `ControlCommand::Keep` (`proton-sync keep`) **refuses** a withheld deletion — distinct from `Deny`, which only revokes an approval: it purges the deletion's baseline record *and its subtree* (a directory delete is planned recursively), so the bootstrap arm adopts the survivor back onto the other side, and it latches `force_full_walk` because an incremental pass's remote map IS the baseline (`reconstruct_remote(base ⊕ delta)`) — a purged `direction: remote` survivor would otherwise never be downloaded. `ControlRequest::direction` is read only by `Approve`, and only when nothing pending matches the selector: the pre-pass approval the Plan screen's typed-`DELETE` gate needs (#227), pinned to a fingerprint derived from the index and refused for a path with no record. `ControlCommand::Activity` (`proton-sync activity [PATH]`) is the per-file history query (#230/#190) over `index::file_events`; the pass-level history + today's byte totals (#229/#238/#191) instead ride on every `Status` reply as `ControlResponse.history` (`PassHistory`), refreshed once per pass into `ControlShared`'s snapshot so a 2s GUI poll never touches SQLite. `StatusHistoryEntry` deliberately gained none of it: it records **every** attempt, idle ones included, at a 20-entry cap — about ten minutes of wall clock at the events-poll cadence — so it can answer neither "the last 20 passes" nor "the last full sweep, 2 days ago". `SyncActivity` is the live "what is the daemon doing right now" surface, and it is **one record answering three questions** (#211/#243/#98) rather than three fields that would drift: phase + current path + action i/N, the **transfer queue** (`transfers`, a bounded window — every row in flight, then the next planned ones as `queued`, capped at `TRANSFERS_REPORTED`; `transfers_remaining` is the untruncated figure `+n more` is sized from, and it is the field that tells "not executing / older daemon" (`None`) from "nothing left" (`Some(0)`) — an empty list alone means neither, and the window is republished on *every* action so a delete between two uploads cannot blank it), and the `pass` block, which is the **pass** as a unit and survives every phase change unlike `since_epoch_secs`, which `begin_activity` resets per phase (#213). The singular `transfer` survives only as a **derived** mirror of the first active row, written by `derive_legacy_transfer` at publish time and by nothing else. The pass block carries the per-direction progress — `uploaded_files`/`downloaded_files` (#243's counts) and `uploaded_bytes`/`downloaded_bytes` (#98's bytes, named to match `index::ByteTotals`) — because a counter on `SyncActivity` itself would reset once per action; all four fold in `PassLog::note_committed`, the fold that already builds the history rollup, off the same `(direction, Some(bytes))` arms as the byte sums, so a count and a byte total can never describe different side effects. **A per-file percentage stays unreachable by construction** and says so at `TransferActivity`: an upload has `bytes_total` and no progress, a download has progress and no total, and `totalStorageSize` is not a file size (0 on 873 of 5424 healthy files): the daemon core updates it from inside the blocking reconcile (phases, per-action), the concrete client feeds it via `proton::ProgressSink` (per-folder walk progress, download staging dir), and `ControlShared` samples a download's bytes-so-far from the staging directory at status-reply time. Display-only — nothing in it participates in sync decisions. `ControlResponse.unsyncable` is the same kind of display-only surface for entities that cannot be synced at all (#295), rendered by `proton-sync status` under `can't sync`. `ControlCommand::List` (`proton-sync list [PATH]`, #99) is the read-only remote browser: one non-recursive listing of `argument`, **the only verb that runs work on the IPC task** (see `proton::CliGate`) and the only one whose selector may legitimately be empty — the root is a value there, so it takes plain `validate_relative_path`, not the non-empty form a side effect demands. The selector has **two frames** (#323): relative to `remote_root` by default, or an **absolute** Proton Drive location when it starts with `/`, validated by `validate_absolute_remote_path` — the third rung of the path-safety ladder, for a question about a folder that is outside every root *by definition* (pricing a candidate before a pair is configured, `gui_core::folder_probe`). Absolute selectors were previously refused by the relative guard, so it is a pure extension, and **the reply answers in the frame the request used** (relative entries stay `remote_root`-relative, absolute ones come back absolute), which is what lets a client feed any entry straight back as its next selector. A **subtree is therefore walked by the client, one request per directory, and that is the design**: this verb may sit on the IPC task only because it is one CLI child under a bounded gate wait, while the other daemon-side shape (`Plan`'s ack-plus-latch on the main loop) queues behind a pass that can run half an hour — and one child per request lands in the *gaps* of a live pass, the gate being held for one child rather than one pass. It has no reserved word (`literal_path` is meaningless; a folder named `all` lists), and it answers a typed `ListingOutcome` — `Listed`/`Busy`/`Failed`, internally tagged with `#[serde(other)] Unknown` — rather than prose, because a client telling "retry" from "gone" by matching a sentence is the bug #103 removes. Entries are capped by the daemon (`LIST_ENTRIES_*`), remote ground truth only (no selective-sync filter, no index read), and the CLI's own wrapper node for the requested directory is dropped. `ControlResponse.auth` is #103's answer: an `AuthState` (`unknown`/`signed-in`/`signed-out`, hand-serialized so an unknown token degrades) living in its own `ControlShared` atomic rather than the core-published snapshot, because it has **two** writers — the pass outcome and the `list` verb, which is where an expired session surfaces first. Only success moves it to `signed-in` and only a *classified* failure to `signed-out`; an unclassified failure moves it nowhere, since a fall-through arm reading "signed in and fine" is #246's shape. The **plan family** is three verbs (#100/#192/#209/#317): `ControlCommand::Plan` (`proton-sync plan`) schedules a plan-only pass and acks immediately — `Syncnow`-shaped, with `syncnow`'s pause semantics — `ControlCommand::PlanResult` (wire `"plan_result"`) reads the answer *and the last apply's verdict* straight from the published slot like `status`, and `ControlCommand::Apply` (`proton-sync apply <TOKEN>`) executes a reviewed plan. Both answer typed outcomes on the `ListingOutcome` pattern — `PlanOutcome` (`scheduled`/`computing`/`computed`/`failed`/`paused`/`absent`) and `ApplyOutcome` (`scheduled`/`stale`/`paused`/`applied`/`diverged`/`failed`), each `#[serde(other)]`-terminated. **`plan_seq`/`apply_seq` are their own counters and a plan pass deliberately does not bump `reconcile_seq`**: bumping it would satisfy a concurrent `syncnow` watcher's target and make it report a sync that never ran. `ReviewedPlan`'s `actions` are a bounded window (`PLAN_ACTIONS_*`) built **destructive-first**, so a deletion can never be truncated out of a reply a user decides from — safe only because an apply names the *token*, never the rows. `ControlRequest::skip_destructive` is #192's filtered apply, read by `Apply` alone, and it **overrides a standing approval**: the user asked for this run without them, which is a different question from whether the deletion may ever apply. `PLAN_PASS_KIND` (`"plan"`) is the open `PassProgress::kind` token a plan pass publishes so a screen can tell its own rehearsal's `files_scanned` from a sync's. The `proton-sync` CLI prints human-readable, git-style output by default — `--json` restores the raw response for scripts and tests; `list`, `plan` and `apply` also exit non-zero when the answer is not a success, so `busy` is never read as an empty folder and a divergence is never read as an apply. **The pair selector (#102 phase 3, ADR 0005 §4).** `ControlRequest` gains one field, `pair: Option<String>` (`#[serde(default)]`) — `None` (an omitted selector, what every pre-multi-pair client sends) means the default pair. `ControlResponse` gains `pair: Option<String>` (`Some(name)` **exactly when the selector resolved**, `None` on an unknown one — a client tells by this shape, never by matching `message`) and `pairs: Vec<PairSummary>` (`#[serde(default)]`, but **never empty on a real reply**, `N == 1` included — a one-pair daemon that suppressed it would be indistinguishable from one that predates the feature, which is what a client's capability gate reads). Both are additive: the nine fields three legacy-JSON tests pin (`a_status_reply_carries_no_plan_and_an_older_daemons_reply_still_parses` and its siblings) are untouched, and `pair`/`pairs` are stamped by `handle_control_connection` on every reply rather than by `ControlShared::response`, which does not have every pair's data to hand. `PairSummary` carries `name` + the three roots/paths + `paused`/`syncing`/`reconcile_seq`/`last_sync_epoch_secs`/`last_error`/pending counts — enough for a header, a selector and a tray tooltip with no second round trip. `reconcile_seq`/`plan_seq`/`apply_seq` were already per-`PairShared` from phase 2's split; phase 3 only gave the wire a way to address more than index 0. `Shutdown` ignores the selector (daemon-wide); every other verb refuses an unresolved one before doing anything, per the verb table in ADR 0005 §4.
- `src/paths.rs` — default state paths. The SQLite index (plus its status/metrics sidecars) and the per-root instance lockfile default to the per-root `<local_root>/.sync` state directory, which the engine ignores everywhere (`index::should_ignore_path` → `is_sync_state_path`; only a *top-level* `.sync` is treated as state). The control socket stays in `$XDG_RUNTIME_DIR` — the XDG home for sockets — since it is a session-scoped runtime endpoint (not persistent state), must stay short for the `sun_path` limit, and must be locatable by the control CLI without knowing the sync root. **Two-tier locking:** the per-root lockfile stops two daemons on the *same* root, while a **user-global** single-instance lock (`default_global_lock_path`, keyed on `$XDG_STATE_HOME`, *not* the per-session runtime dir) stops a second daemon anywhere for this user — required because every daemon shells the same `proton-drive` CLI, whose shared SQLite cache/session store is not concurrency-safe (`SQLITE_BUSY`; #23). That is the *across-daemons* half; the in-process half is `proton::CliGate`, needed once the control socket started running CLI work of its own (#99). Both locks use `daemon.rs`'s `LockGuard`, which **never unlinks** the lockfile: `flock` binds to the inode, so removing the path on drop would let a later start lock a *fresh* inode independently of a daemon still holding the old one (#13). Drop releases the flock and leaves an empty file; `acquire` reuses it, so a leftover lockfile never blocks a restart and never means a daemon is running. At boot a per-root lock another process holds refuses the start (naming the pair); a retry for a pair that was unavailable treats the same contention as "still unavailable". An XDG value is honoured **only when it is absolute** (`absolute_dir`, #286; `is_absolute` subsumes the old emptiness check and catches an unexpanded `~`) — a relative one resolves per-process against cwd, which makes the user-global lock one lock per launch directory instead of one per user, and splits the socket between daemon and client. The GUI keeps its own `absolute_dir` for the config path it owns, but no longer computes the socket path at all — `gui-core` delegates to `default_socket_path` here (#277), so this rule reaches the socket once instead of twice. When `XDG_RUNTIME_DIR` (socket) or `XDG_STATE_HOME`/`HOME` (global lock) are unset or non-absolute, both fall back to a uid-suffixed subdirectory of the shared temp dir, and that fallback **fails closed** (#74): `default_socket_path` and `default_global_lock_path` return `AppResult<PathBuf>` and refuse a path that is not a real directory owned by the current euid at mode 0700, rather than binding the control socket in attacker-plantable space. A caller-supplied `--socket-path` skips that resolution entirely (the defaults stay lazy).
- `src/lib.rs` — `AppResult<T>` alias, `boxed_error`, `lexically_normalized` (the **one** definition of what a path addresses when it cannot be canonicalized — `.` dropped, `..` collapsed against the component it undoes, a leading `..` and `/..` preserved as themselves; shared by `config::local_comparison_key` and `index::canonicalize_best_effort`, which both exist to answer for paths that do not exist yet, and which had drifted apart while each held a private copy), `wire_path` + the `lossy_path` serde module (the **one** definition of how a `PathBuf` crosses any wire this engine publishes — the control protocol #61 and the dry-run report #300 — lossy out, verbatim back, byte-identical for a UTF-8 path; `ipc::wire_path` is a re-export), and `validate_relative_path` (the shared path-safety guard) plus `validate_relative_path_non_empty`. The plain form maps `""`/`.` to `Some("")` on purpose (the listing's root wrapper node and `CreateRemoteDirectory` both need the root as a value); anything that turns a path into a *side effect* — `daemon::safe_local_path` / `safe_remote_path` — must use the non-empty form, since joining `""` onto a root promotes a per-entry action into a whole-root one (#72). `validate_absolute_remote_path` is the **third** rung (#323) and not a variant of either: the path is joined onto nothing, it *is* the location, so what it guards is normalization (`..` refused rather than resolved, `.` stripped, a *relative* path refused) rather than root escape. It may name anywhere in this user's Drive — granting nothing, since the socket is `0600` and the daemon shells the CLI the user can run by hand; routing the walk through the daemon is about `CliGate` (#23), not privilege — and, like the plain relative form, it accepts the root (`/`) because a listing is a read. A future *side-effecting* absolute caller needs its own non-root form.

### Invariants to preserve

- **Commit-after-side-effects, checkpointed.** An index write never precedes its side effect. Mutations commit in per-action **checkpoint transactions** (`commit_checkpoint` in `src/daemon.rs`): every side-effecting action — and every batched download chunk — commits its own mutations immediately after succeeding, while index-only mutations (`AutoLink`/`Purge`) accumulate into the next checkpoint or the final commit (so an adoption-heavy pass isn't thousands of fsyncs). A mid-plan failure keeps completed work durable; the failed action itself is never recorded and replans next pass, while its **successors still execute** (#136 — see the partial-pass invariant below). The **event cursor** advances only in the final commit of a fully-successful pass — never in a checkpoint — and is only ever *read* before the work it claims to cover: a bootstrap captures `latest_cursor` **before** the full-tree walk (`capture_pre_snapshot_cursor`), and when any lookup fails while prior state may exist — the cursor read, or the volume itself, which falls back to a stored cursor row that may be unreadable rather than absent — it persists **no** cursor — never clearing the stored one either, an older cursor being the safe replay point — rather than anchoring after the walk, which would assert that everything changed *during* a 30-minute walk had been applied (#294). A **first-ever bootstrap** has nothing stored to name a volume with — empty baseline, no cursor row — so it names one from the remote instead: a single targeted `list_directory` of the remote root (`volume_id_from_remote_root`, the O(1) call the event resolver already uses, whose nodes carry the composed `volumeId~nodeId`), and then anchors pre-walk like every other pass (#303). That listing is confined to the `Unnameable` arm — any baseline composed id or stored cursor short-circuits it, so it is not a per-bootstrap cost — is skipped entirely when nothing could use its answer (events off, or a degraded session that already pays a snapshot per `scan_interval` tick), and may **never fail a first sync**: an errored or volume-less listing degrades to the pre-#303 post-walk anchor (`PreSnapshotCursor::VolumeUnknown`), whose commonest cause is an *empty* remote root — the listing drops the root's own wrapper node — where a walk that listed no node can have missed no change to one. Once the volume **is** named, a failed cursor read persists nothing rather than retrying after the walk: a post-walk retry there would re-open the mid-walk window through a side door. (Guards: `a_first_ever_bootstrap_anchors_its_cursor_before_the_walk`, `a_failed_remote_root_listing_degrades_to_the_post_walk_anchor`, `a_first_ever_bootstrap_whose_cursor_read_fails_persists_no_cursor`, `a_bootstrap_that_cannot_use_a_cursor_never_lists_the_remote_root`, `a_bootstrap_that_can_already_name_its_volume_lists_nothing_extra`.) Approval consumptions commit in the same checkpoint as their delete's purge. Do not move index writes ahead of their side effect. (See `docs/adr/0003-*`.)
- **Path-safety at boundaries.** Every relative path from an external source (remote listing, local scan, conflict target) must pass `validate_relative_path` / `safe_local_path` before being joined onto a root. Absolute, `..`, and prefix components are rejected to prevent root escape. When adding a boundary that accepts external paths, guard it and add a test there. The guard is a **ladder, and each rung buys less than it looks**. (1) `validate_relative_path` is purely lexical, and deliberately returns `Some("")` for `""`/`.` — the root is a legitimate *value* there (the listing's root wrapper node; `CreateRemoteDirectory`'s empty-path arm). Anything that resolves a path into a **side effect** must therefore use `validate_relative_path_non_empty`, which is what `safe_local_path`/`safe_remote_path` do: joined onto a root, `""` silently promotes a per-entry download or delete into a whole-root one (#72). (2) Clearing `safe_local_path` still does not make a write to a *predictable* name safe (a conflict sidecar, a download destination): its `local_write_escapes_root` check canonicalizes the deepest **existing** ancestor, and a dangling symlink has none — so a broken link planted at the target passes the guard, and `Path::exists()` reports it absent while `fs::copy`/`fs::write` follow it. Such a write must refuse to follow: `create_new` (`O_EXCL`, one syscall, so no check/write race — `copy_into_new_file`) or land via `fs::rename` from a staging dir (what `proton.rs` downloads do), and any presence check guarding it uses `fs::symlink_metadata`, never `exists()`.
- **Non-destructive on unknown digests.** When a remote file exists but exposes no usable SHA-1, `remote_file_delta` returns `FileDelta::Unknown` and the planner avoids destructive actions (see the `Unknown` match arms in `plan_ongoing_action`). Preserve this conservatism.
- **Selective-sync filters apply everywhere.** Include/exclude globs (`ScanOptions`) filter local files, remote files, *and* base-index records before planning, so excluded records are never purged as "missing." Conflict sidecars and the index DB itself are always ignored.
- **First pass after boot always full-scans the *local* tree (warm start or bootstrap).** A fresh process has an empty `pending_changes` (`notify` does not replay pre-existing files), so the first reconcile must full-scan the local tree or it would idle-skip a file edited while the daemon was down. `is_first_reconcile` gates a dedicated `first_reconcile` branch that either **warm-starts** (event-driven reconcile with a *forced* local scan — `try_incremental_reconcile(force_local_scan = true)` — replaying the remote from the persisted cursor instead of the O(folders) walk) or **bootstraps** (the full-tree snapshot). Both full-scan the local tree; only the *remote* walk differs. `is_first_reconcile` clears **only on success**, so a failed first pass retries as a first pass rather than dropping into the steady-state idle fast-path (which skips the local scan). See ADR 0004. Warm-start eligibility: feature on + event source + a resolvable event scope (`resolve_event_scope`: the volume from a baseline composed `proton_id`, else from the sole stored cursor row whose `scope_id` *is* the volume — #32 — plus that cursor; a decline is logged once with its reason) + cursor fresh (`now - updated_at ≤ warm_start_max_cursor_age`, default 7 days) + the across-restart floor not due (`warm_starts_since_full_walk < warm_start_full_walk_every`, default 30, persisted in `warm_start_state`). Any doubt falls back to a bootstrap. Force a full walk with `proton-syncd --full-walk` (sticky across a failed first pass) or the `resync` IPC command (`proton-sync resync`, the addressed pair's `PairShared.force_full_walk` latch, consumed by that pair's next pass). `reacquire_event_source_if_needed` still forces a **mid-life** reacquisition pass to full-walk by reseeding the in-run resync floor — but **not** on the first pass (there `first_reconcile`'s cursor-age gate already covers the stale-cursor concern, and reseeding would risk overflowing the counter when a warm start increments it). **The rule is per pair, through the queue** (#102 phase 4a): every pair is seeded due at boot and its first pass is the first job it pops; `is_first_reconcile` is per pair, so a pair whose first pass failed retries as a first pass while the others proceed. And because the session is process-wide, a reacquisition bumps `Daemon::event_source_generation`: every *other* events-driven pair's cursor is as stale as the reacquiring pair's, so each one full-walks once at its own next steady-state pass (`catch_up_with_event_source_generation`), and the loop pulls every pair in to its new, live cadence. (Guards: `first_reconcile_warm_starts_on_a_fresh_cursor`, `first_reconcile_bootstraps_when_the_cursor_is_stale`, `a_failed_first_pass_retries_as_a_first_pass_and_still_scans_locally`, `the_warm_start_floor_forces_a_bootstrap_and_resets_the_counter`, `event_source_is_reacquired_when_the_keyring_becomes_readable`, `every_pair_gets_a_first_full_local_scan_before_its_idle_fast_path`, `a_failed_first_pass_on_one_pair_retries_as_a_first_pass_while_the_other_proceeds`, `an_event_source_reacquired_on_one_pairs_pass_forces_every_other_pair_to_full_walk_once`.)
- **Periodic safety resync is opt-in (off by default).** `events_full_scan_every` **defaults to `0`, which disables the periodic full-tree resync entirely**: after the first pass the daemon stays purely event-driven until it is restarted or the event stream forces a fallback (no cursor / no volume / fetch error / server refresh / unresolvable node / an incomplete listing, i.e. one holding a node the CLI could not decode / a `Created` node whose parent listing still lags). `effective_full_scan_every` maps the `0` sentinel to `u64::MAX` so the pass counter never reaches it. Set a positive `N` (flag `--events-full-scan-every N` or file `events_full_scan_every = N`) to reinstate a self-healing full walk every `N` *in-run* incremental passes. This is distinct from `warm_start_full_walk_every`, which forces a full walk every N *warm starts across reboots* (persisted counter): `events_full_scan_every` heals a long-running process, `warm_start_full_walk_every` heals a frequently-restarted one. (Guard: `disabled_periodic_resync_never_full_scans_after_the_startup_snapshot`.)
- **`scan_interval` is not a snapshot cadence in events mode; a degraded session is.** With events on and a live event source, a `scan_interval` tick is just another incremental (usually idle) pass — identical to an `EVENTS_POLL_INTERVAL` tick. It deliberately does **not** seed the resync floor to force a snapshot (#52): that would reinstate the periodic full walk the invariant above removes. The exception is a **degraded session** (`events_driven` on but no event source — locked keyring, headless host, no CLI session): every pass is then a full-tree snapshot, so a pair's cadence (`cadence_for`) is the 30s poll only while its events are live — `events_driven` **and** a session — and its own `scan_interval` otherwise, so those snapshots, plus the per-pass `reacquire_event_source_if_needed` retry, ride `scan_interval` (#50). **Per pair, never a process-wide minimum**, which would put a pair whose events are not live on the poll. Under live events the two old timer arms are one cadence, `min(poll, scan_interval)`, measured from the end of the pass, so a `scan_interval` tick no longer adds a second pass beside the poll. **"Event-driven detection unavailable" is one message family with one reason per cause**, because "keeps doing full syncs" is told apart only by the log line: `note_degraded_session_if_needed` reports the *no session* cause (naming both intervals) and `resolve_event_scope` the *no volume* / *no cursor* ones — so exactly one of them speaks per pass, each once, and a cause change re-reports. The family is **one message, two latches** (#102 phase 2): the session causes (no session, and #103's sign-out) latch on the *process* (`Daemon::session_declined`, typed by `SessionDeclineCause` so each recovery clears only its own — including `note_degraded_session_if_needed`'s own else-branch, which is what keeps "re-said on change" true), while no-volume/no-cursor latch on the *pair* (`PairRuntime::event_scope_declined`), because those causes read that pair's baseline and that pair's database. One shared latch would make two pairs declining for two volumes overwrite each other and log every pass for ever. That the two **detection** causes cannot both speak in one pass is structural, not arranged: the degraded reporter runs only when there is no event source, and every path that resolves a scope requires one. **The auth cause is the deliberate exception** — it is evidence from the pass's *outcome*, so it can follow a scope decline in the same pass, which is exactly the case a shared latch used to mask by overwriting. `note_degraded_session_if_needed` therefore keeps both `KeyScope::Pair` values it can see (`events_driven`, `scan_interval`) out of the process latch: a per-pair opt-out may not clear a process cause, and a per-pair number may not enter a reason the latch compares as a string (guard `the_process_session_cause_is_neither_cleared_nor_worded_by_one_pairs_config`). A pass that started streaming and then gave up logs the separate per-pass "event-driven pass fell back to a full-tree snapshot" line instead. (Guards: `a_degraded_session_does_not_full_walk_on_the_events_poll_cadence`, `a_degraded_session_still_reconciles_on_the_scan_interval`, `a_degraded_session_reports_that_cause_once_without_masking_the_scope_causes`, `a_degraded_pair_rides_its_scan_interval_while_a_live_pair_polls`, `the_process_session_cause_is_neither_cleared_nor_worded_by_a_second_real_pair`.)
- **A local change the watcher cannot queue must still force a scan.** The events-mode idle fast-path skips the local stat-walk when the event delta, `pending_changes` and `pending_deletions` are all empty, so anything the watcher drops is invisible to that pass — and with the periodic resync off by default and restarts warm-starting from the cursor, nothing later re-derives it. Watcher paths therefore feed the gate (#51): a **directory** `Create`/`Modify` is queued in `pending_changes` (filtered through `scan_options.allows_relative_directory`; never `mark_modified`, a directory has no file-content record semantics; the empty relative path is the watched root, not an entity) because an empty `mkdir` emits no file event at all; and a watcher **rescan notice** (events were *lost*) sets `force_local_rescan`, which forces `force_local_scan` on the next incremental pass and clears only when a pass succeeds. The notice has **two shapes** and one handler (`latch_local_rescan`, which sets the flag on *every* pair, ADR 0005 §5): notify 8.2 reports a Linux inotify queue overflow as an **`Ok` event** — `Event::new(Other).set_flag(Rescan)`, no paths — caught by `event.need_rescan()` at the top of `Daemon::route_event`, noted (`LostEvents::note_rescan`) *before* the per-path handlers because a handler returns early on error and a later note would be skipped, while a flagged event that also carries paths still has them queued; a watcher `Err` (`LostEvents::note_error`) is the other, and it also marks the roots it names `RootWatch::Incomplete` (every root when it names none: `MaxFilesWatch` carries the directory it could not add) so the next pass registers them again (`maintain_root_watch`) and scans locally until that takes. **Losses are noted while a drain routes and settled once after it** (`settle_lost_events`): an overflow can deliver thousands of notices in one backlog, and each used to latch every pair, warn, and walk every watched root again — now it is one latch and one re-registration per affected root per drain. An overflow also **re-registers the watch** (`settle_lost_events` → `rewatch_after_rescan`, #428): notify adds a subdirectory's watch only when it handles that directory's own create event, so a folder made during the overflow would never be watched again; `watch_root` on the root re-walks it (notify's `add_watch` visits every directory and `IN_MASK_ADD`s the ones it holds) — the owning root when the notice carries a path, every ready root when it carries none (Linux always). **Routing comes before every filter**: `Daemon::route_event` hands each path to the pair whose root is its longest component-wise prefix, so pair B's globs and conflict naming never see a path under pair A's root, a rename straddling two roots queues each side on its own pair, and a path no pair owns is dropped. The watcher channel is routed before every pop, in up to `MAX_DRAIN_ROUNDS` bounded rounds, so a pair's queued changes — and the echo of its own last write (#49), one that arrives while the backlog ahead of it is routed included — reach it before its next pass; that narrows the echo window rather than closing it (#425: an echo still in notify's thread when the last round ends is routed after the pair's next pass has cleared `authored_writes`, without the suppression). What arrives after the last round waits for the next drain, which `step_blocking` reaches as soon as the job it pops has run, not at the next step. A **third** cause is an event the handler itself failed to queue (`mark_modified` erroring returns at the first path, dropping it and every later one): `Daemon::route_event` notes that `Err` too, in the one place, and still returns it. The overflow was once handled only as an `Err`, which notify does not send for it, so the net never fired (#423) — and the old guard injected the `Err` it expected, not the shape on the wire. (Guards: `an_empty_directory_create_is_mirrored_by_the_next_event_driven_pass`, `an_inotify_overflow_event_forces_the_next_event_driven_pass_to_scan_locally`, `a_rescan_event_that_also_carries_paths_still_queues_them`, `a_watcher_error_forces_the_next_event_driven_pass_to_scan_locally`, `an_event_the_handler_could_not_queue_still_forces_a_local_scan`, `a_rescan_notice_forces_a_local_rescan_on_every_pair`, `a_watcher_error_forces_a_local_rescan_on_every_pair`, `an_overflow_re_registers_the_watch_on_every_root`, `a_folder_created_during_an_inotify_overflow_is_watched_once_its_root_is_registered_again`, `a_watcher_event_is_routed_to_the_pair_that_owns_the_path`, `an_event_under_pair_a_is_never_tested_against_pair_bs_filters`, `a_daemon_echo_is_routed_before_its_pairs_next_pass`, `an_echo_that_arrives_while_the_backlog_is_routed_still_reaches_its_pair_before_the_pop`, `a_set_cancel_flag_ends_the_step_while_the_watcher_keeps_producing`, `events_that_arrive_beyond_the_drain_round_cap_wait_for_the_next_drain`, `control_commands_that_arrive_during_the_drain_wait_for_the_next_drain`, `the_event_the_idle_wait_carried_is_routed_before_the_backlog`, `a_burst_of_rescan_notices_latches_once_and_registers_each_root_once`, `a_local_change_that_arrives_while_run_is_idle_is_routed_and_mirrored`.)
- **A wire path is a rendering, never a selector; and an unsyncable entity is named, not counted.** Every `PathBuf` that leaves the process as JSON goes through `lossy_path` (`ControlResponse`, `PlannedAction`, `DryRunReport`), because `impl Serialize for Path` *errors* on a non-UTF-8 path and `serde_json` is all-or-nothing: one such path used to fail the whole control reply (#61) or the whole dry-run report (#300, certain since #270 guaranteed such a path is planned rather than dropped). Two paths differing only in invalid bytes collapse to one string, so a command that turns a selector into a destructive side effect matches in wire form and **refuses an ambiguous selector** (`apply_approval_command`) rather than resolving it arbitrarily; the same rule binds any future command that authorises a plan row by path (#227). The other half: `SkipUnsupported` is correct and conservative, but a bare `skipped_unsupported` counter is not a report. The daemon keeps a standing `unsyncable` list (`record_unsyncable`), warns once per path per **run** (not per pass — a pass-rate log on a permanent condition is noise), publishes it on the status payload + metrics sidecar, and persists it. It is **merged, not recomputed**, and it has **two producers** whose evidence prunes differently (#232). The plan's `SkipUnsupported` rows are one; the local stat-walk's *drops* — a socket, symlink, FIFO or device node, which `visit_directory` reports rather than skipping silently — are the other, and they never reach the planner at all. A skip is never written to `file_index`, so it is absent from the baseline `reconstruct_remote` overlays and an incremental pass simply does not plan it — which is why a **remote** reason (and an unknown one, whose producer cannot be placed) is dropped by absence only on a full-tree snapshot. A **local** reason prunes on every pass that reaches the executor: both `bootstrap_reconcile` and `try_incremental_reconcile` run the whole local walk before planning and the events-mode idle fast-path returns before either, so that walk's silence *is* evidence — and without the split a deleted socket would sit on the list until a full sweep, which with the periodic resync off by default and restarts warm-starting is close to never. `UnsyncableReason::origin` is the one definition of which is which (`daemon::pass_proves_absence_of`), exhaustive by variant so a new reason must answer the question. Any pass may add; a path this pass planned a real action for or onto is dropped **unless this pass also observed it as unsyncable**, which is what a socket replacing a synced file looks like — the planner sees the file gone and plans a delete while the scan sees the socket, and the path is both. Reporting is one **local kind** per token (`local_symlink`/`local_socket`/`local_fifo`/`local_device`/`local_special_file`), added as tokens and not as variants a client must know: an older build parses `local_socket` to `Other` and prints it. The scan's own split matters as much — a path an exclude glob, an include filter, `.proton-sync.toml`, a sidecar or the `.sync` directory hides is **excluded, not unsyncable**, so the rule test runs first and the user's own skip rules never appear under "cannot be synced". (Guards: the `an_unsyncable_entity_is_named_persisted_and_outlives_*` / `a_path_that_becomes_syncable_*` / `*_once_per_run_not_once_per_pass` / `a_local_reason_prunes_on_any_pass_while_a_remote_one_waits_for_a_full_sweep` / `a_deleted_socket_leaves_the_list_on_the_next_pass_that_plans_anything` / `a_path_the_scan_still_reports_survives_a_delete_planned_for_the_file_it_replaced` daemon tests, `a_socket_symlink_or_fifo_is_named_instead_of_silently_dropped` and `a_socket_an_exclude_rule_hides_is_excluded_not_unsyncable` in `index`, `a_non_utf8_path_anywhere_still_serializes_the_whole_dry_run_report`, `dry_run_cli_reports_a_plan_containing_a_non_utf8_filename`.)
- **Delete-approval guard is execution-time, and holds the cursor when withholding.** **Gating and disposal are two questions**: this gate decides whether a deletion happens at all, and `trash::LocalDeleteMode` decides what a local one does once it does — neither changes the other's semantics, so an existing config behaves exactly as before. The gate lives in `execute_plan_and_commit` (`decide_delete_gate`), **not** the pure planner: it withholds `RemoteDelete`/`LocalDelete` (never `Purge`) whose direction is guarded at that path (per `dirconfig`) unless a matching approval exists. A withheld action skips **both** its side effect and its index mutation (re-plans next pass). If any action is withheld this pass, `cursor_update` is forced to `None` so a withheld `LocalDelete` keeps re-deriving from ground truth (else `reconstruct_remote` would drop it once the cursor passed its event). Approvals are consumed in the same checkpoint transaction as their delete's index purge — an executed delete's approval is consumed even when a later action fails the pass. The gate also *reports*: every withheld item carries its first-seen epoch (from `withheld_deletions`) and, for a directory, the subtree file count and byte total from the already-filtered baseline. (Guards: the `guard_*`/`a_withheld_local_delete_holds_the_event_cursor` daemon tests, plus `a_withheld_deletion_keeps_the_age_it_was_first_seen_at_across_restarts`, `keeping_a_folder_purges_its_whole_subtree` and `a_kept_remote_direction_deletion_comes_back_only_on_a_full_walk`.)
- **A failed item does not fail the pass, and partial failure is its own state.** `execute_plan_and_commit` continues past an action whose side effect failed (#136): the action's queued mutations are rolled back (never recorded), it is collected into `PassFailures` and reported as a bounded `failed_items` list plus an untruncated `failed_item_count`, and the rest of the plan executes — one poisoned file can no longer starve every action ordered after it, forever. The pass returns `PassOutcome::Partial { failed }`, a **third** outcome that is enumerated everywhere a pass outcome is branched on (`reconcile_blocking`'s message, the `proton-sync` headline/history/`syncnow`, the `#[must_use]` on `PassOutcome` that forces every test to say which it expects) rather than falling through an existing arm (#246). A partial pass sets `last_error` to a one-line summary, so every older surface still reports it as a problem, but it does **not** set `last_sync` / `last_successful_sync_summary` and does **not** clear `is_first_reconcile` / `force_local_rescan`. Two things keep the work from being lost: the **event cursor is held** (the same decision as a withheld delete and a vanished node — one policy, three causes), and every failed path is **re-queued into `pending_changes`** after the pass clears it, because a failed *upload* has no remote event and the held cursor alone would let the next event-driven pass take the idle fast-path. Two exceptions stay pass-fatal: a shutdown (`cancel_flag`, or every remaining action becomes a doomed spawn-and-kill) and `CONSECUTIVE_FAILURE_LIMIT` consecutive failures in a pass where **nothing** has succeeded (a dead CLI or an expired session is not a per-item problem; gated on zero successes so it can never starve anything). (Guards: `a_failing_action_no_longer_starves_the_actions_ordered_after_it`, `a_partial_pass_re_queues_its_failed_paths_so_the_next_event_driven_pass_retries_them`, `a_systemically_failing_pass_is_abandoned_rather_than_ground_through`, `a_shutdown_stops_the_pass_instead_of_failing_every_remaining_action`, `mid_plan_failure_leaves_index_and_cursor_unadvanced`.)
- **A plan-only pass observes and consumes NOTHING.** It is the most dangerous thing in the plan family because it runs the same scan and the same walk as a real pass, so anything it consumed would be spent *without* the side effects that justify spending it — and the real pass would then be unable to re-derive what the rehearsal rehearsed. One rule, one reason, and it is structural rather than a list each branch remembers: a plan pass does not go through `reconcile_blocking` at all (`Daemon::plan_now` → `plan_only_blocking`), and it **always full-walks the remote**, so it never streams events and the cursor hazard cannot arise. Nothing is persisted or cleared: no event cursor, no drained `pending_changes`/`pending_deletions`, no `is_first_reconcile`/`force_local_rescan` cleared, no warm-start counter moved, no `last_sync`/`last_successful_sync_summary`/`last_plan_summary` set, no `sync_passes`/`sync_events` row (history is written behind a side effect, and there was none), no delete approval consumed, no `withheld_deletions` re-stamped, and not even the standing `unsyncable` list merged into — this pass's drops ride on the plan itself as `cannot_sync` (#315). The **apply** it authorises is re-plan-and-compare, never replay: `compute_directory_deletion_verdicts` proves a recursive delete against the actions that will *really* be planned (#282), so executing frozen rows could authorise a deletion nothing re-derived. A divergence returns an `Err` — not a clean pass that did nothing, which would set `last_sync` and draw "everything is up to date" over a plan still waiting (#246's shape) — after publishing the fresh plan under a new token. A **filtered** apply (#192) skips destructive rows at the *executor*, never by filtering the plan: the gate must still run over the full plan or `replace_withheld_deletions` wipes the #225 first-seen ages and `pending_deletions` blanks over deletions that are still real. A skipped row holds the event cursor for the same reason a withheld delete does. A **pause is asymmetric across the two verbs, deliberately**: it cancels a booked apply, but a booked *plan* still runs. Both halves follow from the same rule — every booked request must be sealed — because cancelling an apply *is* a seal (`discard_queued_apply_for_pause` seals it `Failed`) while returning early from `plan_now` would seal nothing, leaving `plan_outcome` on `Computing` for ever and the GUI's plan poller, which has neither a paused bail-out nor a timeout, hung on `Checking…`. So the plan's pause check lives at the **ack** only (`PlanOutcome::Paused`); `LoopCommand::PlanNow` reaches `plan_now` without one, and must keep doing so — "making it consistent with the apply" is the fix to refuse. It is safe because that pass is inert, which is the invariant's own first sentence. A paused bail-out in the *client* is wrong for the mirror reason: between the ack and `plan_now`'s `syncing.store(true)` a poller reads `paused && !syncing` for a pass that will run and seal, so it would report a pause for a plan that then completes — and for an `apply` it races the daemon's own typed verdict and substitutes a sentence the client made up (#103's shape). That bail belongs to `watch_syncnow` **alone**, because only a `syncnow` skipped by a pause is never sealed (`reconcile_if_needed` early-returns without bumping `reconcile_seq`, so its target is unreachable and only the client can end the wait); `poll_until`, which serves `plan` and `apply`, had copied it and must not (guard `a_pause_mid_wait_does_not_end_a_plan_or_apply_wait`). (Guards: `a_plan_pass_observes_and_consumes_nothing`, `a_plan_pass_is_visible_as_a_plan_on_the_activity_surface`, `a_second_plan_request_while_one_is_running_is_answered_by_that_pass`, `applying_a_reviewed_plan_executes_it`, `an_apply_whose_plan_moved_executes_nothing_and_publishes_the_new_plan`, `an_apply_landing_on_an_idle_cycle_still_reaches_the_comparison`, `an_apply_that_fails_before_deciding_still_seals_a_verdict`, `a_pause_cancels_an_apply_it_overtook_rather_than_latching_it`, `a_plan_pass_booked_before_a_pause_still_runs_and_seals`, `a_filtered_apply_drops_the_deletion_and_leaves_the_approval_standing`, `a_filtered_apply_still_reports_the_deletions_it_skipped_as_pending`, `the_plan_window_never_truncates_a_destructive_row`, plus `the_plan_verb_reviews_and_the_token_applies_that_exact_plan` and `a_filtered_apply_runs_the_plan_without_its_deletions` in `tests/ipc_cli.rs`.)
- **A node that vanished mid-pass is skipped, never recorded, and also holds the cursor.** A node listed at plan time can be trashed/deleted by another client before its transfer runs (#31). `proton.rs` classifies that one case (`NodeNotFound`, from the CLI's stderr); the executor skips **just that action** — no side effect, no index mutation, so it re-plans next pass — instead of failing the whole pass, and a batched chunk's staged siblings still land and checkpoint-commit. **`NodeNotFound` means "skip and replan", not "this node is confirmed gone".** `download` covers one file and is exact; `download_many` is one invocation over a whole batch whose note names no request, so *every* unstaged (exit 0) or unsalvaged (failed) file in that chunk carries the type — including one the CLI skipped for its own reasons (a Proton-native document). That misread costs a replan and nothing else, and it lasts only while a vanished node keeps the note in stderr. `skip_if_node_vanished` is the single classifier for every single-file download, so the two **conflict-sidecar** downloads (`Conflict`, `TypeConflict`) skip on the same signal — and there the skip must take the *record* with it: a `Conflict` row whose sidecar was never written has no exit and is invisible to the GUI's conflicts list (#46), and the next pass reaches `(Changed, Missing)` and copies the local file in instead. The disappearance is *not* treated as a confirmed remote delete (a "not found" can equally be a transient listing error or a permissions change, and a `Download` may be an update to a file that has a base record), so nothing is purged on that signal. Any skip forces `cursor_update` to `None` for the same reason a withheld delete does: the skipped node's event must stay in the next delta so ground truth re-derives it. Everything *else* (a failed listing, an upload, a delete, an unexplained transfer failure) still fails the pass. (Guards: `a_vanished_node_skips_its_download_and_the_rest_of_the_pass_still_runs`, `a_vanished_node_in_a_batch_does_not_fail_the_rest_of_its_chunk`, `a_vanished_conflict_sidecar_skips_the_whole_action_including_its_record`.)

- **History is written behind its side effect, and an idle pass writes nothing.** A pass's history rows (`PassLog` in `src/daemon.rs`) buffer exactly like `index_mutations`: a failed action truncates them back, a checkpoint drains them, and they commit **in the same transaction** as the index mutation they accompany — so a history row can never describe a side effect that did not land, nor survive a shutdown that discarded one. The rollup (`changed`/bytes) is folded only *after* a transaction commits, never from the live buffer. The `sync_passes` row is opened lazily by the first checkpoint that commits an event, with `outcome = interrupted` and duration `0` — the true values for a pass in flight — so a crash leaves an honest row and no startup repair sweep is needed; every graceful ending (clean, partial, **and failed**, including a shutdown mid-plan) seals it in `reconcile_blocking`'s three-arm outcome match, which is why `interrupted` is reachable only by a crash. A pass is recorded only when it **changed something, did not end clean, or was a full sweep**: the events-driven default polls every 30s (~2900 passes/day on a live account), so recording idle passes identically would evict every useful row within minutes — and "the daemon is alive and passing" is already answered by `reconcile_seq`/`last_sync_epoch_secs`. A changeless *full sweep* is still recorded, because "when did the last one run, and was anything out of step" is exactly what it answers (#238). (Guards: `idle_passes_record_nothing_at_all`, `a_full_sweep_that_changed_nothing_is_still_recorded`, `a_partial_pass_is_recorded_as_partial_and_only_the_landed_action_has_an_event`, `a_failed_pass_is_recorded_with_its_error`, `a_failure_storm_never_evicts_the_last_full_sweep`.)

- **A folder that is not there, a lock another process holds and a watch that did not take do not stop the daemon, and a missing folder is not a failed pass** (#102 phase 4b, maintainer decisions M1/M1b). **Boot** prepares each pair (`prepare_pair_state`: create the folder, the index and lockfile directories, take the per-root lock) and opens its index; any failure builds a `PairSlot::Unavailable` that publishes the reason — it used to exit, and systemd restarted it every 10 s. The order is unchanged: every pair's per-root lock, then the one global lock (fatal, as before), then the indexes. The first metrics write is part of being prepared: its failure *demotes* the pair (`demote_pair`) instead of failing the start. **A retry** is a `Sync` job on an unavailable slot (`retry_unavailable`, unpaused only): the same preparation with `RootMode::MustExist` — **it never creates the folder**, so an unplugged drive's mount point is not conjured into an empty tree the next pass would reconcile against the remote (only boot creates it, as it always did). Success installs a `Ready` runtime with `is_first_reconcile` set and runs that pair's first pass in the same job; failure keeps it unavailable with its reason, logged once per cause. **The same OS error behind the folder that boot recorded is the same condition** (`FolderError`, carried by `PrepareFailure::Folder` and stored on `UnavailablePair`): a retry that meets it keeps boot's reason and adds no history entry, instead of rewording `could not be created: Not a directory` into a circular `does not exist … the daemon creates it when it starts` — and the retry's wording no longer sends the user to restart the daemon, which creates the folder even when it is an unmounted drive's mount point (#426). A retry reads a standing cause (`StandingCause`) before it reads the folder's existence. **A folder that vanishes under a ready pair** is the typed `RootUnavailable` (`is_root_unavailable_error`), raised by `ensure_root_available` at the top of `reconcile_blocking_inner` — *after* `take_apply_request`, so `seal_apply_outcome` answers a booked apply, and *before* the event-source reacquire and the `force_full_walk`/`reset_index` swaps, so a `reset-index` or `resync` made while it is gone survives until it returns. It also stops the events-mode idle fast-path from reporting `Clean` and moving the cursor over a folder that is not there. **The check runs again before the final commit of `execute_plan_and_commit`**, because a folder that vanishes *during* a pass leaves every later download refused with a warning — which used to end the pass `Clean` and claim the newer event cursor, so the skipped files were never asked for again. **It compares the directory's identity with `PairRuntime::known_root`, not only `is_dir()`** (`root_availability(root, expected)`, at the top of the pass too): a tree deleted and made again by something else, or an unmounted drive's mount point that stays a directory, is a directory and is not the folder the pass started on. **And it runs right after the local scan, before the first side effect, and before every download chunk** (the third 4b round, ADR 0005 item 13): the window between the top check and the scan holds the keyring read, the event fetch and the cursor capture, and a folder swapped in during it was scanned as the user's own — an empty replacement planned `RemoteDelete` for everything recorded and executed it before the final check could see it. A plan is therefore only ever derived from a scan of the directory `known_root` names (`try_incremental_reconcile` and `bootstrap_reconcile` both check straight after `scan_local_entities_reporting_progress`), nothing executes on another directory — **before each action since the fourth round (ADR 0005 item 14), and again immediately before an upload or a remote move since the fifth (item 15)**: `execute_plan_and_commit` checks before its loop (after the apply comparison, before anything about the pass is mutated) **and at the top of every action of that loop, for every arm**, so a folder swapped between two actions ends the pass with the current action having no side effect — a `LocalDelete` used to dispose of the replacement's own files at the planned paths (for good in `permanent` mode) and an `Upload` used to push the replacement's bytes under the planned path with the scan's digest recorded — and a tree deleted between two chunks of one download group ends the pass before the next chunk is issued (`execute_download_run`, the same check before every chunk, since a batched run is one action whose chunks are its side effects). **The two arms with a CLI child of their own between that look and their side effect look once more** (item 15): `Upload` runs `ensure_directory` (about a second) before the child that reads the file, and `MoveRemote` runs it before `rename_or_move`, so a swap inside that second had the replacement's bytes uploaded under the planned path; each looks again immediately before its transfer or rename (`a_folder_swapped_while_an_upload_makes_its_remote_directory_uploads_nothing_from_it`, `a_folder_swapped_while_a_move_makes_its_remote_directory_moves_nothing`). Every other arm's side effect follows the top look with nothing slower than a local `stat` between them (`CreateRemoteDirectory`, `RemoteDelete` and the downloads make their one CLI call straight after it, and the local arms go through `ensure_directory_below`), and `a_swap_before_an_arm_runs_nothing_of_it` is one row per remaining side-effecting arm (`Upload` and `LocalDelete` are pinned by the round-4 tests; `AutoLink`/`Purge`/`SkipUnsupported` are index-only). A swap *during* a transfer's own CLI call cannot be closed by any look; the check before the final commit holds the cursor for it. **A look that fails with something other than "not found" ends the pass too** (fail closed: `EIO`, `ESTALE` or a timeout on a network mount is no answer, and carrying on would run on a folder nobody could name), **after the index-only work the loop had accumulated is committed** (`keep_accumulated_work`, at every exit of the loop for that cause — the top-of-action look, an arm that met it, a download run, the check after the loop). Those adoptions and purges were derived from the scan the post-scan check validated and are what the next checkpoint would have carried, so a large adoption on a flaky mount no longer starts over from the scan at every failed look, and a first sync whose folder is then replaced by an empty one has, with the state outside the folder, a baseline that records what it adopted — which is what holds the replacement. **With the default layout the index goes with the folder and that commit cannot land**, so the replacement is held by the count the pass planned with, noted in memory when its plan existed (`PairRuntime::items_known_in_memory`: the baseline as the planner sees it plus the adoptions it planned, committed or not; spent when a pass completes and by a `reset-index`) — a demotion carries the greater of it and the database's count, a database that cannot be read still being `Unreadable` (`a_first_sync_swapped_for_an_empty_folder_is_held_with_the_state_inside_the_folder`, and its outside twin); the failed action's own queue is discarded like any failed action's (`a_look_that_fails_mid_pass_keeps_the_adoptions_made_before_it`, `every_exit_of_the_loop_for_an_unavailable_folder_keeps_the_adoptions_before_it`). The arms' directory creation (`ensure_directory_below`) keeps its own check because it is the one place a directory is made and must not make the root: the creation primitive's rule, not a second copy of the executor's. **The executor makes a directory in one place, `ensure_directory_below`, and never the root**: `create_dir_all` made every missing ancestor, so a tree deleted while a pass ran came back from the next download's destination holding a fraction of itself, and the next pass planned the rest as deletions. It checks the root first, then makes the levels one at a time with `create_dir` (`create_directories_below`, which stops at the root), so a root that vanishes between the check and the call fails the call. **No code path a pass runs can make the root or an ancestor of it** (item 13): the client's download staging directory is made non-recursively, one level below the directory the executor made (`proton::create_download_scratch_dir`, the one place the client makes a directory — a second chunk of one group used to make a deleted root again through `create_dir_all`), and `write_atomically` makes no directory at all (the sidecars live beside the index, whose directory `prepare_pair_state` makes). The `create_dir_all` calls that remain are boot's alone — `prepare_pair_state`'s root under `RootMode::Create`, `from_pairs_with_opener`'s socket directory and the user-global lock's directory (`create_parent_directory`, both never under a root), `paths::ensure_private_runtime_dir`'s fallback runtime directory — none reachable from a pass or a retry. **A pair's state directories are made below the folder the preparation just found** (`create_state_directory_below` → `create_directories_below`, item 14): `prepare_pair_state` used to look at the folder and then `create_dir_all(<root>/.sync)`, which made a root that vanished between the two calls again, on every retry; now that call fails instead, and `LockGuard::acquire` makes no directory at all (`preparing_a_pair_never_makes_a_folder_that_vanished_after_its_look`, through the `prepare_pair_state_after` seam). A typed `RootUnavailable` out of an action ends the pass at once instead of counting as an item failure — otherwise twenty identical failures trip the breaker and the pass reads "abandoned" with the folder never named — in the per-action loop **and** in the batched download run, whose group-level directory creation used to record it as one failed item per member and carry on to the final check. **A `resync`/`force_full_walk` latch taken by a pass that then ends `RootUnavailable` is latched again** (`reconcile_blocking_inner`), so the walk the user asked for still happens. Now the typed error is returned before that transaction: the cursor (the fifth cause of the one cursor policy), the index-only tail and the history rows are held, checkpoints that already landed stay, the row they opened is sealed `failed` by the typed arm (`interrupted` is what only a crash leaves), and the next pass takes the missing-folder path. `reconcile_blocking`'s typed arm writes **no** `sync_passes` row, spawns no `proton-drive` child and writes **no sidecar** (there is nothing to record; and `write_atomically` used to create its directory, which with the default layout is inside the root, so a status write made a missing folder again — since item 13 it makes none, so a *failed* pass over a vanished folder cannot bring it back either); it still sets `last_error`, bumps `reconcile_seq` and publishes. A plan on a missing folder answers in the sync's own words — `root_availability` is the one definition of the message, used by `ensure_root_available` and by `plan_only_blocking`, with no latch and no demotion because a plan observes and consumes nothing — and seals `Failed`; it used to fail at the scan with a bare `No such file or directory (os error 2)` and no path. **A plan on a replaced folder is refused the same way** (item 14): `examine_ready_pair` runs on `Sync` jobs only, and the plan used to ask `root_availability(root, None)` — whether *a* directory was there — so it scanned the replacement and published `RemoteDelete` for everything recorded, rows the plan screen's typed-DELETE gate pins approvals to (#227) that stand after the replacement is judged. `plan_only_blocking` reads `PairPass::root_verdict` — the identity against `known_root` plus the `unjudged` latch, the sync's own verdict without the sync's once-per-cause latch — and `build_plan_report` checks again right after its scan (`expected`; the one-shot child passes `None` and keeps its presence check), so a plan is never derived from a replacement and stores nothing (`a_plan_on_a_replaced_folder_is_refused_and_publishes_no_rows`, `a_plan_is_refused_when_the_folder_is_swapped_during_its_scan`). The cause is logged once per pair (`PairRuntime::root_unavailable`, `UnavailablePair::reason`), again when it changes — **never in a process latch**. **A pair whose folder is no longer the one it ran on is examined once, before its pass, and the question is the same however it stopped being that folder** (`Daemon::examine_ready_pair`, `PairRuntime::examine`, `Examination`; the first thing in every unpaused `Sync` job of a ready pair, before `maintain_root_watch`). Two things can have happened. The directory at the root path is a different one from the one the pair accepted: `PairRuntime::known_root` (a `RootRecord`) is recorded when the runtime is **opened**, so it exists whether or not a watch registration ever completed (a watcher refused from boot, `ENOSPC`, leaves the pair able to tell), it is **back-filled by the first examination that can see the folder** when the look at open failed (`Examination::Unrecorded`, item 13 — a pair used to be without it for life), it moves only when the examination accepts a replacement, and it is **carried through a demotion** (`UnavailablePair::known_root`) so a promotion from **any** cause is examined against it: `retry_unavailable` hands a plainly promoted runtime the carried identity and runs `examine_ready_pair` on it, so an empty replacement over a baseline that records items is held, one with content is accepted with its deletions withheld once, and one that cannot be judged does not start. **The record takes two looks, the index's own rule** (item 14, `RootRecord::from_two_looks`): on a filesystem that names the folder differently on each look (a FUSE mount without stable inode numbers) one look made every job `Replaced`, which set `force_delete_approval` on every pass and, with the guard off, withheld every deletion for ever — a policy override nothing reported. Two looks that disagree at open are `RootRecord::PresenceOnly`: no replacement is detected for that pair, nothing is held or forced for one, the examination never records the folder, the configured deletion policy applies as it is, and the pair says so once at open (`open_does_not_trust_a_folder_identity_the_filesystem_gives_differently_on_each_look`, `a_folder_the_filesystem_cannot_name_consistently_keeps_the_configured_policy`); the index's and the lock's presence checks still work there. **A plain promotion is judged before anything is prepared** (item 14): with the default layout the demotion dropped the only connection to the baseline, and the retry made `.sync`, a fresh index and a lock in an empty replacement, which the examination after the open then read as "nothing recorded" and accepted — the bootstrap downloaded the whole remote into it. `UnavailablePair::demoted` reads the baseline's count as the planner sees it (`recorded_item_count`, through the connection it is about to drop) into `UnavailablePair::recorded_items`, **a `CarriedCount` and not an `Option`** (item 15): `Absent` is a pair that was never ready in this process (nothing to lose), `Items(n)` is a count, and `Unreadable` is a baseline that could not be counted, which is *not* zero — the first version filtered an unknown count out together with an absent one, so the judgement was skipped and an empty replacement was prepared and populated. `retry_unavailable` runs `judge_carried_replacement` on a plain promotion before `prepare_pair_state` whenever `CarriedCount::at_risk` (a positive count, or an unreadable one): **a folder that holds nothing the pair's rules would keep is held, with nothing created, opened, locked or downloaded, whichever directory it is and whatever identity the pair recorded** — `StandingCause::ReplacedByEmptyFolder` for a count, `ReplacedByEmptyFolderUncounted` (worded without a number it does not have, released the same two ways) for an unreadable one. The first version required a *different* directory and a pair that had recorded an identity, so a folder emptied in place after a failed retry (C1) and a pair whose folder cannot be named consistently (C3) were prepared and populated; a count of `0` and a pair that was never ready are not judged (`a_baseline_that_recorded_nothing_is_not_held_when_the_folder_is_replaced_by_an_empty_one`). A look that fails, a folder that cannot be searched and rules that cannot be built each prepare nothing and say so (`a_promotion_over_a_folder_nobody_can_look_at_prepares_nothing_and_says_why`, `..._nobody_can_search_...`, `a_promotion_whose_rules_cannot_be_built_prepares_nothing_and_says_why`). The count rides on the promoted runtime (`PairRuntime::carried_recorded_items`, a `CarriedCount` too, read beside the fresh index's own by `recorded_under_an_empty_folder`, where an unreadable one with nothing else to say is `Recorded::Uncounted`) until a pass completes on it or a reset discards it (`a_carried_count_is_spent_by_the_pass_that_completes_on_its_runtime`, `a_reset_index_discards_the_count_a_demotion_carried_even_when_its_pass_fails`). A lifted hold is not examined again (`standing_cause_status` just did; its first pass withholds every deletion) and a `reset-index` is not examined at all (its pass empties the baseline the examination would read, and would otherwise hold the pair the user asked to start over) — `Promotion` is the three-way record of which; the `RootWatch` state is about registration and says nothing about which folder this is. Or the index or the lock it holds is no longer the file at its path: the index by the `(device, inode)` recorded at open (`PairRuntime::db_identity`), the lock by the held file's own (`LockGuard::is_the_file_at`), a missing file counting as gone (`PairRuntime::state_status`, `removed_state`). The default layout keeps both inside the folder, so a folder deleted and made again left the pair `Ready` on a connection to a file with no name (every write failed with `attempt to write a readonly database`, a new file was uploaded again on every pass, `last_error` stuck until a restart) and holding a lock on a file a second daemon could lock beside it. **If either happened and the folder holds nothing the pair's own `ScanOptions` would keep** (`index::local_tree_holds_syncable_entry`, built on `visit_directory`'s predicates, so `.sync`, a trash directory, `.proton-sync.toml`, a conflict sidecar and anything an exclude rule hides do not count) **while the baseline as the planner sees it (`filter_base_index`) records items, the pair is held** (`StandingCause::ReplacedByEmptyFolder`) **and nothing is created, opened, locked or downloaded.** The baseline is read through the connection the pair still holds, which works on a file that has been unlinked. Planned as it stands that is the deletion of everything recorded (held by the guard by default, executed outright where it is off), and preparing the pair again in it would download the whole remote into it: #426 reached mid-life, with no restart. For the default layout this takes precedence over the state demotion — the old order demoted first, and the same-job retry created `.sync`, a new index and a lock in the empty folder and bootstrapped. A folder emptied **in place** with its state intact is *not* held: that is the user's own deletion, withheld or executed by the guard like any other. Otherwise a state that went with a folder that has content (or a pair that recorded nothing) demotes the pair and the retry in the **same job** prepares it again (`RootMode::MustExist`: still never creates the folder); an index that went with the folder is an empty baseline, so the first pass bootstraps: it adopts and downloads, and cannot plan a deletion. A replaced folder with content, or a pair that records nothing, is accepted (`known_root` moves, `maintain_root_watch` registers it, the pass scans it), so a filesystem with unstable inode numbers costs one rescan and never a stuck pair; a directory entry alone counts as content; boot has no identity to compare, so the same state at startup is #426. It runs **only while the folder is there** (a missing folder is the typed error's, reported once; demoting too would write two history entries for one cause); a **plan refuses** with the reason instead of demoting; and the IPC task's approvals connection is replaced when the pair is prepared again (`PairShared::runtime_generation` against `ControlPlanePair::opened_under`), because `has_runtime` flips false and true inside one job and that task may never read the false. A filesystem that names one file differently on two looks (a FUSE mount without stable inode numbers) cannot support the comparison, so the index's identity is then `None` and the lock's `comparable` is false and **only presence is checked** — otherwise every attempt would prepare the pair again, a full first pass each time (`PairRuntime::open_looking` and `LockGuard::acquire_looking` take the `stat` as an argument so a test can make two looks disagree). **Only "not found" says a file or folder is gone** (`Look`, `look_at_root`, `FileIdentity::look`): any other `stat` error (`EIO`/`ESTALE` on a network mount, `EACCES`) is `Look::Unreadable` and decides nothing — no demotion, no hold, no watch change, no acceptance — and is said once per cause (`note_unreadable`, `PairRuntime::unreadable`, `UnavailablePair::unreadable`). A replaced folder whose content or baseline could not be read (`Recorded::CannotTell`) is neither accepted nor held, and **its pass does not start**: `PairRuntime::unjudged` makes `ensure_root_available` raise the typed `RootUnavailable`, so the cursor and every latch stay as they were and the judgement is made again at the next job. **A retry re-checks the folder's content** (`standing_cause_status`), not its existence: still empty stays unavailable and moves one history entry; content makes it ready, watched and scanned (a partly restored folder counts, and so does a stray `.directory` or an empty `lost+found/`, because the content test is binary — so **the first pass after any accepted replacement withholds every `RemoteDelete`/`LocalDelete` for approval, whatever `deletion_policy`/`[delete_approval]` says** (item 13; `PairRuntime::force_delete_approval`, set when `examine_ready_pair` accepts a replacement with content and when a hold lifts on content in `retry_unavailable`, **not** by a `reset-index`, whose bootstrap plans no deletion; read by `decide_delete_gate`, which counts what it withheld only for this reason in `DeleteGate::forced`; cleared when a pass completes with that count at zero; carried through a demotion on `UnavailablePair`; **and persisted** — `index::forced_delete_approval`, one row like `warm_start_state` (item 14): written when it is set (`PairRuntime::force_delete_approval_until_settled`), cleared **in the final commit of the pass that spends it** so a restart between the two cannot find it standing on disk and spent in memory, loaded at open (a read that fails withholds for one pass rather than deleting), truncated by `reset_index_state` because a start-over plans no deletion — so a restart, which the GUI's restart-daemon flow performs, does not spend it either; it used to start `false` at open and execute the withheld deletion on the boot pass with the guard off (`the_forced_approval_after_a_replacement_outlives_a_restart`)). The withheld deletions are pending exactly like guarded ones — same list, same ages, same cursor hold. The deletions exist only for an index that survived outside the folder: with the default layout the index went with the folder, so the pass after the hold lifts is a bootstrap and plans none); the cause holds through the folder going away and an empty one returning; a look that failed holds it. **`proton-sync reset-index --yes` is the explicit way out, and a restart is deliberately not offered** (with the guard off, a restart over an empty mount point deletes everything remote when the index survived outside the folder, and downloads everything into the mount point when it did not — the hold is in memory only, so a restart while held is #426 again; a `reset_index` latched earlier, while paused say, releases a later hold with no new request, which is still the user's explicit request and is kept): `retry_unavailable` releases the cause when `reset_index` is latched (`StandingStatus::Reset`), prepares the pair (a fresh index where the state went with the folder, the surviving one otherwise), and the pass that follows consumes the existing latch before it loads the baseline, so it is a bootstrap — it downloads, adopts and has nothing to delete from; the request is sealed as any `reset-index` is. `resync` does not release the hold. An apply cut short by `RootUnavailable` is sealed `Failed` even though the deletions it had already checkpointed ran. **What a pair published stays published.** An unavailable pair's `status_history` is its real history (the sidecar at boot, the runtime's on a demotion) plus at most one `unavailable` entry: `record_repeatable_status_entry` moves the newest entry's time for a repeat of the same cause instead of adding one, because an entry per attempt evicted a 20-entry history in about ten minutes; it is **never empty** (gui-core reads no `last_sync` and no history as `FirstRun`). `last_sync`, the summaries, the pass history and the corpus size are carried across a demotion and back. `PairShared::has_runtime` is the IPC task's whole view of the slot: it opens the approvals connection on first use when set and drops it when not, and `pause`/`resume` write no metrics sidecar for a pair that is not ready (the file belongs to whoever holds its lock) nor into a directory that is gone. **A watch that did not take does not make a pair unavailable**: syncing without one is correct, only not cheap. `RootWatch` is `Unregistered`, `Watching(RootIdentity)` or `Incomplete`; `maintain_root_watch` runs before each pass of a ready, unpaused pair (after `examine_ready_pair`: it registers, it does not judge) and registers an unregistered root, **registers again a root whose identity (device, inode, birth time) changed** — deleted and created again between two passes, it passes `is_dir()` and the kernel dropped the watch with the old directory — and retries an `Incomplete` one. - **N pairs, one queue: a pass touches only its own pair, every consumed request is sealed, and shutdown cuts at a pair boundary** (#102 phase 4a). A pass reaches its pair's published state only through `PairPass::pair_shared`, resolved by `pass_for(i)` from the index the queue popped. With an index-0 shortcut a pass on pair B would take pair A's queued apply, consume A's `reset_index` latch and truncate B's own index, or bump A's `reconcile_seq` — which is why every such shortcut is `#[cfg(test)]`. Every arm of `run_job` that consumes a request answers it, because pollers have no deadline: a paused pair seals its queued apply `Failed`, a booked plan still runs on a paused pair and seals, and an unavailable pair seals syncs, plans and applies with its reason. Shutdown is the cancel flag plus a `Notify`: the step checks the flag before every pop, so a shutdown mid-pass fails only that pass (its checkpoints stay, its cursor does not move), earlier pairs stay committed and later ones never start; requests still queued at shutdown are not sealed, as before (the socket goes away and clients give up after their transport errors). (Guards: `a_reset_requested_for_one_pair_never_truncates_another`, `an_apply_booked_for_one_pair_is_never_taken_by_another_pairs_pass`, `a_resync_latched_for_one_pair_forces_only_that_pairs_walk`, `a_pass_publishes_into_and_bumps_only_its_own_pair`, `a_scheduled_sweep_latches_only_its_own_pair`, `a_pause_on_one_pair_cancels_only_that_pairs_queued_apply`, `a_plan_booked_for_a_paused_pair_still_runs_and_seals`, `an_unavailable_slot_seals_syncnow_plan_and_apply`, `a_shutdown_mid_pair_two_leaves_pair_one_committed_and_pair_three_untouched`, `a_boot_sequence_is_cut_at_a_pair_boundary`, `a_cancel_set_while_the_loop_is_idle_ends_run_promptly`.)

### Testing pattern

`Daemon<C: ProtonClient>` is generic over the client. Tests inject fake `ProtonClient` implementations (see the fakes in `src/daemon.rs` tests — including one that fails uploads to exercise the checkpoint-commit invariant: completed actions stay committed, the failed action is never recorded — see the `reconcile_checkpoints_*` tests) so reconciliation is tested without a real Proton Drive. A test reaches the default pair's state through `daemon.pair()` / `daemon.pair_mut()` and its pass family through `daemon.pass()` / `daemon.reconcile_blocking()` — **all four `#[cfg(test)]`**, as is `ControlShared::pair()`, so production code cannot take an index-0 shortcut (`daemon.runtime(i)` / `daemon.pass_for(i)` address any pair). Multi-pair tests build a daemon with `Daemon::from_pairs` over `pair_configs(dir, names)` (one root, index and lock per pair, one shared daemon-wide half) and a `MultiRootClient` that records which remote root each walk listed. **Anything about ordering is driven through `step_blocking` itself** (`Stepper`: real `loop_rx`/`watch_rx` channels, a `RecordingWatcher`, a `FakeClock` a fake client can move mid-pass) — never through a test-only copy of the loop body, which is how an ordering goes untested. Loop-level behaviour (shutdown waking an idle loop, a boot cut at a pair boundary, per-pair cadence in real time) runs `Daemon::run` on a multi-thread runtime. **A test that builds a daemon from a *resolved* config must repoint `global_lock_path` first** (`resolve_runtime_configs` fills it with the real per-user lock under `$XDG_STATE_HOME`, which a running daemon on the same machine holds — `docs/agent-notes/resolved-configs-carry-the-real-global-lock.md`). **A test that starts a binary of this crate starts it through `tests/common`** (`syncd`/`sync_cli`: the only places a test names a binary; `sandboxed`/`sandbox`: `HOME` and the five XDG directories in the test's own directory, the D-Bus bus addresses removed, and stub `secret-tool` and `curl` first on `PATH`; `run_bounded`: killed after its bound, and failed if the run reached a stub; `spawn_logging`: a daemon with its stderr kept; `refuse_the_real_cli`: a `proton-syncd` with no fake `proton-drive`, **or with `events_driven` left on** — which reads the signed-in Proton session from the desktop keyring — is refused before it spawns) — a refusal test that regresses becomes a real daemon, and one did bind the live control socket (`docs/agent-notes/resolved-configs-carry-the-real-global-lock.md`). `tests/test_isolation.rs` pins the helpers, and its scan fails any file under `tests/` other than `common/mod.rs` that contains the literal `CARGO_BIN_` + `EXE_` or calls `.spawn()`; it does not catch a binary reached without that name (a path built from `target/`, a `concat!`-split name), and it follows no data flow. The binary-level two-pair tests (`tests/ipc_cli.rs`, `DaemonProcess::spawn_with_config`) start a real `proton-syncd` with **only daemon-wide flags** — a per-pair flag beside several pairs is refused — with `events_driven = false` and a `scan_interval_secs` in each table, through that sandbox and with `RUST_LOG=warn`. `tests/scripts.rs` runs `setup.sh`'s config helpers on a temporary file and `uninstall.sh --dry-run` in a cleared, scratch environment with `systemctl` and `cargo` stubbed (a dry run removes nothing; never run the scripts for real from a test). The planner in `src/sync.rs` is pure and tested directly with in-memory maps. Prefer adding regression tests next to the logic you change (planner tests in `sync.rs`, boundary tests where external paths first enter).

## Conventions

- Errors use `AppResult<T>` = `Result<T, Box<dyn Error + Send + Sync>>`; construct ad-hoc errors with `boxed_error(...)`.
- Structured logging via `tracing` to **stderr** (stdout is reserved for machine-readable dry-run JSON). Control verbosity with `RUST_LOG`; default is `info`.
- Uploads/downloads/deletes are never auto-retried (avoids duplicate side effects); only read-only remote listings retry per `proton_list_attempts`. Continuing past a failed action (#136) is not a retry: that action is attempted at most once per pass, exactly as before.
