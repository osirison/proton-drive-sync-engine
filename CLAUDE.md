# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Rust prototype for bidirectional file sync between a local folder and Proton Drive. Ships two binaries backed by one library crate (`proton_drive_sync_engine`):

- `proton-syncd` (`src/bin/proton-syncd.rs`) — long-running daemon; also hosts the one-shot `--dry-run` path, which returns before `Daemon::new` and so takes **neither** lock and builds its **own** `ProtonDriveClient`. That is deliberate — taking the user-global lock would fail the preview exactly when a daemon is up, the only case it is useful in — so it *warns* instead (#317): `daemon::probe_daemon_lock` takes a **shared** `flock` on `config.global_lock_path` non-blockingly and drops it in the next statement, which is as close to "check without acquiring" as `flock` (which has no query op) allows. Never waits, never holds, never creates the file, and answers a three-state `GlobalLockProbe` whose `Unknown` is evidence of neither. stderr only: stdout carries the report.
- `proton-sync` (`src/bin/proton-sync.rs`) — thin control CLI that talks to the daemon over a Unix socket.

Unix-only today: control-plane IPC uses Unix domain sockets (`#[cfg(unix)]` guards in `src/ipc.rs`). Edition 2024 toolchain required.

## Architecture

The engine reconciles **three sources of truth** into a plan, then executes it:

1. Local files under `local-root` (`index::scan_local_files_with_options`, SHA-1 hashed)
2. Remote files from `proton-drive filesystem list --json` (`proton::ProtonClient::list`)
3. The last-synced baseline in SQLite (`index::load_index`)

Data flow: **scan → `sync::plan_sync` → execute actions → commit index**. This is the spine; changes to sync behavior almost always start in `src/sync.rs`.

### Module responsibilities

- `src/sync.rs` — **pure** planner. `plan_sync` produces `Vec<PlannedAction>` with no I/O. Bootstrap (empty index) vs ongoing logic are separate; ongoing decisions come from a `(local_delta, remote_delta)` matrix in `plan_ongoing_action`. Also owns conflict-sidecar naming (`ConflictNaming`, default suffix `proton-cloud`, configurable via `conflict_suffix` — **changing it orphans sidecars already on disk**: they stop matching `is_conflict_copy`, so the scanner no longer ignores them and they upload as ordinary files; guard `changing_the_suffix_orphans_sidecars_written_under_the_old_one`. Threaded explicitly from `plan_sync`/`plan_sync_entities` down, and reaching every *detector* too — `ScanOptions`, the daemon watcher, the GUI's disk walk — because one spelling on the writing side and another on the reading side means the engine uploads the sidecar it just wrote) **and each sidecar's source**: `PlannedAction.sidecar_from_local_copy` distinguishes the ordinary conflict (download the remote revision) from `(Changed, Missing)` — a local edit whose remote copy was deleted elsewhere — where the sidecar is a *copy of the local file*, because there is nothing to download and a conflict with no sidecar has no exit and is invisible to the GUI's disk-walking conflicts list (#46). A kind mismatch is likewise two questions, not one: `is_live_kind_clash` (both sides live and disagreeing) is the only real `TypeConflict`, while `only_base_kind_is_stale` means the index row is out of date and the surviving entity is planned as a bootstrap, whose upsert replaces the row's `entity_kind` (#47). `plan_entity_action` is the **single** definition of what a path resolves to, and `compute_directory_deletion_verdicts` proves its subtrees through it: a recursive directory delete may only be proved against the actions that will really be planned. Dispatching that proof on `base.entity_kind` alone narrowed a live entity of the *other* kind away as absent on both sides, scored it a clean `Purge`, and deleted the only copy of it (#282). The proof is one bottom-up fold — each entry planned once, folded into its nearest *tracked* ancestor, since selective-sync gaps mean the immediate parent may have no base row — and is skipped wholesale when no base directory is live on exactly one side, those arms being the only readers of a verdict (#48). A path that is not valid UTF-8 is **unsyncable** (`is_representable_remotely`, #270): the CLI reports the remote tree as JSON, so an upload's copy comes back under a lossy key and forks into a perpetual Upload+Download pair. The gate sits in `plan_entity_action`, the one definition of what a path plans to, so the deletion proof inherits it: such a path plans `SkipUnsupported` and nothing else, which is not a delete, so no ancestor subtree holding one is ever proved clean and the recursive `LocalDelete` that would destroy its only copy is never authorised. A `MoveRemote` onto such a path is dropped in `plan_file_path_transitions`. A directory `MoveLocal` suppresses its **untracked** live descendants there too (#12): the rename happens before the per-path actions, so a bootstrap `Upload` planned for a new file at the old path would first recreate the moved-away parent remotely and then read a file that is no longer there. Nothing can be re-planned at the new path either — the pre-move scan does not hold that key — so the subtree is left to the next pass, which the executor guarantees runs by re-queueing the move destination. The rule is one-sided: remote names are never screened, since a genuine U+FFFD is indistinguishable from a lossy one and an already-forked pair settles by downloading the lossy copy. Every `SkipUnsupported` is built through the one constructor `PlannedAction::skip_unsupported`, so it always says **why**: `UnsyncableReason` is `unrepresentable_path` (the local #270 cause, visible to any pass that scans locally) or `remote_not_downloadable` (a Proton-native Docs/Sheets node, or a #59-degraded one) — plus the five #232 local kinds, which arrive from the scanner rather than the planner and so never appear on a `PlannedAction` at all. Every reason answers `origin` (`Local`/`Remote`/`Unknown`), the one definition of which passes may drop a standing item by absence. Note what does *not* plan a skip: a remote file with no `claimedDigests.sha1` yields `FileDelta::Unknown`, whose arms plan an `AutoLink`/`Conflict`/nothing — a Proton-native document has no digest *because* it is not a byte blob, which is the fact #295's evidence read backwards. `UnsyncableItem` (path + kind + reason + first-seen) is the shared shape #232's local kinds — sockets, symlinks, FIFOs, devices — plug into; the token is hand-serialized so an unknown one parses to `Other` instead of failing an older client's whole reply, which is exactly what let those five be added without a lockstep client upgrade. `entity_kind` is `File` for every local kind: the engine knows two kinds and none of these is a directory it would descend into (a symlink to a folder is not followed either), so the *reason* is what says what it really is. `SyncAction::is_destructive` is the **one** definition of the plan's destructive set (`RemoteDelete`/`LocalDelete`/`Purge`) — `PlanSummary::destructive_actions` counts with it and `apply --skip-destructive` (#192) drops with it, so the number a user is shown and the rows a filtered apply omits are the same set by construction. A different question from `delete_direction`, which is the *approval gate's* set and excludes `Purge` (index-only, destroys nothing). `plan_token` (#100) is a plan's identity: a version-tagged SHA-1 over the rows sorted and length-prefixed, from **raw path bytes** (two paths differing only in invalid UTF-8 are two plans and the wire form collapses them), covering every field that says what will happen — `size_bytes` included, because an upload whose file changed under the review is exactly the divergence the token exists to catch. `DryRunReport.cannot_sync` (#315) carries the walk's own drops — sockets, symlinks, FIFOs, devices — under a name that is deliberately **not** `unsyncable`: that word means the daemon's persistent merged store, and a one-shot report has no store to merge into and no age to carry. Disjoint from the plan's own `SkipUnsupported` rows, so the two can be summed.
- `src/daemon.rs` — the runtime. `run()` reconciles once on startup, then runs a `tokio::select!` loop over filesystem-watch events (`notify`), control commands forwarded from the IPC task (`syncnow`/`shutdown`), a periodic scan interval, a faster events-poll interval (armed only while `events_driven` is on **and** an event source exists — see the cadence invariant below), and shutdown signals. **The control socket is served on its own task** (`serve_control_socket`, one further task per connection) from a continuously-published `ControlShared` snapshot (+`paused`/`syncing`/`auth` atomics and a `reconcile_seq` pass counter), so status/pause/approve answer instantly even while a reconcile blocks the main task; everything a connection is served from is one `ControlPlane` (snapshot, the second SQLite connection for approval writes — both set a busy timeout — the loop channel, and the `list` verb's `BrowseContext`). `List` is the one verb that runs work there: it `spawn_blocking`s a listing on the daemon's **own** client behind `proton::CliGate`, bounded by `BROWSE_GATE_WAIT` (well inside `IPC_IO_TIMEOUT`) so it answers `busy` instead of parking a control connection behind a transfer. Sign-in state (#103) is recorded by `note_auth_evidence`: a completed pass is evidence of `signed-in` (a bootstrap listed, an incremental fetched the delta, a partial landed at least one action), a pass failing on a typed `AuthFailure` is `signed-out`, and any other failure moves nothing. A sign-out is reported through the **existing** `note_event_scope_declined` latch (one line per cause, said once, re-said on change) rather than a second channel, and recovery clears that latch only when it holds `AUTH_DECLINE_REASON`. `Syncnow` is an immediate ack — the sync runs on the main loop, and clients (e.g. `proton-sync syncnow`) poll status until `reconcile_seq` advances past the ack's value with `syncing == false`. `Shutdown` (IPC) exits through the same path as SIGTERM, including cancelling an in-flight proton-drive command. `reconcile_blocking_inner` dispatches between `bootstrap_reconcile` (full-tree snapshot) and `try_incremental_reconcile` (event-driven, O(changes)); the first pass after boot goes through `first_reconcile`, which **warm-starts** (incremental with a forced local scan) when eligible or bootstraps otherwise (see ADR 0004 and the "First pass after boot" invariant). All funnel side effects + incremental checkpoint commits through `execute_plan_and_commit` (consecutive planned downloads execute as chunked multi-file `download_many` invocations, grouped by destination directory). The event cursor advances **only** in the final commit of a fully-successful pass, and only when `events_driven` is on. `events_driven` is now **on by default** (opt out with `--no-events-driven` / `events_driven = false`, which restores the byte-identical snapshot-only path); when the reused CLI session/keyring is unavailable the daemon degrades to snapshots at runtime anyway — on the `scan_interval` cadence, not the event poll, and it says so once (`note_degraded_session_if_needed` feeds the same one-reason-per-cause latch as `resolve_event_scope`'s declines). Holds an advisory lockfile (`LockGuard`) to prevent duplicate instances. **The plan verb (#100/#192/#209) is `Syncnow`-shaped, not `List`-shaped**: `plan_now`/`plan_only_blocking` run a plan-only pass on the main loop (a full local walk plus an O(folders) remote walk must never run on the IPC task), which is what makes the existing `SyncActivity` describe the rehearsal and closes #209's progress line with no second channel. It shares one body with the child `--dry-run` — `build_plan_report`, scan → list → plan — so there is one definition of what a rehearsal is and the token cannot depend on who asked. `PassIntent` carries an apply through `reconcile_blocking_inner` to the **one** comparison in `execute_plan_and_commit`, taken before that method mutates anything about the pass; every exit seals the request (`seal_apply_outcome`), because a booked request nothing answers is a client polling for ever. An apply overtaken by a **pause** is cancelled rather than latched (`discard_queued_apply_for_pause`): `resync`/`reset_index` survive a pause because they describe the next pass, but an apply performs deletions under a minutes-old review. A plan pass claims `syncing` — it must, or `activity` is gated off every status reply — while bumping no `reconcile_seq`, so `ControlShared.plan_pass` tells the two apart and `a_counted_pass_is_running` is what the `syncnow`/`resync` acks ask: a client told "already in progress" waits for `reconcile_seq + 2`, which a queued sync behind a *rehearsal* can never reach alone.
- `src/reconstruct.rs` — **pure** `reconstruct_remote(base ⊕ delta)`: overlays a volume-event delta onto the last-known remote view (the baseline `file_index`) to hand the planner a *complete* remote map without a full walk. Removals (delete / `Updated`+`trashed`) resolve from the baseline; created/updated nodes resolve via an injected `RemoteChangeResolver` (a targeted parent list); anything unresolvable returns `Reconstruction::FallbackToSnapshot` so the daemon re-bootstraps rather than plan against an incomplete map. A **`Created` node that is absent from its parent listing also falls back** — the CLI listing lags the event stream, and dropping it would advance the cursor past a create nothing re-derives (#30); an absent *`Updated`* node is a real move/trash and only drops its stale location. Selective-sync filters apply to the delta.
- `src/proton.rs` — `ProtonClient` trait + `ProtonDriveClient` impl that shells out to the `proton-drive` executable. Parses the tree-shaped remote JSON (nodes may nest under `children`/`entries`/`files`). Extracts SHA-1 from `activeRevision.claimedDigests.sha1` when present. `CommandPolicy` governs per-command timeout and list retry attempts. `download_many` fetches a batch of files in **one** CLI invocation (multiple `path...` args, one shared staging dir, per-file results; the per-invocation timeout scales with batch size, and a failed batch salvages fully-staged files by verifying their claimed SHA-1) — the executor chunks consecutive planned downloads to `download_batch_size` (default 25; `1` restores one-subprocess-per-file). `list_directory` is the non-recursive, single-directory list used for targeted event resolution (the O(1) sibling of the O(folders) BFS); the daemon's `TargetedResolver` memoizes one listing per parent **for the duration of a pass**, so N events in one folder cost one invocation instead of N (#70) — the memo is built and dropped with the pass because resolution reads *current* remote state. **A listing is all-or-nothing.** The CLI wraps `id`/`uid`/`name`/`path` in a `{ok, value}` result, parsed into `WrappedString`'s three states: `Absent` (field missing/null — legitimate, dropped silently as before), `Decoded`, and `Undecodable` (a value that is *present* but carries no usable string). A node whose identity or both locators are `Undecodable` fails the whole listing with a `remote listing is incomplete` error rather than being dropped — a dropped node is indistinguishable from a deleted one and would plan a `LocalDelete` for content that still exists remotely (#59). A degraded node that one locator still places is kept but **inert** (no digest, `downloadable: false` → the planner's `Unsupported` arm). The file-insert branch also rejects the empty relative path, like the directory branch (#72). Per-node error classification lives here too: a download whose CLI stderr says the node is gone returns the typed `NodeNotFound` (`is_node_not_found_error` for callers) instead of a plain message, so the executor can skip that one action — stderr is matched here only, never re-matched by callers. The same rule now carries **auth** (#103): `cli_failure` is the one constructor behind every "the CLI exited non-zero" error, and it types a session-shaped stderr `AuthFailure` (`is_auth_failure_error`), so the daemon's sign-in verdict comes from a downcast rather than from a second needle list in `daemon.rs` or the GUI — two definitions of "signed out" disagree. A `PassFailures` breaker trip inherits it (`abandoned`), because "this is systemic, not per-item" is precisely the expired-session case its own doc names. Concurrency lives here too: **`CliGate` serializes every `proton-drive` child** a client spawns, taken in `run_once` (the single spawn choke point, so a new call site is covered without being told). It is the in-process half of the `paths.rs` user-global lock (#23), needed because the control socket's `list` verb (#99) runs CLI work on the IPC task while the main loop may be mid-pass on the same client — one client is one gate, which is why `Daemon` holds `Arc<C>` and shares that instance rather than building a second. The decision is written at `CliGate`: the gate is held for **one child**, not one pass (so an interactive request lands in the gaps of a 30-minute walk), and the wait is bounded for interactive callers only (`GateWait::AtMost` → typed `CliBusy`, `is_cli_busy_error`) while the daemon's own work waits forever. `browse_directory` is `list_directory` under that bounded wait with one attempt; both share one body (`list_one_directory`), and `list_directory`'s signature and never-fail-the-bootstrap contract are unchanged.
- `src/events.rs` — **remote change detection** via Proton's volume event stream (the O(changes) alternative to the O(folders) `proton.rs` full walk). Pure, transport-agnostic: `parse_volume_events` normalizes the cleartext event delta (`RemoteChange`: created/updated/deleted + `trashed` flag — note a *trash* is `Updated`+`trashed`, not `Deleted`), and `EventsClient<T: HttpTransport, S: SessionProvider>` fetches it, refreshing once on `401`. Detection needs only a session (no decryption); the concrete HTTP transport and session provider (an independent forked session) are injected, so the crate ships no networking dependency. See `docs/adr/0001-*`.
- `src/index.rs` — SQLite schema (`file_index` table + `remote_event_cursor` + `delete_approvals` + `warm_start_state` + `unsyncable_items` + `withheld_deletions` + the history pair `sync_passes`/`sync_events`), local directory scanning, SHA-1 hashing, `ScanOptions` (include/exclude globs + ignore rules + the `ConflictNaming` deciding which files are sidecars — pass the daemon's, not a default, or the scanner and the planner disagree; `should_ignore_path` takes it too), and record CRUD. For event-driven reconcile it also persists the per-scope events cursor (`EventCursor` load/store/clear) and resolves a remote node id back to a local path (`path_for_proton_id`, keyed by the stored `proton_id` = composed `volumeId~nodeId`; bridge an event's raw `LinkID` with `events::node_uid`). `warm_start_state` (single row) persists the across-restart warm-start counter (`load/store_warm_start_count`) that drives `warm_start_full_walk_every`. The `delete_approvals` table stores standing per-item delete approvals keyed by `(path, direction)` and pinned to a `fingerprint`. `withheld_deletions` is its sibling for the *other* half of the lifecycle: the epoch each withheld deletion was **first** held at, keyed and pinned identically, replaced wholesale each gate pass with the previous ages carried forward (a changed fingerprint re-stamps) — `PendingDeletion::detected_epoch_secs` is the age of the *pass*, since the gate stamps `now` on everything it withholds and a pass cannot idle-skip while anything is pending (#225). `purge_subtree_records` is the refusal primitive (#224): it forgets a path and everything under it, component-wise, so the surviving side re-adopts. `unsyncable_items` persists the display-only "cannot be synced" list (byte-exact BLOB key, because the `unrepresentable_path` reason *is* the non-UTF-8 paths a TEXT key mangles — see `normalize_legacy_text_keys`). `scan_local_tree` is the full local stat-walk in its richer form: it returns the entities the walk kept **and** the `UnsyncableEntry`s it dropped (#232), from one walk, so a caller merging the second cannot pair it with a stale first — every other `scan_local_*` entry point is this one with the second half discarded. There is no partial form, which is what lets a caller read a path's absence from that list as evidence. `should_ignore_path` also skips `.proton-sync.toml` at any depth. `reset_index_state` truncates every table the daemon decides from (baseline, cursors, warm-start counter, approvals) in one transaction — it never removes the database *file*, which a running daemon holds open. It also owns **pass and path history** (#213/#229/#238/#230/#190/#191) as *one* schema with six queries over it, not six storage decisions: `sync_passes` is the retained **rollup** (one row per *notable* pass — `started_at`, measured `duration_ms`, `kind` ∈ {`full-sweep`,`warm-start`,`incremental`}, `outcome` ∈ {`clean`,`partial`,`failed`,`interrupted`}, `changed`/`failed` counts, per-direction byte sums) and `sync_events` is the expiring **detail** (one row per side effect that landed: `pass_id`, `path`, nullable `source_path`, `action`, nullable `bytes`). There is no `direction` column — direction is `SyncAction::transfer_direction`, a property of the action. `last_transfer` is the point query over that detail (#233): the newest event row for a path whose action has a `SyncAction::transfer_direction`, scanned newest-first and stopped at the first hit. It is the **only** remote-side timestamp the engine has — `file_index` holds none, because `proton.rs` parses `activeRevision` for `claimedDigests.sha1` and nothing else, so a new column would be a second copy of a table that already answers it. `None` means the engine has no record of moving that path's bytes: nothing ever transferred, it aged out of retention, it was adopted (`AutoLink` moves no bytes), or it has moved since. A **byte total always comes from the rollup** (`byte_totals_since`), never by summing event rows, so it outlives the detail and there is exactly one way to get the number — and it is a different question from `PlanSummary::upload_bytes`, which is what a plan *intends* to move rather than what landed; `sync_events.bytes` is per-row display data, and a *path-filtered* `file_events` therefore returns `totals: None` rather than a window-wide figure that reads as one file's. Retention (`HistoryRetention`, applied by `prune_history` only on a pass that wrote rows) bounds each table by age **and** rows — passes 2000/1yr, events 20k/90d — and **exempts the newest full sweep from both pass bounds**, because every non-clean pass is notable and a chronically failing daemon would otherwise evict it within hours (written `id IS NOT (SELECT MAX(id) …)`, not `<>`: a NULL subquery would void the whole predicate).
- `src/session.rs` — concrete impls of the `events` seams for the **current CLI-session-reuse** approach: `CliKeyringSession` (a `SessionProvider` that reuses the logged-in `proton-drive` CLI's session from the OS keyring via `secret-tool`; `refresh` re-reads the keyring rather than owning a token refresh) and `CurlHttpTransport` (a dependency-free `HttpTransport` shelling `curl`). Independent (browser-forked) auth is deferred by decision — see `docs/adr/0001-*`.
- `src/config.rs` — layered config resolution. Precedence: **explicit CLI flag > TOML file value > XDG default**. `resolve_runtime_config` merges `DaemonConfigInput` (from clap) with `FileConfig` (from `--config`), validates roots/globs, and resolves `dry_run` (`--no-dry-run` beats `--dry-run` beats file `dry_run`). Every local-filesystem path option expands a leading `~` to `$HOME` (`expand_tilde`; `~user` is rejected) — the daemon runs shell-less, and a literal `~` root diverges from the `proton-drive` CLI, which does expand it. Also resolves the daemon-wide **delete-approval** defaults (`[delete_approval] remote/local`, both default `true`; `--no-delete-approval` forces both off) that seed `src/dirconfig.rs` — plus `deletion_policy`, the *same* guard as one named setting (`ask_every_time` / `only_permanent` / `never` / `only_recoverable`, #194). **The two spellings are mutually exclusive**: a file setting both is a startup error naming both keys, because one setting written two ways has no defensible precedence — and that rule is what lets a round-trip writer know which key it may rewrite (an existing `[delete_approval]` file keeps working and is never rewritten into the new spelling). Owns three further keys the Settings screen's Advanced tab needs (#237): `log_level` (`--log-level` > `RUST_LOG` > file > `info` — a **configured** value is validated and fatal while an unusable `RUST_LOG` falls through, because `EnvFilter` reads a bare `inf0` as the target directive `inf0=trace` and silences the daemon while looking accepted), `conflict_suffix`, and `socket_path` (which was always a key — #237's premise that it was not is stale). `validate_file_config_text` is the **one** place the post-parse rules live (relative `socket_path` after `~` expansion, `log_level`, `conflict_suffix`, both-spellings, positive integers, globs); `gui-core`'s config writer calls it rather than re-deriving them, and the **warm-start** config (`WarmStartConfig`: `warm_start`/`--no-warm-start` default on, `warm_start_full_walk_every` default 30, `warm_start_max_cursor_age_secs` default 7 days — both `0` = disabled sentinels — plus the one-shot `--full-walk`). See ADR 0004. **Folder pairs (#102 phase 1, ADR 0005).** A config file's per-pair half may be written two ways: `[[pair]]` tables, each with a required `name`, or — for a file with **no** `[[pair]]` — the top-level keys, which are then *one implicit pair called `default`* (`DEFAULT_PAIR_NAME`). That implicit reading is **permanent, not a migration step**: every config written before multi-pair resolves byte-identically, unrewritten, and no user action is asked for. Both spellings at once is a startup error naming the offending keys — the same rule as `deletion_policy` + `[delete_approval]`, for the same reason. Which keys are which is not a table in a doc but a value the code reads: `ConfigKey::scope` is an **exhaustive match with no `_` arm** returning `KeyScope::{Daemon,Pair}`, so a new variant cannot be added without answering the question, and `every_file_config_key_is_classified_exactly_once` compares `ConfigKey::ALL` against the keys a fully-populated `FileConfig` serializes to (an exhaustive struct literal, so a new *field* is a build failure until it has a variant) — both directions, because either gap is silent. Rule 1 *reads* that classification (`FileConfig::key_present`, also exhaustive), which is what keeps it load-bearing rather than decorative. `socket_path` and `log_level` are daemon-wide by nature; `proton_cli`/`proton_timeout_secs`/`proton_list_attempts` are daemon-wide **by force** — they construct the one shared `ProtonDriveClient`, and one client is one `CliGate` (#23), so N clients would be N gates (guard `the_shared_proton_client_keys_cannot_be_per_pair`); everything else describes a tree and is per-pair. `resolve_pairs` is the one definition of the pair shape, called by the daemon *and* by `validate_file_config_text`, and it carries only the rules no flag can change the answer to: both-spellings, `name` (required, `[A-Za-z0-9._-]{1,64}`, unique **case-insensitively** — #298's rule one layer up), an explicit `pair = []` refused rather than read as the default pair, and **roots that may not collide or nest**. Nesting has a concrete cause, not a principle: `index::is_sync_state_path` matches only the *first* path component, so a pair inside another pair's root would have its `.sync` index, lockfile and sidecars uploaded as the outer pair's ordinary files; `db_path`/`lockfile_path` are checked as *effective* paths through the shared `effective_state_path`, before any lock is taken, because `flock` treats two descriptors on one inode as independent and a shared lockfile would otherwise surface as a spurious "already running". Comparison is **lexical** (a file must be checkable without touching the filesystem), and remote roots compare with the leading `/` stripped since `/Drive/X` and `Drive/X` name one location. Value-level per-pair rules run per pair in `validate_pair_file_values` — deliberately *not* in `resolve_pairs`, since a flag can still mask each of them (`--local-root /x` over a file's `local_root = ""` starts today), and the merged value is caught where it always was. **More than one pair is refused** by `refuse_unsupported_pair_count`, on *both* readers' paths (`ConfigDoc::save` must never write a config the daemon would refuse to start on) and *after* the structure rules, so a genuinely broken multi-pair file says what is wrong with it rather than being masked by "not yet supported"; phase 4 lifts that one function. Flags keep meaning "the single pair". `resolve_control_socket_path` is the **client** half of the same precedence (`--socket-path` > file `socket_path` > XDG default, sharing `require_absolute_socket_path`), so `proton-sync --config` finds a file-configured socket instead of every invocation repeating `--socket-path` (#63).
- `src/dirconfig.rs` — **hierarchical, per-directory config** (the `.gitignore`-style layer). A `.proton-sync.toml` in any directory applies to it and everything beneath it; `DirectoryConfigResolver::resolve` walks the entity's ancestor directories root-first over the daemon-wide default (nearest wins; unset options inherit). Machine-local: ignored by scan/plan/watch (`index::should_ignore_path`) and never synced. A file may use either delete-approval spelling (`[delete_approval]` or `deletion_policy`) but **not both** — as in the daemon config, except that a directory file cannot stop the daemon, so an ambiguous one takes the malformed path. Malformed/unreadable/ambiguous files fail safe (guard stays on). All-`Option` `DirectorySettings` → resolved `EffectiveSettings`; extend by adding an `Option` field + resolved counterpart. See `docs/adr/0002-*`.
- `src/ipc.rs` — JSON-line request/response protocol over the Unix socket; binds with mode `0600` **inside a freshly created 0700 staging directory and renames the socket into place**, because `bind` creates it `0777 & ~umask` and a chmod afterwards leaves a window in which any local user can issue a command (#62; a process-wide `umask` flip would race the runtime's other threads). The staged path is longer than the published one, so `bind_listener` measures it against the platform's own `sockaddr_un` and refuses a socket that fits only unstaged, naming staging as the cause; cleanup is `remove_dir`, never `remove_dir_all`, so it can only ever remove the empty directory it created. Every wire `PathBuf` serializes through `lossy_path` (`wire_path` = `to_string_lossy`, verbatim back): `impl Serialize for Path` *errors* on a non-UTF-8 path, so one withheld deletion for such a file used to fail **every** reply — status/pause/approve alike — and lock the control plane out (#61). `approve`/`deny` selectors are therefore matched in the wire form too (as `Path`s, so a trailing slash still matches), and a selector matching more than one pending deletion approves nothing. Every reply that renders a *selector* back is bounded by `SELECTOR_DISPLAY_LIMIT` through the one `daemon::truncate_for_display` body that also backs `truncate_error` (#313) — a request may carry 64 KiB and nothing narrower bounds `argument`. **Display only**: the matching above still compares the full wire form, since truncating before it would make two different paths compare equal. `ControlResponse` carries `syncing` + `reconcile_seq` + `activity` + `failed_items`/`failed_item_count` (all `#[serde(default)]` for wire compat); `ControlCommand::Shutdown` asks the daemon to exit gracefully (used by the GUI's restart-daemon flow and `proton-sync stop`); `ControlCommand::Resync` (`proton-sync resync`) latches a full-tree walk for the next pass (self-heal drift; overrides the warm start); `ControlCommand::ResetIndex` (wire `"reset_index"`, `proton-sync reset-index --yes`) latches a discard of everything the daemon has learned — the main loop truncates *before* it loads the baseline, then rebuilds by bootstrap adoption, and the latch is **re-set if the truncation fails** so a confirmed request is never lost. The `--yes` gate is client-side because the wire carries no confirmation field. `ControlCommand::Keep` (`proton-sync keep`) **refuses** a withheld deletion — distinct from `Deny`, which only revokes an approval: it purges the deletion's baseline record *and its subtree* (a directory delete is planned recursively), so the bootstrap arm adopts the survivor back onto the other side, and it latches `force_full_walk` because an incremental pass's remote map IS the baseline (`reconstruct_remote(base ⊕ delta)`) — a purged `direction: remote` survivor would otherwise never be downloaded. `ControlRequest::direction` is read only by `Approve`, and only when nothing pending matches the selector: the pre-pass approval the Plan screen's typed-`DELETE` gate needs (#227), pinned to a fingerprint derived from the index and refused for a path with no record. `ControlCommand::Activity` (`proton-sync activity [PATH]`) is the per-file history query (#230/#190) over `index::file_events`; the pass-level history + today's byte totals (#229/#238/#191) instead ride on every `Status` reply as `ControlResponse.history` (`PassHistory`), refreshed once per pass into `ControlShared`'s snapshot so a 2s GUI poll never touches SQLite. `StatusHistoryEntry` deliberately gained none of it: it records **every** attempt, idle ones included, at a 20-entry cap — about ten minutes of wall clock at the events-poll cadence — so it can answer neither "the last 20 passes" nor "the last full sweep, 2 days ago". `SyncActivity` is the live "what is the daemon doing right now" surface, and it is **one record answering three questions** (#211/#243/#98) rather than three fields that would drift: phase + current path + action i/N, the **transfer queue** (`transfers`, a bounded window — every row in flight, then the next planned ones as `queued`, capped at `TRANSFERS_REPORTED`; `transfers_remaining` is the untruncated figure `+n more` is sized from, and it is the field that tells "not executing / older daemon" (`None`) from "nothing left" (`Some(0)`) — an empty list alone means neither, and the window is republished on *every* action so a delete between two uploads cannot blank it), and the `pass` block, which is the **pass** as a unit and survives every phase change unlike `since_epoch_secs`, which `begin_activity` resets per phase (#213). The singular `transfer` survives only as a **derived** mirror of the first active row, written by `derive_legacy_transfer` at publish time and by nothing else. The pass block carries the per-direction progress — `uploaded_files`/`downloaded_files` (#243's counts) and `uploaded_bytes`/`downloaded_bytes` (#98's bytes, named to match `index::ByteTotals`) — because a counter on `SyncActivity` itself would reset once per action; all four fold in `PassLog::note_committed`, the fold that already builds the history rollup, off the same `(direction, Some(bytes))` arms as the byte sums, so a count and a byte total can never describe different side effects. **A per-file percentage stays unreachable by construction** and says so at `TransferActivity`: an upload has `bytes_total` and no progress, a download has progress and no total, and `totalStorageSize` is not a file size (0 on 873 of 5424 healthy files): the daemon core updates it from inside the blocking reconcile (phases, per-action), the concrete client feeds it via `proton::ProgressSink` (per-folder walk progress, download staging dir), and `ControlShared` samples a download's bytes-so-far from the staging directory at status-reply time. Display-only — nothing in it participates in sync decisions. `ControlResponse.unsyncable` is the same kind of display-only surface for entities that cannot be synced at all (#295), rendered by `proton-sync status` under `can't sync`. `ControlCommand::List` (`proton-sync list [PATH]`, #99) is the read-only remote browser: one non-recursive listing of `argument`, **the only verb that runs work on the IPC task** (see `proton::CliGate`) and the only one whose selector may legitimately be empty — the root is a value there, so it takes plain `validate_relative_path`, not the non-empty form a side effect demands. The selector has **two frames** (#323): relative to `remote_root` by default, or an **absolute** Proton Drive location when it starts with `/`, validated by `validate_absolute_remote_path` — the third rung of the path-safety ladder, for a question about a folder that is outside every root *by definition* (pricing a candidate before a pair is configured, `gui_core::folder_probe`). Absolute selectors were previously refused by the relative guard, so it is a pure extension, and **the reply answers in the frame the request used** (relative entries stay `remote_root`-relative, absolute ones come back absolute), which is what lets a client feed any entry straight back as its next selector. A **subtree is therefore walked by the client, one request per directory, and that is the design**: this verb may sit on the IPC task only because it is one CLI child under a bounded gate wait, while the other daemon-side shape (`Plan`'s ack-plus-latch on the main loop) queues behind a pass that can run half an hour — and one child per request lands in the *gaps* of a live pass, the gate being held for one child rather than one pass. It has no reserved word (`literal_path` is meaningless; a folder named `all` lists), and it answers a typed `ListingOutcome` — `Listed`/`Busy`/`Failed`, internally tagged with `#[serde(other)] Unknown` — rather than prose, because a client telling "retry" from "gone" by matching a sentence is the bug #103 removes. Entries are capped by the daemon (`LIST_ENTRIES_*`), remote ground truth only (no selective-sync filter, no index read), and the CLI's own wrapper node for the requested directory is dropped. `ControlResponse.auth` is #103's answer: an `AuthState` (`unknown`/`signed-in`/`signed-out`, hand-serialized so an unknown token degrades) living in its own `ControlShared` atomic rather than the core-published snapshot, because it has **two** writers — the pass outcome and the `list` verb, which is where an expired session surfaces first. Only success moves it to `signed-in` and only a *classified* failure to `signed-out`; an unclassified failure moves it nowhere, since a fall-through arm reading "signed in and fine" is #246's shape. The **plan family** is three verbs (#100/#192/#209/#317): `ControlCommand::Plan` (`proton-sync plan`) schedules a plan-only pass and acks immediately — `Syncnow`-shaped, with `syncnow`'s pause semantics — `ControlCommand::PlanResult` (wire `"plan_result"`) reads the answer *and the last apply's verdict* straight from the published slot like `status`, and `ControlCommand::Apply` (`proton-sync apply <TOKEN>`) executes a reviewed plan. Both answer typed outcomes on the `ListingOutcome` pattern — `PlanOutcome` (`scheduled`/`computing`/`computed`/`failed`/`paused`/`absent`) and `ApplyOutcome` (`scheduled`/`stale`/`paused`/`applied`/`diverged`/`failed`), each `#[serde(other)]`-terminated. **`plan_seq`/`apply_seq` are their own counters and a plan pass deliberately does not bump `reconcile_seq`**: bumping it would satisfy a concurrent `syncnow` watcher's target and make it report a sync that never ran. `ReviewedPlan`'s `actions` are a bounded window (`PLAN_ACTIONS_*`) built **destructive-first**, so a deletion can never be truncated out of a reply a user decides from — safe only because an apply names the *token*, never the rows. `ControlRequest::skip_destructive` is #192's filtered apply, read by `Apply` alone, and it **overrides a standing approval**: the user asked for this run without them, which is a different question from whether the deletion may ever apply. `PLAN_PASS_KIND` (`"plan"`) is the open `PassProgress::kind` token a plan pass publishes so a screen can tell its own rehearsal's `files_scanned` from a sync's. The `proton-sync` CLI prints human-readable, git-style output by default — `--json` restores the raw response for scripts and tests; `list`, `plan` and `apply` also exit non-zero when the answer is not a success, so `busy` is never read as an empty folder and a divergence is never read as an apply.
- `src/paths.rs` — default state paths. The SQLite index (plus its status/metrics sidecars) and the per-root instance lockfile default to the per-root `<local_root>/.sync` state directory, which the engine ignores everywhere (`index::should_ignore_path` → `is_sync_state_path`; only a *top-level* `.sync` is treated as state). The control socket stays in `$XDG_RUNTIME_DIR` — the XDG home for sockets — since it is a session-scoped runtime endpoint (not persistent state), must stay short for the `sun_path` limit, and must be locatable by the control CLI without knowing the sync root. **Two-tier locking:** the per-root lockfile stops two daemons on the *same* root, while a **user-global** single-instance lock (`default_global_lock_path`, keyed on `$XDG_STATE_HOME`, *not* the per-session runtime dir) stops a second daemon anywhere for this user — required because every daemon shells the same `proton-drive` CLI, whose shared SQLite cache/session store is not concurrency-safe (`SQLITE_BUSY`; #23). That is the *across-daemons* half; the in-process half is `proton::CliGate`, needed once the control socket started running CLI work of its own (#99). Both locks use `daemon.rs`'s `LockGuard`, which **never unlinks** the lockfile: `flock` binds to the inode, so removing the path on drop would let a later start lock a *fresh* inode independently of a daemon still holding the old one (#13). Drop releases the flock and leaves an empty file; `acquire` reuses it, so a leftover lockfile never blocks a restart and never means a daemon is running. An XDG value is honoured **only when it is absolute** (`absolute_dir`, #286; `is_absolute` subsumes the old emptiness check and catches an unexpanded `~`) — a relative one resolves per-process against cwd, which makes the user-global lock one lock per launch directory instead of one per user, and splits the socket between daemon and client. The GUI keeps its own `absolute_dir` for the config path it owns, but no longer computes the socket path at all — `gui-core` delegates to `default_socket_path` here (#277), so this rule reaches the socket once instead of twice. When `XDG_RUNTIME_DIR` (socket) or `XDG_STATE_HOME`/`HOME` (global lock) are unset or non-absolute, both fall back to a uid-suffixed subdirectory of the shared temp dir, and that fallback **fails closed** (#74): `default_socket_path` and `default_global_lock_path` return `AppResult<PathBuf>` and refuse a path that is not a real directory owned by the current euid at mode 0700, rather than binding the control socket in attacker-plantable space. A caller-supplied `--socket-path` skips that resolution entirely (the defaults stay lazy).
- `src/lib.rs` — `AppResult<T>` alias, `boxed_error`, `wire_path` + the `lossy_path` serde module (the **one** definition of how a `PathBuf` crosses any wire this engine publishes — the control protocol #61 and the dry-run report #300 — lossy out, verbatim back, byte-identical for a UTF-8 path; `ipc::wire_path` is a re-export), and `validate_relative_path` (the shared path-safety guard) plus `validate_relative_path_non_empty`. The plain form maps `""`/`.` to `Some("")` on purpose (the listing's root wrapper node and `CreateRemoteDirectory` both need the root as a value); anything that turns a path into a *side effect* — `daemon::safe_local_path` / `safe_remote_path` — must use the non-empty form, since joining `""` onto a root promotes a per-entry action into a whole-root one (#72). `validate_absolute_remote_path` is the **third** rung (#323) and not a variant of either: the path is joined onto nothing, it *is* the location, so what it guards is normalization (`..` refused rather than resolved, `.` stripped, a *relative* path refused) rather than root escape. It may name anywhere in this user's Drive — granting nothing, since the socket is `0600` and the daemon shells the CLI the user can run by hand; routing the walk through the daemon is about `CliGate` (#23), not privilege — and, like the plain relative form, it accepts the root (`/`) because a listing is a read. A future *side-effecting* absolute caller needs its own non-root form.

### Invariants to preserve

- **Commit-after-side-effects, checkpointed.** An index write never precedes its side effect. Mutations commit in per-action **checkpoint transactions** (`commit_checkpoint` in `src/daemon.rs`): every side-effecting action — and every batched download chunk — commits its own mutations immediately after succeeding, while index-only mutations (`AutoLink`/`Purge`) accumulate into the next checkpoint or the final commit (so an adoption-heavy pass isn't thousands of fsyncs). A mid-plan failure keeps completed work durable; the failed action itself is never recorded and replans next pass, while its **successors still execute** (#136 — see the partial-pass invariant below). The **event cursor** advances only in the final commit of a fully-successful pass — never in a checkpoint — and is only ever *read* before the work it claims to cover: a bootstrap captures `latest_cursor` **before** the full-tree walk (`capture_pre_snapshot_cursor`), and when any lookup fails while prior state may exist — the cursor read, or the volume itself, which falls back to a stored cursor row that may be unreadable rather than absent — it persists **no** cursor — never clearing the stored one either, an older cursor being the safe replay point — rather than anchoring after the walk, which would assert that everything changed *during* a 30-minute walk had been applied (#294). A **first-ever bootstrap** has nothing stored to name a volume with — empty baseline, no cursor row — so it names one from the remote instead: a single targeted `list_directory` of the remote root (`volume_id_from_remote_root`, the O(1) call the event resolver already uses, whose nodes carry the composed `volumeId~nodeId`), and then anchors pre-walk like every other pass (#303). That listing is confined to the `Unnameable` arm — any baseline composed id or stored cursor short-circuits it, so it is not a per-bootstrap cost — is skipped entirely when nothing could use its answer (events off, or a degraded session that already pays a snapshot per `scan_interval` tick), and may **never fail a first sync**: an errored or volume-less listing degrades to the pre-#303 post-walk anchor (`PreSnapshotCursor::VolumeUnknown`), whose commonest cause is an *empty* remote root — the listing drops the root's own wrapper node — where a walk that listed no node can have missed no change to one. Once the volume **is** named, a failed cursor read persists nothing rather than retrying after the walk: a post-walk retry there would re-open the mid-walk window through a side door. (Guards: `a_first_ever_bootstrap_anchors_its_cursor_before_the_walk`, `a_failed_remote_root_listing_degrades_to_the_post_walk_anchor`, `a_first_ever_bootstrap_whose_cursor_read_fails_persists_no_cursor`, `a_bootstrap_that_cannot_use_a_cursor_never_lists_the_remote_root`, `a_bootstrap_that_can_already_name_its_volume_lists_nothing_extra`.) Approval consumptions commit in the same checkpoint as their delete's purge. Do not move index writes ahead of their side effect. (See `docs/adr/0003-*`.)
- **Path-safety at boundaries.** Every relative path from an external source (remote listing, local scan, conflict target) must pass `validate_relative_path` / `safe_local_path` before being joined onto a root. Absolute, `..`, and prefix components are rejected to prevent root escape. When adding a boundary that accepts external paths, guard it and add a test there. The guard is a **ladder, and each rung buys less than it looks**. (1) `validate_relative_path` is purely lexical, and deliberately returns `Some("")` for `""`/`.` — the root is a legitimate *value* there (the listing's root wrapper node; `CreateRemoteDirectory`'s empty-path arm). Anything that resolves a path into a **side effect** must therefore use `validate_relative_path_non_empty`, which is what `safe_local_path`/`safe_remote_path` do: joined onto a root, `""` silently promotes a per-entry download or delete into a whole-root one (#72). (2) Clearing `safe_local_path` still does not make a write to a *predictable* name safe (a conflict sidecar, a download destination): its `local_write_escapes_root` check canonicalizes the deepest **existing** ancestor, and a dangling symlink has none — so a broken link planted at the target passes the guard, and `Path::exists()` reports it absent while `fs::copy`/`fs::write` follow it. Such a write must refuse to follow: `create_new` (`O_EXCL`, one syscall, so no check/write race — `copy_into_new_file`) or land via `fs::rename` from a staging dir (what `proton.rs` downloads do), and any presence check guarding it uses `fs::symlink_metadata`, never `exists()`.
- **Non-destructive on unknown digests.** When a remote file exists but exposes no usable SHA-1, `remote_file_delta` returns `FileDelta::Unknown` and the planner avoids destructive actions (see the `Unknown` match arms in `plan_ongoing_action`). Preserve this conservatism.
- **Selective-sync filters apply everywhere.** Include/exclude globs (`ScanOptions`) filter local files, remote files, *and* base-index records before planning, so excluded records are never purged as "missing." Conflict sidecars and the index DB itself are always ignored.
- **First pass after boot always full-scans the *local* tree (warm start or bootstrap).** A fresh process has an empty `pending_changes` (`notify` does not replay pre-existing files), so the first reconcile must full-scan the local tree or it would idle-skip a file edited while the daemon was down. `is_first_reconcile` gates a dedicated `first_reconcile` branch that either **warm-starts** (event-driven reconcile with a *forced* local scan — `try_incremental_reconcile(force_local_scan = true)` — replaying the remote from the persisted cursor instead of the O(folders) walk) or **bootstraps** (the full-tree snapshot). Both full-scan the local tree; only the *remote* walk differs. `is_first_reconcile` clears **only on success**, so a failed first pass retries as a first pass rather than dropping into the steady-state idle fast-path (which skips the local scan). See ADR 0004. Warm-start eligibility: feature on + event source + a resolvable event scope (`resolve_event_scope`: the volume from a baseline composed `proton_id`, else from the sole stored cursor row whose `scope_id` *is* the volume — #32 — plus that cursor; a decline is logged once with its reason) + cursor fresh (`now - updated_at ≤ warm_start_max_cursor_age`, default 7 days) + the across-restart floor not due (`warm_starts_since_full_walk < warm_start_full_walk_every`, default 30, persisted in `warm_start_state`). Any doubt falls back to a bootstrap. Force a full walk with `proton-syncd --full-walk` (sticky across a failed first pass) or the `resync` IPC command (`proton-sync resync`, a `ControlShared.force_full_walk` latch consumed by the next pass). `reacquire_event_source_if_needed` still forces a **mid-life** reacquisition pass to full-walk by reseeding the in-run resync floor — but **not** on the first pass (there `first_reconcile`'s cursor-age gate already covers the stale-cursor concern, and reseeding would risk overflowing the counter when a warm start increments it). (Guards: `first_reconcile_warm_starts_on_a_fresh_cursor`, `first_reconcile_bootstraps_when_the_cursor_is_stale`, `a_failed_first_pass_retries_as_a_first_pass_and_still_scans_locally`, `the_warm_start_floor_forces_a_bootstrap_and_resets_the_counter`, `event_source_is_reacquired_when_the_keyring_becomes_readable`.)
- **Periodic safety resync is opt-in (off by default).** `events_full_scan_every` **defaults to `0`, which disables the periodic full-tree resync entirely**: after the first pass the daemon stays purely event-driven until it is restarted or the event stream forces a fallback (no cursor / no volume / fetch error / server refresh / unresolvable node / an incomplete listing, i.e. one holding a node the CLI could not decode / a `Created` node whose parent listing still lags). `effective_full_scan_every` maps the `0` sentinel to `u64::MAX` so the pass counter never reaches it. Set a positive `N` (flag `--events-full-scan-every N` or file `events_full_scan_every = N`) to reinstate a self-healing full walk every `N` *in-run* incremental passes. This is distinct from `warm_start_full_walk_every`, which forces a full walk every N *warm starts across reboots* (persisted counter): `events_full_scan_every` heals a long-running process, `warm_start_full_walk_every` heals a frequently-restarted one. (Guard: `disabled_periodic_resync_never_full_scans_after_the_startup_snapshot`.)
- **`scan_interval` is not a snapshot cadence in events mode; a degraded session is.** With events on and a live event source, a `scan_interval` tick is just another incremental (usually idle) pass — identical to an `EVENTS_POLL_INTERVAL` tick. It deliberately does **not** seed the resync floor to force a snapshot (#52): that would reinstate the periodic full walk the invariant above removes. The exception is a **degraded session** (`events_driven` on but no event source — locked keyring, headless host, no CLI session): every pass is then a full-tree snapshot, so the fast events-poll arm is gated on `event_source.is_some()` and those snapshots — plus the per-pass `reacquire_event_source_if_needed` retry — ride `scan_interval` instead of the 30s poll (#50). **"Event-driven detection unavailable" is one message family with one reason per cause**, because "keeps doing full syncs" is told apart only by the log line: `note_degraded_session_if_needed` reports the *no session* cause (naming both intervals) through the same `event_scope_declined` latch `resolve_event_scope` uses for *no volume* / *no cursor* — so exactly one of them speaks per pass, each once, and a cause change re-reports. A pass that started streaming and then gave up logs the separate per-pass "event-driven pass fell back to a full-tree snapshot" line instead. (Guards: `a_degraded_session_does_not_full_walk_on_the_events_poll_cadence`, `a_degraded_session_still_reconciles_on_the_scan_interval`, `a_degraded_session_reports_that_cause_once_without_masking_the_scope_causes`.)
- **A local change the watcher cannot queue must still force a scan.** The events-mode idle fast-path skips the local stat-walk when the event delta, `pending_changes` and `pending_deletions` are all empty, so anything the watcher drops is invisible to that pass — and with the periodic resync off by default and restarts warm-starting from the cursor, nothing later re-derives it. Two watcher paths therefore feed the gate (#51): a **directory** `Create`/`Modify` is queued in `pending_changes` (filtered through `scan_options.allows_relative_directory`; never `mark_modified`, a directory has no file-content record semantics; the empty relative path is the watched root, not an entity) because an empty `mkdir` emits no file event at all; and a watcher **error** (an inotify queue overflow means events were *lost*) sets `force_local_rescan`, which forces `force_local_scan` on the next incremental pass and clears only when a pass succeeds. (Guards: `an_empty_directory_create_is_mirrored_by_the_next_event_driven_pass`, `a_watcher_error_forces_the_next_event_driven_pass_to_scan_locally`.)
- **A wire path is a rendering, never a selector; and an unsyncable entity is named, not counted.** Every `PathBuf` that leaves the process as JSON goes through `lossy_path` (`ControlResponse`, `PlannedAction`, `DryRunReport`), because `impl Serialize for Path` *errors* on a non-UTF-8 path and `serde_json` is all-or-nothing: one such path used to fail the whole control reply (#61) or the whole dry-run report (#300, certain since #270 guaranteed such a path is planned rather than dropped). Two paths differing only in invalid bytes collapse to one string, so a command that turns a selector into a destructive side effect matches in wire form and **refuses an ambiguous selector** (`apply_approval_command`) rather than resolving it arbitrarily; the same rule binds any future command that authorises a plan row by path (#227). The other half: `SkipUnsupported` is correct and conservative, but a bare `skipped_unsupported` counter is not a report. The daemon keeps a standing `unsyncable` list (`record_unsyncable`), warns once per path per **run** (not per pass — a pass-rate log on a permanent condition is noise), publishes it on the status payload + metrics sidecar, and persists it. It is **merged, not recomputed**, and it has **two producers** whose evidence prunes differently (#232). The plan's `SkipUnsupported` rows are one; the local stat-walk's *drops* — a socket, symlink, FIFO or device node, which `visit_directory` reports rather than skipping silently — are the other, and they never reach the planner at all. A skip is never written to `file_index`, so it is absent from the baseline `reconstruct_remote` overlays and an incremental pass simply does not plan it — which is why a **remote** reason (and an unknown one, whose producer cannot be placed) is dropped by absence only on a full-tree snapshot. A **local** reason prunes on every pass that reaches the executor: both `bootstrap_reconcile` and `try_incremental_reconcile` run the whole local walk before planning and the events-mode idle fast-path returns before either, so that walk's silence *is* evidence — and without the split a deleted socket would sit on the list until a full sweep, which with the periodic resync off by default and restarts warm-starting is close to never. `UnsyncableReason::origin` is the one definition of which is which (`daemon::pass_proves_absence_of`), exhaustive by variant so a new reason must answer the question. Any pass may add; a path this pass planned a real action for or onto is dropped **unless this pass also observed it as unsyncable**, which is what a socket replacing a synced file looks like — the planner sees the file gone and plans a delete while the scan sees the socket, and the path is both. Reporting is one **local kind** per token (`local_symlink`/`local_socket`/`local_fifo`/`local_device`/`local_special_file`), added as tokens and not as variants a client must know: an older build parses `local_socket` to `Other` and prints it. The scan's own split matters as much — a path an exclude glob, an include filter, `.proton-sync.toml`, a sidecar or the `.sync` directory hides is **excluded, not unsyncable**, so the rule test runs first and the user's own skip rules never appear under "cannot be synced". (Guards: the `an_unsyncable_entity_is_named_persisted_and_outlives_*` / `a_path_that_becomes_syncable_*` / `*_once_per_run_not_once_per_pass` / `a_local_reason_prunes_on_any_pass_while_a_remote_one_waits_for_a_full_sweep` / `a_deleted_socket_leaves_the_list_on_the_next_pass_that_plans_anything` / `a_path_the_scan_still_reports_survives_a_delete_planned_for_the_file_it_replaced` daemon tests, `a_socket_symlink_or_fifo_is_named_instead_of_silently_dropped` and `a_socket_an_exclude_rule_hides_is_excluded_not_unsyncable` in `index`, `a_non_utf8_path_anywhere_still_serializes_the_whole_dry_run_report`, `dry_run_cli_reports_a_plan_containing_a_non_utf8_filename`.)
- **Delete-approval guard is execution-time, and holds the cursor when withholding.** The gate lives in `execute_plan_and_commit` (`decide_delete_gate`), **not** the pure planner: it withholds `RemoteDelete`/`LocalDelete` (never `Purge`) whose direction is guarded at that path (per `dirconfig`) unless a matching approval exists. A withheld action skips **both** its side effect and its index mutation (re-plans next pass). If any action is withheld this pass, `cursor_update` is forced to `None` so a withheld `LocalDelete` keeps re-deriving from ground truth (else `reconstruct_remote` would drop it once the cursor passed its event). Approvals are consumed in the same checkpoint transaction as their delete's index purge — an executed delete's approval is consumed even when a later action fails the pass. The gate also *reports*: every withheld item carries its first-seen epoch (from `withheld_deletions`) and, for a directory, the subtree file count and byte total from the already-filtered baseline. (Guards: the `guard_*`/`a_withheld_local_delete_holds_the_event_cursor` daemon tests, plus `a_withheld_deletion_keeps_the_age_it_was_first_seen_at_across_restarts`, `keeping_a_folder_purges_its_whole_subtree` and `a_kept_remote_direction_deletion_comes_back_only_on_a_full_walk`.)
- **A failed item does not fail the pass, and partial failure is its own state.** `execute_plan_and_commit` continues past an action whose side effect failed (#136): the action's queued mutations are rolled back (never recorded), it is collected into `PassFailures` and reported as a bounded `failed_items` list plus an untruncated `failed_item_count`, and the rest of the plan executes — one poisoned file can no longer starve every action ordered after it, forever. The pass returns `PassOutcome::Partial { failed }`, a **third** outcome that is enumerated everywhere a pass outcome is branched on (`reconcile_blocking`'s message, the `proton-sync` headline/history/`syncnow`, the `#[must_use]` on `PassOutcome` that forces every test to say which it expects) rather than falling through an existing arm (#246). A partial pass sets `last_error` to a one-line summary, so every older surface still reports it as a problem, but it does **not** set `last_sync` / `last_successful_sync_summary` and does **not** clear `is_first_reconcile` / `force_local_rescan`. Two things keep the work from being lost: the **event cursor is held** (the same decision as a withheld delete and a vanished node — one policy, three causes), and every failed path is **re-queued into `pending_changes`** after the pass clears it, because a failed *upload* has no remote event and the held cursor alone would let the next event-driven pass take the idle fast-path. Two exceptions stay pass-fatal: a shutdown (`cancel_flag`, or every remaining action becomes a doomed spawn-and-kill) and `CONSECUTIVE_FAILURE_LIMIT` consecutive failures in a pass where **nothing** has succeeded (a dead CLI or an expired session is not a per-item problem; gated on zero successes so it can never starve anything). (Guards: `a_failing_action_no_longer_starves_the_actions_ordered_after_it`, `a_partial_pass_re_queues_its_failed_paths_so_the_next_event_driven_pass_retries_them`, `a_systemically_failing_pass_is_abandoned_rather_than_ground_through`, `a_shutdown_stops_the_pass_instead_of_failing_every_remaining_action`, `mid_plan_failure_leaves_index_and_cursor_unadvanced`.)
- **A plan-only pass observes and consumes NOTHING.** It is the most dangerous thing in the plan family because it runs the same scan and the same walk as a real pass, so anything it consumed would be spent *without* the side effects that justify spending it — and the real pass would then be unable to re-derive what the rehearsal rehearsed. One rule, one reason, and it is structural rather than a list each branch remembers: a plan pass does not go through `reconcile_blocking` at all (`Daemon::plan_now` → `plan_only_blocking`), and it **always full-walks the remote**, so it never streams events and the cursor hazard cannot arise. Nothing is persisted or cleared: no event cursor, no drained `pending_changes`/`pending_deletions`, no `is_first_reconcile`/`force_local_rescan` cleared, no warm-start counter moved, no `last_sync`/`last_successful_sync_summary`/`last_plan_summary` set, no `sync_passes`/`sync_events` row (history is written behind a side effect, and there was none), no delete approval consumed, no `withheld_deletions` re-stamped, and not even the standing `unsyncable` list merged into — this pass's drops ride on the plan itself as `cannot_sync` (#315). The **apply** it authorises is re-plan-and-compare, never replay: `compute_directory_deletion_verdicts` proves a recursive delete against the actions that will *really* be planned (#282), so executing frozen rows could authorise a deletion nothing re-derived. A divergence returns an `Err` — not a clean pass that did nothing, which would set `last_sync` and draw "everything is up to date" over a plan still waiting (#246's shape) — after publishing the fresh plan under a new token. A **filtered** apply (#192) skips destructive rows at the *executor*, never by filtering the plan: the gate must still run over the full plan or `replace_withheld_deletions` wipes the #225 first-seen ages and `pending_deletions` blanks over deletions that are still real. A skipped row holds the event cursor for the same reason a withheld delete does. A **pause is asymmetric across the two verbs, deliberately**: it cancels a booked apply, but a booked *plan* still runs. Both halves follow from the same rule — every booked request must be sealed — because cancelling an apply *is* a seal (`discard_queued_apply_for_pause` seals it `Failed`) while returning early from `plan_now` would seal nothing, leaving `plan_outcome` on `Computing` for ever and the GUI's plan poller, which has neither a paused bail-out nor a timeout, hung on `Checking…`. So the plan's pause check lives at the **ack** only (`PlanOutcome::Paused`); `LoopCommand::PlanNow` reaches `plan_now` without one, and must keep doing so — "making it consistent with the apply" is the fix to refuse. It is safe because that pass is inert, which is the invariant's own first sentence. A paused bail-out in the *client* is wrong for the mirror reason: between the ack and `plan_now`'s `syncing.store(true)` a poller reads `paused && !syncing` for a pass that will run and seal, so it would report a pause for a plan that then completes — and for an `apply` it races the daemon's own typed verdict and substitutes a sentence the client made up (#103's shape). That bail belongs to `watch_syncnow` **alone**, because only a `syncnow` skipped by a pause is never sealed (`reconcile_if_needed` early-returns without bumping `reconcile_seq`, so its target is unreachable and only the client can end the wait); `poll_until`, which serves `plan` and `apply`, had copied it and must not (guard `a_pause_mid_wait_does_not_end_a_plan_or_apply_wait`). (Guards: `a_plan_pass_observes_and_consumes_nothing`, `a_plan_pass_is_visible_as_a_plan_on_the_activity_surface`, `a_second_plan_request_while_one_is_running_is_answered_by_that_pass`, `applying_a_reviewed_plan_executes_it`, `an_apply_whose_plan_moved_executes_nothing_and_publishes_the_new_plan`, `an_apply_landing_on_an_idle_cycle_still_reaches_the_comparison`, `an_apply_that_fails_before_deciding_still_seals_a_verdict`, `a_pause_cancels_an_apply_it_overtook_rather_than_latching_it`, `a_plan_pass_booked_before_a_pause_still_runs_and_seals`, `a_filtered_apply_drops_the_deletion_and_leaves_the_approval_standing`, `a_filtered_apply_still_reports_the_deletions_it_skipped_as_pending`, `the_plan_window_never_truncates_a_destructive_row`, plus `the_plan_verb_reviews_and_the_token_applies_that_exact_plan` and `a_filtered_apply_runs_the_plan_without_its_deletions` in `tests/ipc_cli.rs`.)
- **A node that vanished mid-pass is skipped, never recorded, and also holds the cursor.** A node listed at plan time can be trashed/deleted by another client before its transfer runs (#31). `proton.rs` classifies that one case (`NodeNotFound`, from the CLI's stderr); the executor skips **just that action** — no side effect, no index mutation, so it re-plans next pass — instead of failing the whole pass, and a batched chunk's staged siblings still land and checkpoint-commit. **`NodeNotFound` means "skip and replan", not "this node is confirmed gone".** `download` covers one file and is exact; `download_many` is one invocation over a whole batch whose note names no request, so *every* unstaged (exit 0) or unsalvaged (failed) file in that chunk carries the type — including one the CLI skipped for its own reasons (a Proton-native document). That misread costs a replan and nothing else, and it lasts only while a vanished node keeps the note in stderr. `skip_if_node_vanished` is the single classifier for every single-file download, so the two **conflict-sidecar** downloads (`Conflict`, `TypeConflict`) skip on the same signal — and there the skip must take the *record* with it: a `Conflict` row whose sidecar was never written has no exit and is invisible to the GUI's conflicts list (#46), and the next pass reaches `(Changed, Missing)` and copies the local file in instead. The disappearance is *not* treated as a confirmed remote delete (a "not found" can equally be a transient listing error or a permissions change, and a `Download` may be an update to a file that has a base record), so nothing is purged on that signal. Any skip forces `cursor_update` to `None` for the same reason a withheld delete does: the skipped node's event must stay in the next delta so ground truth re-derives it. Everything *else* (a failed listing, an upload, a delete, an unexplained transfer failure) still fails the pass. (Guards: `a_vanished_node_skips_its_download_and_the_rest_of_the_pass_still_runs`, `a_vanished_node_in_a_batch_does_not_fail_the_rest_of_its_chunk`, `a_vanished_conflict_sidecar_skips_the_whole_action_including_its_record`.)

- **History is written behind its side effect, and an idle pass writes nothing.** A pass's history rows (`PassLog` in `src/daemon.rs`) buffer exactly like `index_mutations`: a failed action truncates them back, a checkpoint drains them, and they commit **in the same transaction** as the index mutation they accompany — so a history row can never describe a side effect that did not land, nor survive a shutdown that discarded one. The rollup (`changed`/bytes) is folded only *after* a transaction commits, never from the live buffer. The `sync_passes` row is opened lazily by the first checkpoint that commits an event, with `outcome = interrupted` and duration `0` — the true values for a pass in flight — so a crash leaves an honest row and no startup repair sweep is needed; every graceful ending (clean, partial, **and failed**, including a shutdown mid-plan) seals it in `reconcile_blocking`'s three-arm outcome match, which is why `interrupted` is reachable only by a crash. A pass is recorded only when it **changed something, did not end clean, or was a full sweep**: the events-driven default polls every 30s (~2900 passes/day on a live account), so recording idle passes identically would evict every useful row within minutes — and "the daemon is alive and passing" is already answered by `reconcile_seq`/`last_sync_epoch_secs`. A changeless *full sweep* is still recorded, because "when did the last one run, and was anything out of step" is exactly what it answers (#238). (Guards: `idle_passes_record_nothing_at_all`, `a_full_sweep_that_changed_nothing_is_still_recorded`, `a_partial_pass_is_recorded_as_partial_and_only_the_landed_action_has_an_event`, `a_failed_pass_is_recorded_with_its_error`, `a_failure_storm_never_evicts_the_last_full_sweep`.)

### Testing pattern

`Daemon<C: ProtonClient>` is generic over the client. Tests inject fake `ProtonClient` implementations (see the fakes in `src/daemon.rs` tests — including one that fails uploads to exercise the checkpoint-commit invariant: completed actions stay committed, the failed action is never recorded — see the `reconcile_checkpoints_*` tests) so reconciliation is tested without a real Proton Drive. The planner in `src/sync.rs` is pure and tested directly with in-memory maps. Prefer adding regression tests next to the logic you change (planner tests in `sync.rs`, boundary tests where external paths first enter).

## Conventions

- Errors use `AppResult<T>` = `Result<T, Box<dyn Error + Send + Sync>>`; construct ad-hoc errors with `boxed_error(...)`.
- Structured logging via `tracing` to **stderr** (stdout is reserved for machine-readable dry-run JSON). Control verbosity with `RUST_LOG`; default is `info`.
- Uploads/downloads/deletes are never auto-retried (avoids duplicate side effects); only read-only remote listings retry per `proton_list_attempts`. Continuing past a failed action (#136) is not a retry: that action is attempted at most once per pass, exactly as before.
